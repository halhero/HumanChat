# 简化请求理解第一步：结构化契约修改记录

日期：2026-11-15。

## 1. 本步解决什么问题

HumanChat 当前会把用户原话直接用于长期记忆召回和主 Agent。像“继续”“按刚才那个方案”这类表达依赖前文，单独拿去检索时缺少真实主题；而“把它发给他”这类表达在缺少对象或接收者时，直接执行又可能产生错误行为。

本步只建立请求理解的独立能力边界，尚未修改 Graph：

```text
当前用户原话 + 有界近期对话
                ↓
       RequestUnderstanding
                ↓
resolved_request 或 clarification_question
```

## 2. 为什么只有两个字段

结构化结果只有：

```python
resolved_request: str
clarification_question: str
```

它们表达两个互斥结果：

- 请求可以可靠理解时，输出自包含的 `resolved_request`；
- 缺少的信息会实质改变回答、召回或工具选择时，输出最小澄清问题。

没有增加 `needs_clarification`，因为它会重复表达“澄清问题是否为空”；没有增加置信度、意图标签和原因，因为当前 Graph 没有这些字段的消费者。

## 3. 单一验证边界

`RequestUnderstanding` 在 Pydantic 模型中一次性检查：

- 两个字段不能同时为空；
- 两个字段不能同时有值；
- 不接受 schema 之外的额外字段。

下游节点将直接依赖这个契约，不再重复判断相同结构是否合法。模型返回非法 JSON 结构时异常会向上传递，本步没有增加重试、静默 fallback 或兼容分支。

## 4. Prompt 的职责

Prompt 明确要求模型只做 contextualization：

- 补全指代、省略和上下文依赖；
- 忠实保留原意，不回答、不执行、不编造；
- 自包含输入只做最小整理；
- 只有会改变实际处理方式的关键歧义才澄清；
- 澄清只询问继续处理所需的最小信息。

加入“继续”“按刚才那个方案”“把它发给他”三个短例子，是为了明确行为边界，而不是建立固定意图分类器。

## 5. 模型调用方式

`invoke_request_understanding()` 复用传入的现有聊天模型，通过 LangChain `with_structured_output(..., method="json_mode")` 获取结构化结果。没有新增模型配置、独立客户端、重试层或 fallback。

调用输入明确分为：

```json
{
  "recent_context": [],
  "current_user_input": "..."
}
```

本函数不读取数据库和 checkpoint，也不自行决定历史范围；调用方必须传入已经受限的近期上下文。

## 6. 测试覆盖与局限

聚焦测试验证：

- 自包含请求返回 `resolved_request`；
- 上下文依赖请求确实收到近期对话；
- 关键歧义返回单一澄清问题；
- 非关键歧义不强制澄清；
- 双空、双非空和额外字段在唯一边界失败。

这些测试验证程序契约和数据传递，不宣称模拟输出能够证明真实模型的语义判断质量。真实模型效果仍取决于 prompt、模型能力和后续代表性样例评估。

## 7. 本步未修改内容

本步没有修改 Graph、ChatState、长期记忆、工具循环、审批恢复、应用层、API 或前端。请求理解能力将在下一步接入现有 Graph。
