# 简化请求理解第三步：聚焦回归与实现说明

日期：2026-11-15。

## 1. 本阶段结论

本次功能已经形成两条明确且互斥的 Graph 路径：

```text
新用户回合
  -> initialize_turn
  -> understand_request
       -> 可以可靠理解
            -> build_memory_context
            -> call_agent_model
            -> 原有工具调用 / 审批 / 恢复循环
            -> finalize_reply
            -> finish_turn

       -> 缺少会实质改变处理方式的关键信息
            -> reply_clarification
            -> finalize_reply
            -> finish_turn
```

该实现只解决“把依赖上下文的当前表达整理为忠实、自包含请求，以及必要时澄清”这一问题。它没有建立固定意图分类体系，也没有引入任务状态机。

## 2. 为什么需要请求理解层

用户在连续对话中经常会说：

```text
继续。
按刚才那个方案做。
这个有没有问题？
你还记得我们之前说的吗？
```

这些句子本身通常没有足够的检索词。直接拿原话做长期记忆召回，可能找不到用户真正指向的项目、方案或问题；直接交给主 Agent，也会迫使后续每个模块各自猜测上下文。

请求理解层只做一次有限职责的转换：

```text
原话 + 有界近期对话
  -> 自包含的 resolved_request
  或
  -> 一个最小澄清问题
```

它不回答用户问题、不执行工具、不修改长期记忆，也不替代原始用户消息。

## 3. 原话与派生请求的数据流

### 3.1 原始用户输入

原话仍是系统中的事实来源，继续保存在：

- `question`；
- `input_source` / `SourceMessage`；
- checkpoint 中的消息历史；
- `finalize_reply` 提交的 `HumanMessage`；
- 后台记忆形成读取的证据消息。

本次没有把改写结果写入这些位置。

### 3.2 派生请求

`resolved_request` 是只在当前回合有效的语义视图，其生产者和消费者如下：

| 环节 | 行为 |
| --- | --- |
| `initialize_turn` | 将字段重置为空，防止上一回合泄漏 |
| `understand_request` | 唯一生产者 |
| `build_memory_context` | 将其作为长期记忆召回请求 |
| 主 Agent 请求组装 | 放入 system 信息块，并声明原话优先 |
| `finalize_reply` | 不保存该字段为用户消息或记忆证据 |

主 Agent 最终同时看到：

1. 原始用户 `HumanMessage`；
2. system message 中的 `resolved_request` JSON 信息块。

派生请求没有被伪装成第二条用户消息。system 信息还明确规定：如果派生语义与原话冲突，必须以原话为准。

## 4. 澄清回合如何工作

请求理解模型只在多个合理解释会显著改变回答、记忆召回或工具选择时返回 `clarification_question`。

此时 Graph：

1. 不执行 `build_memory_context`；
2. 不调用主 Agent；
3. 不进入任何工具节点；
4. `reply_clarification` 把澄清问题包装为内部 `AIMessage`；
5. 复用 `finalize_reply` 保存“用户原话 + 助手澄清问题”。

因此澄清是普通对话回合，而不是 LangGraph interrupt，也不会混入工具审批协议。用户下一次回答澄清问题时，会作为新的用户回合结合近期上下文重新理解。

## 5. 为什么同一回合只理解一次

`understand_request` 只位于 Graph 起始路径：

```text
START -> initialize_turn -> understand_request
```

工具执行、工具拒绝和工具结果都返回 `call_agent_model`，不会返回起点。工具审批恢复通过 LangGraph checkpoint 从中断位置继续，也不会重新经过 `understand_request`。

相关集成测试验证了同一回合即使发生工具循环或跨应用实例恢复，请求理解模型仍只调用一次。

## 6. 历史范围与运行成本

请求理解使用现有 `memory_history_tokens` 作为近期历史预算，没有增加新的配置项。

`recent_history()` 现在从消息尾部按完整对话组向前选择，预算无法容纳下一组时立即停止。这样新增请求理解节点不会为了获取少量近期上下文而先遍历和分组完整 thread 历史。

每个新的用户回合增加一次结构化模型调用：

```text
输入：当前原话 + token 预算内的近期对话
输出：resolved_request 或 clarification_question
```

工具循环和审批恢复不增加额外请求理解调用。该成本是本功能的明确代价，没有新增独立模型配置、重试层或 fallback 链。

## 7. 结构化输出边界

请求理解结果只有两个字段：

```text
resolved_request: str
clarification_question: str
```

边界规则是二者必须恰好一个非空，并拒绝额外字段。验证只发生在模型输出进入系统的请求理解模块，没有在下游节点重复增加相同检查。

非法输出会让当前回合明确失败，不会静默退回原始问题。这样可以避免系统表面成功、实际却绕过请求理解语义。

## 8. 本次修改涉及的生产文件

| 文件 | 职责变化 |
| --- | --- |
| `human_chat/request_understanding.py` | 定义 prompt、最小结构化结果和唯一调用边界 |
| `human_chat/schemas.py` | 增加两个仅限当前回合的派生状态字段 |
| `human_chat/graph.py` | 拆分初始化与记忆上下文节点，接入理解、路由和澄清路径 |
| `human_chat/memory/request.py` | 有界地从尾部选择近期对话，不再先分组完整历史 |
| `human_chat/conversation/protocol.py` | 将原有 thinking 进度事件映射到新的理解节点，保持外部协议不变 |

测试和阶段记录位于对应的 `tests/` 与 `资料/89`、`资料/90`、`资料/91` 文件中。

## 10. 明确未实现的内容

本次按批准边界没有实现：

- 固定意图标签或复杂路由矩阵；
- `TaskState`、`TaskWorkspace`、任务队列或暂停/恢复状态机；
- 跨所有历史会话搜索“之前聊过什么”；
- 请求理解专用模型配置、重试或自动 fallback；
- 长期记忆模型、数据库、索引、worker、job 或召回算法调整；
- 前端、公开 API、会话协议和工具审批协议调整。

## 11. 剩余风险与后续可改进点

自动测试证明了数据流、路由和边界契约，但 fake model 不能证明真实模型在所有自然语言表达上的改写质量。实际效果仍取决于当前模型对指代、歧义和近期上下文的理解。

后续如有真实对话证据显示过度澄清、错误消歧或语言不一致，应优先根据失败样本调整 prompt 和少量高价值示例，而不是立即增加置信度、意图标签、重试链或新的状态系统。
