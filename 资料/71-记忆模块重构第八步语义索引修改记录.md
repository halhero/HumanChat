# 第八步：真实语义索引与派生数据同步

## 1. 本步解决什么

**本步的重点是建立一份可以重建的检索表示，并防止它在主记录变化后继续冒充最新事实。** 仅仅调用 embedding API 不足以完成记忆检索，更新和删除的一致性同样属于本步工作。

关键词检索无法理解“先说结论”和“先给判断”的语义联系。因此本步引入真实 embedding 接口，而不是用固定向量冒充语义检索。主记录仍由现有 JSON/LangGraph Store 保存，向量只是可重建的检索投影，不是第二份权威记忆。

## 2. 实际修改

- `human_chat/memory/index.py`：新增 `MemoryView`、`memory_views`、`MemoryIndex` 和 `create_embeddings`。
- `memory/service.py`：所有真实写入经过 `_persist`；索引挂接后收到变更通知，删除同步清除索引快照里的正文。
- `config.py`：增加 embedding 模型、地址、独立密钥配置。空地址/密钥沿用现有模型服务，不将真实凭据写入代码。
- `requirements.txt`：声明向量库所需 numpy；`.gitignore` 排除本轮隔离验证目录。

`InMemoryVectorStore` 是 LangChain 的向量存储实现，负责相似度计算和快照读写。这里不重新实现余弦相似度。适配器管理记录版本、同步和删除，这些是项目业务语义，不是向量库自动负责的事。选择它是因为目前是单进程、小规模项目；没有为了检索强制迁移数据库。

## 3. 数据流和关键代码

```text
主记录 inventory -> 当前/历史 MemoryView -> 仅对新正文请求 embedding
                -> LangChain 向量存储 -> 原子替换索引快照
查询 -> query embedding -> LangChain 相似度 -> 记录ID/父版本
```

索引条目包含父记录版本。后续读取必须回到主记录校验，不能直接相信快照中的旧正文。历史、撤销、过期状态也明确区分，不能一律视为当前事实。

`sync` 在网络请求前记录 generation；写入或删除会递增 generation。如果 embedding 很慢，在这期间发生删除，旧同步结果会被丢弃。网络调用不占主存储锁。相同正文可复用已存向量，避免仅证据变化就重复付费。

快照先写临时文件，再替换正式文件。更换 embedding 配置后旧向量清空重建，避免不同向量空间混用。这里是可重建索引，不改动主记录。

默认模型 `text-embedding-v4`，批次限制为10，关闭 OpenAI token-array 输入转换，使用字符串和 float 输出。参数依据[百炼官方说明](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)。地址仍可配置，不强制覆盖用户现有可用端点。

### 3.1 先区分三个东西，避免把向量库当记忆主库

| 对象 | 保存/计算什么 | 丢失时怎么办 |
| --- | --- | --- |
| Repository 中的 MemoryItem | 认识、证据、版本、历史、回执 | 不能靠向量推回这些事实 |
| Embedding 模型 | 把文本编码为一组数字；相近语义常有较近表示 | 服务不可用时记录检索降级 |
| MemoryIndex | 文本向量与记录 ID/版本的对应关系 | 从主记录重新计算和建立 |

例如“先给判断”和“先说结论”没有完全相同的词，向量可能接近。但向量接近只说明语义相似，不说明一定适用于本轮任务，更不说明它是真实、未过期的当前状态。资料72负责组合候选，资料74才负责用途判断。

### 3.2 为什么要多一层 MemoryView

一条 MemoryItem 可能带若干历史版本。检索“现在项目怎样”和“以前项目怎样”需要区分这些版本，因此 `memory_views()` 展开为视图：

```text
主记录 m1，第3版：暂停；history 中保存第2版：进行中
    -> m1@3：version=3，parent_version=3，status=current
    -> m1@2：version=2，parent_version=3，status=historical
```

`version` 是该视图展示哪版内容，`parent_version` 是展开时主记录处于哪版。为什么旧视图也带父版本？如果后来纠错把第2版标成 revoked，即使历史正文没变，旧索引也已不可信；父版本变化可以让读取端拒绝旧投影。

deleted 记录不生成视图；retracted 生成 revoked 状态供维护辨别，回答召回会排除它。索引包含历史或错误内容是为了维护比较，不代表所有索引项都可直接拿来回答。

### 3.3 sync 怎样避免重复费用和删除复活

实际 [index.py](../human_chat/memory/index.py) 先按正文查缓存，只编码缺失正文：

```python
views = memory_views(service.inventory())
missing = list(dict.fromkeys(v.text for v in views if v.text not in cached))
if missing:
    vectors = self.embeddings.embed_documents(missing)
    if len(vectors) != len(missing):
        raise ValueError("Embedding response count does not match input")
    cached.update(zip(missing, vectors))
```

`dict.fromkeys` 在这里保持出现顺序并去重；`zip` 把每段正文与响应向量一一配对。响应数量必须相同，否则不能把错位向量写入。重复确认只更新证据、正文未变时，可以复用向量。

网络请求放在锁外，否则慢 embedding 会长时间挡住删除。这样又产生一个竞争问题：

```text
sync 读取 m1，记下 generation=7 -> 请求 embedding
用户删除 m1 -> changed 清理索引，generation 变为8
旧 embedding 返回 -> generation 不等 -> 丢弃这一轮同步结果
```

对应代码是 `if generation != self._generation: return False`。generation 是索引同步期间的变更计数，与 m1 的业务 version 不同；它保护一次同步快照不会把中途发生的删除覆盖回去。下一次后台循环从当前主记录重新同步。

### 3.4 查询结果只是一张待核对的索引卡

`search` 先 `embed_query`，再调用 LangChain 的 `similarity_search_with_score_by_vector`，返回 `(视图ID, 分数, 父版本)`。下一层拿 ID 回到本次 inventory 生成的视图检查。索引里的 text 不直接进入回答请求，因此旧向量命中也不能跳过当前状态校验。

最终集成又补了 `covers(views)`：即使查询没有返回旧项，也要知道索引是否覆盖当前全部视图。缺项会标记 semantic_projection_incomplete。否则一次“零命中”可能只是新记录尚未建索引，却被维护模块误解成库里没有旧认识。

### 3.5 为什么选择现有框架，再加这些项目代码

LangChain 提供向量存储、相似度查询和快照读写；项目代码负责 m1@3 与证据、撤销、删除之间的业务关系。框架不知道“用户纠正后旧认识不能再当真”，因此这些规则仍需要项目实现。

当前适配器直接组织 `InMemoryVectorStore.store` 中的行，以复用向量并原子替换快照。代价是依赖这一实现的数据结构，升级 LangChain 时要复核；它也不是大规模远程向量数据库。快照含正文和向量，不应当作无敏感内容的缓存上传 GitHub。更换编码模型或地址后重建投影，不修改主记录。
