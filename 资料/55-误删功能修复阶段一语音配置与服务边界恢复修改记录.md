# 误删功能修复阶段一：语音配置与服务边界恢复修改记录

## 1. 本阶段目标

前后端分离阶段二删除旧 CLI 时，把“服务器本地录音、服务器本地播放”与“语音业务能力”
一起删除了。前两项确实不适合 Web 架构，但角色音色配置、STT 服务调用和 TTS 服务调用
并不属于 CLI，不应因此消失。

本阶段只恢复不依赖具体界面的语音核心能力：

1. 恢复角色文件中的 TTS 音色配置；
2. 恢复 STT 与 TTS 环境配置；
3. 建立可被 FastAPI、脚本或未来其他适配器复用的语音服务接口；
4. STT 直接处理内存中的音频字节，不要求服务器本地文件路径；
5. TTS 返回音频字节，不写固定文件，也不在服务器扬声器播放；
6. 明确 `tts_auto_start` 只控制进程所有权，不控制 TTS 功能是否可用。

本阶段不添加 HTTP 路由和前端按钮。资源生命周期、API 和浏览器交互会在后续阶段接入，
避免一次提交同时改变配置、服务、HTTP 契约和 UI，降低审查难度。

## 2. 为什么角色 TTS 配置必须保留

`characters/nanami.yaml` 描述的是角色本身，其中既包括文本行为，也包括角色如何发声：

```yaml
tts:
  ref_audio_path: ...
  prompt_text: ...
  prompt_lang: ja
  text_lang: ja
  split_method: cut5
  speed_factor: 1.0
```

这些字段不是 CLI 的显示配置，而是 GPT-SoVITS 合成请求所需的角色音色参数：

- `ref_audio_path`：TTS 服务可访问的参考音频；
- `prompt_text`：参考音频对应的文字，用于帮助模型对齐音色与发音；
- `prompt_lang`：参考文本语言；
- `text_lang`：待合成文本语言；
- `split_method`：长文本切分策略；
- `speed_factor`：语速倍率。

新的 `CharacterTtsConfig` 恢复了这组结构，同时将 `Character.tts` 定义为可选字段：

```python
tts: CharacterTtsConfig | None = None
```

这样既不会丢失七海的音色，也允许未来存在纯文本角色。某个角色没有配置 TTS 时，后续
API 会明确报告该角色不支持语音，而不是让整个角色配置加载失败。

`speed_factor` 使用 Pydantic `Field` 限定为 `0.25` 到 `4.0`。配置在系统启动时就会被
校验，明显错误的语速不会等到请求外部 TTS 服务后才暴露。

## 3. STT 服务为什么接收 bytes

旧 `stt.py` 的公开函数接收服务器本地路径：

```python
transcribe_audio_file(settings, audio_path)
```

CLI 时代，音频文件和 Python 进程位于同一台电脑，这种形式可以工作。Web 架构下，音频
来自用户浏览器，浏览器本地路径对服务器没有意义。正确的数据流是：

```text
浏览器录音或选择文件
        -> HTTP 上传音频字节
        -> FastAPI
        -> SpeechToTextService.transcribe(bytes, metadata)
        -> 外部 STT 服务
```

因此新的 `SpeechToTextService` 接收：

```python
audio: bytes
filename: str
content_type: str
```

`filename` 和 `content_type` 是发送给 OpenAI 兼容接口的文件元数据，不用于读取服务器
磁盘。这样 API 不需要创建共享临时文件，也不会发生两个并发请求同时覆盖 `input.wav`
的问题。

## 4. Protocol 的意义

STT 和 TTS 都先定义 `Protocol`：

```python
class SpeechToTextService(Protocol):
    def transcribe(...) -> str:
        ...
```

`Protocol` 是 Python 的结构化接口。实现类不需要继承这个 Protocol，只要提供相同的方法
签名，就能被类型检查器和上层代码当成该服务使用。

对商业项目而言，这层边界有三个作用：

1. Application 不依赖 OpenAI SDK 或 GPT-SoVITS 的实现细节；
2. 将来更换云厂商时，只新增适配器，不需要修改会话和 Graph；
3. API 层不直接拼接供应商参数，供应商变化被限制在语音模块内部。

当前实现包括：

- `OpenAICompatibleSttService`：调用 OpenAI 兼容的 transcription API；
- `GptSoVitsTtsService`：调用 GPT-SoVITS 兼容的 `/tts` HTTP 接口。

## 5. TTS 为什么返回音频而不播放

旧 `TtsClient.synthesize_and_play()` 同时承担四件事：

1. 构造 TTS 请求；
2. 调用 TTS 服务；
3. 把返回值写入固定的 `speech/tmp.wav`；
4. 通过 `simpleaudio` 在服务器扬声器播放。

这违反了前后端分离后的设备边界。部署到服务器后，真正使用耳机和扬声器的是浏览器
所在设备，不是 FastAPI 所在设备。

新的 TTS 接口只返回：

```python
SynthesizedAudio(content: bytes, media_type: str)
```

后续 FastAPI 可以把 `content` 作为 HTTP 响应返回，浏览器再用 `Audio` 或 Web Audio API
播放。这样支持远程访问、多用户并发，也不再依赖共享文件路径。

## 6. `tts_auto_start` 的正确语义

恢复的配置包括：

```env
HUMANCHAT_TTS_SERVICE_URL="http://127.0.0.1:9880"
HUMANCHAT_TTS_AUTO_START="false"
```

二者负责不同问题：

- `TTS_SERVICE_URL` 回答“请求应该发到哪里”；
- `TTS_AUTO_START` 回答“这个服务进程由谁启动”。

因此：

```text
auto_start=false + 后台服务已运行 -> 可以正常合成
auto_start=false + 后台服务未运行 -> 请求时报告服务不可用
auto_start=true  + 后台服务已运行 -> 复用已有服务，不重复启动
auto_start=true  + 后台服务未运行 -> HumanChat 尝试启动本地服务
```

`GPT_SOVITS_DIR`、`GPT_SOVITS_PYTHON` 和 `GPT_SOVITS_API_SCRIPT` 只在自动启动时需要。
不能因为这三个字段为空，就禁止调用已经由用户在后台启动的服务。

进程探测和自动启动属于 Application 资源生命周期，将在阶段二实现。本阶段先恢复配置，
并确保其语义不再被错误解释为功能开关。

## 7. 错误边界

语音模块定义了两种稳定的应用异常：

- `SpeechRecognitionError`：音频为空、供应商调用失败或没有识别文本；
- `SpeechSynthesisError`：文本为空、TTS HTTP 失败或返回空音频。

外部 SDK 和 HTTP 库的原始异常通过 `raise ... from exc` 保留为异常链，便于服务器日志
定位根因；上层 API 后续只需要识别稳定的业务异常，不必了解每家供应商的异常类型。

## 8. 依赖调整

`requirements.txt` 显式增加：

- `openai`：STT 供应商适配器的直接依赖；
- `httpx`：TTS HTTP 客户端的直接依赖。

即使其他库可能间接安装它们，项目直接 import 的包也应声明为直接依赖。否则上游库一旦
调整自己的依赖关系，HumanChat 会在没有修改代码的情况下突然无法启动。

没有恢复：

- `sounddevice`：服务器麦克风录音不属于 Web 后端；
- `simpleaudio`：服务器本地播放不属于 Web 后端；
- `requests`：项目统一使用支持现代连接管理的 `httpx`。

- `human_chat/config.py`：恢复 STT/TTS 和可选本地服务启动配置；

## 10. 明确没有恢复的旧实现

以下删除仍然是合理的，本阶段没有回退：

- CLI 的 `TextInputProvider`、`AudioFileInputProvider` 和 `MicrophoneInputProvider`；
- 服务器端 `sounddevice` 录音；
- 服务器端 `simpleaudio` 播放；
- 固定 `data/audio/input.wav` 和 `speech/tmp.wav`；
- Graph 内每次回答后强制执行的 TTS 节点；
- 旧 `ChatRuntime` 和 CLI 主循环。

语音是独立应用能力和表现层能力，不应重新成为 LangGraph 的固定节点。文本回答完成与
否，不应该由音频设备或 TTS 服务是否在线决定。

结果确认：

- Python 模块编译通过；

## 12. 下一阶段
