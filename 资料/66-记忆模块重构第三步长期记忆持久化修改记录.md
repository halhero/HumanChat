# 记忆模块重构第三步：长期记忆持久化

日期：2026-10-15。前置资料65；前置提交 `f19bd1d`。

## 1. 改了什么

将现有 Repository、Service、资源组装迁入 `human_chat/memory/`，同步更新 Application、Graph 和测试导入，删除旧模块而非保留转发文件。数据模型、业务维护、底层存取开始聚合为同一个明确子系统。

Repository 增加同一存储资源的进程内锁入口，为下一步原子读改写提供边界；Store 读取按明确的 Item 契约处理，移除猜测字典/对象以及 Pydantic 版本的分支。保留原有分页、精确 namespace、JSON 临时文件替换。

## 2. 为什么不是重新造数据库

**这一步需要回答得非常具体：调用谁之后数据才真正保存？应用重启后又从哪里读回来？** 资料65定义的 Pydantic 对象只存在于内存；有字段、有 `model_dump` 都不等于已经持久化。

现有 JSON 与 LangGraph Store 已能保存完整字典。新需求主要是确保新字段真正经过序列化，并将比较旧版本与保存新版本放在同一读改写边界。没有理由再造一个 JsonStore，或为这一步强迫迁移 PostgreSQL。

`MemoryResource` 继续向上提供 Service、backend 和 persistent，Repository 与实际 Store 留在内部。JSON 和 PostgresStore 是持久后端；InMemoryStore 只是运行期数据，其资源关闭重建后不承诺保留。

## 3. 数据怎样落盘

```text
MemoryItem（正文、版本、来源、历史、回执）
  -> Repository.upsert_item
  -> model_dump(mode="json")
  -> JSON 临时文件替换，或 Store.put
  -> 新 Repository 读取
  -> MemoryItem 校验并恢复完整结构
```

JSON 临时替换避免半份文件被当成完成结果，不等于多进程事务。Store 的单条 put 也不等于与检查点和任务表共同原子提交。共享锁按文件路径或 Store 实例及 namespace 标识，只针对当前单进程模型，不承诺跨进程 CAS。

`list_items()` 是列举，不是语义搜索。真正向量索引在第8步建立，本步没有把现有 search 调用包装成语义能力。

### 3.1 三个文件的分工，用“暂停项目”说明

| 文件/入口 | 在这次操作中负责什么 | 不负责什么 |
| --- | --- | --- |
| `resources.open_memory_resource` | 按配置建立 JSON 或 Store 适配器，再交给 Service | 不理解“暂停”的含义 |
| `service.LongTermMemoryService` | 后续检查预期版本，只合并 state，然后请求保存 | 不知道 JSON 临时文件如何命名 |
| `repository.upsert_item` | 按 item.id 替换完整记录，并保存全部字段 | 不知道这次变化是否获得原话支持 |

`upsert` 就是“有这个 ID 则更新，没有则新增”。它很容易实现，但没有业务含义：把错误的完整对象交给它，它也会忠实保存。所以把 Repository 隐藏在 Service 内部有实际意义，自动维护必须先过 `apply`，不能从 Graph 直接绕到 `put`。

### 3.2 JSON 路径：完整对象到底如何变成文件

`JsonMemoryRepository.upsert_item` 的核心代码：

```python
memory = self._load_memory(namespace)
memory.items = [existing for existing in memory.items if existing.id != item.id]
memory.items.append(item)
self._save_memory(namespace, memory)
```

它读出当前集合，去掉同 ID 旧项，加入完整新项。这里不是“只把 state 一个字段写进 JSON”；字段合并已由上层完成。`_save_memory` 再序列化整个集合，关键动作如下（省略临时文件清理）：

```python
temporary_path.write_text(
    json.dumps(_model_to_dict(memory), ensure_ascii=False, indent=2),
    encoding="utf-8",
)
temporary_path.replace(path)
```

`_model_to_dict` 实际调用 `model_dump(mode="json")`，连同嵌套的证据、历史、回执一起转换。先写临时文件再替换正式文件，可以避免正常读取遇到只写了一半的 JSON；它不保证断电时的完整磁盘耐久性，也不能解决两个独立进程互相覆盖。

读回时 `json.loads` 先还原字典，`LongTermMemory(**data)` 再还原嵌套模型。`**data` 是把字典键值展开为构造参数，并不是多存一份数据。

### 3.3 LangGraph Store 路径：框架已经负责什么

```python
# LangGraphMemoryRepository.upsert_item
self.store.put(namespace, item.id, _model_to_dict(item))
```

同一份业务记录交给框架 Store 保存；namespace 是空间，例如 `("users", "default", "memory")`，item.id 是空间里的记录键。`get(namespace, id)` 取回 `Item`，适配器用其 `value` 恢复 `MemoryItem`。因此本项目确实使用 LangGraph 的存储实现，MemoryService 是其上方的业务规则，不是另一个数据库。

列举用了 `store.search(namespace, limit=100, offset=...)`。这里没有查询向量，仅分页取数据；还要检查返回项的 namespace 完全相等，避免前缀匹配把子空间混进来。语义索引在资料71单独讲。

### 3.4 为什么新增 locked，而没有把所有层都锁一遍

需要保护的是“读取第2版 -> 检查第2版 -> 写成第3版”这一整段。如果只在最终文件写入时加锁，两段操作仍可能都先读到第2版，后写的覆盖先写的。

`Repository.locked(namespace)` 提供共享资源锁；Service 在完整读改写范围内使用它。JSON 按规范化文件路径共用锁，Store 按实例和 namespace 共用锁。`@contextmanager` 加 `yield` 把获取/释放包装为 `with` 块；`RLock` 允许同一线程在内部调用 inventory 时再次进入。

当前锁是**进程内协调**。不能据此启动多个服务进程共同写同一 JSON，也不能把它描述成数据库的跨进程条件更新。将来真的部署多进程时，需要后端事务或 CAS，而不是再增加一层 Python 锁。

### 3.5 存储选择与资源关闭

| 后端配置 | 实际对象 | 重建后的数据 |
| --- | --- | --- |
| `json` | JsonMemoryRepository | 文件保留，可以读回 |
| `memory` | LangGraph InMemoryStore | 新建 Store 后为空 |
| `postgres` | LangGraph PostgresStore | 依赖数据库持久保存；本轮未实连验收 |

`MemoryResource` 保留 service/backend/persistent；索引字段是后面接入时增加的。`open_memory_resource` 用 `yield` 交出资源，Application 的上下文管理器退出时关闭其持有的外部连接。上层用 Service，不必根据后端写三套聊天逻辑。

## 4. 实际案例与验证

在隔离存储中写入版本2的“记忆模块暂停”，同时带主体、旧版本、原文依据和操作回执。重新创建 Repository 后读回整个对象，要求结构完全相等，而不只比较 text。

实际执行仓储与资源相关检查10项，通过。包括 JSON 和真实 InMemoryStore 的完整记录往返、分页、namespace 与资源边界。Store 用例是在同一个内存 Store 上重建适配器，不把它表述为进程重启持久化。
