# 第十四步：统一切换到透明自动记忆

## 1. 本步目标与实际行为

**本步的核心不是增加一个后台开关，而是改变聊天完成与记忆维护之间的调用关系，并清掉旧审批链的所有入口。** 前面组件分别可用，还不等于真实聊天已经使用它们。

前十三步分别建立了数据、存储、形成、检索、上下文和后台任务能力，本步把它们接成唯一运行链路。

回答前：任务上下文构建 -> 整体预算 -> Graph 模型输入。

回答完成后：checkpoint -> 登记后台任务 -> 前台 turn.completed；后台独立形成计划、保存和同步索引。用户不需要批准，不显示“正在保存/保存几条”，也不等待后台处理完成。

这是自动保存环节不可感知，不是删除用户主动管理记忆的能力。原有可主动打开的记忆管理界面及手工添加/删除接口保留；危险工具仍必须审批。

## 2. 文件与职责调整

### 应用和资源

- `memory/resources.py`：在真实资源构造时挂接一个语义索引，仍只由服务访问主 repository。没有把 LangGraph Store 重复传入 Graph。
- `application.py`：组装 Retriever、ContextBuilder、Formation、Jobs、Worker；从不可变 checkpoint 读取原始来源，管理启动/关闭。
- `config.py`：提供 `memory_semantic_enabled`，默认开启。明确关闭表示接受无语义服务的降级，不是伪装成正常语义检索。
- `.gitignore`：排除本地任务数据库及临时记忆文件，避免运行数据意外上传。

### Graph

- 移除 memory_prompt 以及“未注入构建器就全量拼接”的过渡入口。所有回答分支使用同一装配函数。
- 新增终点 `finish_turn`；取消任务用 `update_state(as_node="finish_turn")` 清理未完成节点，不调用工具，也不伪造记忆批准。
- 每轮重置 assistant_text，防止沿用上一轮完成标记。

- `web/src/App.tsx/api.ts/types.ts/ReviewDialog.tsx/styles.css` 删除记忆勾选状态、保存通知与专用样式。工具确认按钮保留。
- `MemoryService.format_for_prompt` 删除，服务只提供记录，不再负责提示词；职责由 ContextBuilder/请求装配承担。

## 3. 为什么后台不能只 enqueue 一次就结束

### 3.1 先把修改前后的时序对照起来

```text
修改前：回答 -> finalize_reply -> 提取 -> memory_review中断
                                  -> 用户勾选批准 -> 保存 -> 回合结束

修改后：回答 -> finalize_reply -> finish_turn -> checkpoint
                                           -> 登记任务 -> 前台回合完成
后台线程：收到任务 -> 读原话 -> 形成并保存计划 -> apply -> 任务done
         -> 另行同步索引
```

前台仍会做短暂的任务登记，不等待后台提取与复核模型。后台可能在前台最终事件发出前已经开始，也可能稍后开始；代码不要求二者具有固定先后时间，只要求前台不等待后台维护结束。

自动保存不再弹窗和通知，但回答前的上下文适用性模型调用仍在前台，会影响回答等待时间。“保存不可感知”不能被夸大成“整个记忆系统没有延迟或成本”。

### 3.2 Application 究竟注入了什么

`open_human_chat_application` 在资源已打开后建立依赖，主要关系如下：

```text
MemoryResource.service + index -> MemoryRetriever
Retriever + 辅助LLM            -> MemoryContextBuilder -> Graph
同一Retriever/Service/辅助LLM  -> MemoryFormation -> MemoryWorker
Checkpoint + SessionRepository -> Application加载来源/登记任务
```

这是依赖注入：创建组件的地方决定它使用哪个具体对象，业务函数只调用已经提供的对象。Graph 不在每轮临时打开数据库，Formation 也不自己再创建一个记忆库，因此读取与写入针对同一份 Service。

Repository 仍在 Service 内；Store 也没有多余地交给 Graph.compile。LangGraph 负责对话图和 checkpoint，LangChain 负责消息、结构化输出和向量实现，项目负责维护政策与任务生命周期。各层框架化不意味着把所有业务都塞成 Graph 节点。

### 3.3 正常登记发生在哪几行

[application.py](../human_chat/application.py) 的 `_stream_graph` 完成图迭代后执行：

```python
snapshot = self._graph.get_state(self._graph_config(session.thread_id))
self._enqueue_memory_sources(session, snapshot)
```

`_enqueue_memory_sources` 只选有可信时间、后面跟着助手消息的用户来源；正常路径还要求 source.id 等于当前 input_source.id。它传给队列的是 user/thread/checkpoint/source/time，不是整段聊天正文。

正在等待工具批准的回合没有新完成问答，不应登记为已经完成的来源；取消也不应把上一轮 assistant_text 当成新完成标记。所以 `prepare_context` 每轮清空本轮工具状态及 assistant_text，保留已提交消息历史。

### 3.4 启动对账补哪个间隙

checkpoint 与任务表不是同一事务。若 Graph 已提交但进程在 enqueue 前退出，单靠现场登记会丢任务。应用启动时读取会话当前 checkpoint 中已完成的用户/助手消息对，对有可信来源时间的用户消息登记稳定任务ID；已登记任务 INSERT OR IGNORE，不重复执行。正常每轮只登记当前来源，避免每次重新遍历提交全部历史任务。

任务定位持久 checkpoint ID，恢复时不把后来对话当成当时的上下文。不完整轮次、无来源时间的旧消息不自动变成新证据。必要前文按预算保留完整轮次，原始消息仍存在 checkpoint。

如果 checkpointer 不持久，任务库也只使用内存，不能承诺进程重启后恢复。默认 SQLite checkpoint 才具有上述持久恢复能力。

后台 `_load_memory_source` 用记录的 checkpoint_id 读取指定快照，定位 source_id，只取它**之前**的必要消息为 context_messages。它不会读取最新会话再随意挑出一段后来的讨论，避免未来发言污染当时依据。

这个恢复能力依赖 checkpoint 仍可访问；当前没有检查点归档/删除与任务引用的联合保留政策。对账也扫描已知会话，启动成本会随历史增长。这些是实际生命周期边界，不应称为无限历史自动恢复。

## 4. 旧中断与删除

### 4.1 为什么不能直接批准旧 memory_review

旧检查点可能停在已删除的审批节点。若自动 resume 为 approve，既违反新的无感流程，也会把旧文本候选绕过新依据检查直接保存。现在只识别 type=memory_review 并退役它；工具中断保持原审批语义。

`discard_pending_turn` 使用 LangGraph 的 `update_state(..., as_node="finish_turn")`：告诉图从终点语义更新状态，清掉未完成执行分支而保留已提交历史。它不是实际执行一次工具，也不是把批准字段偷偷设为 True。调用者必须先停止正在运行的前台回合，避免同时恢复和取消。

旧 checkpoint 中若停在 memory_review，不自动批准旧候选；结束旧保存阶段，再仅依据可信原话由新链路重新判断。对危险工具中断不作这种处理。

服务删除依次使主记录成为无正文墓碑、清除索引、清除有关待执行计划。旧来源重新换一种描述也不能重新写回；持续禁记身份还提供给语义复核，规范身份同时由存储边界确定性拦截。跨任意同义表述的语义判断不是数学保证，本轮不假装能完全解决这一点。

### 4.2 为什么后端改了，前端和 API 也必须改

只删 Graph 节点会留下 UI 等待永远不会发生的“保存成功”事件，或让旧 selected_item_ids 混入工具审批。因此本步同时删除 memory.saved 消费、候选勾选状态、记忆审批类型；工具 approve/reject 保留。最终集成还用 extra=forbid 拒绝旧请求字段，避免误把旧记忆批准当成工具批准。

主动记忆管理界面仍走 Application.add_memory/delete_memory；“自动保存不打断对话”和“用户能主动查看/删除”兼容。STT、TTS、角色和 MCP 注册也仍通过原资源入口创建，没有因移除记忆审批而删除。

### 4.3 为什么关闭顺序是功能的一部分

Application 退出先 close_memory_worker：通知停止并等待线程结束，再解除删除回调、关闭 Jobs。随后外层 with 块才释放工具、语音、记忆和 checkpoint 等资源。反过来先关 checkpoint，后台还在 load_source，就会出现正常退出时的数据读取失败。

## 6. 仍有限制

单进程工作线程，不支持多 worker/分布式部署；后台保存有短暂延迟，紧接着提问可能在保存完成前发生。前台不等待后台，这是透明性与即时一致性的明确取舍。原始聊天记录不会随“删除长期记忆”删除；模型语义误判、第三方服务不可用、大规模目录预算仍是需要诚实保留的风险。
