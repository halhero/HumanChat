# 前后端分离阶段二：会话与流式对话接口修改记录

## 一、这一步要解决什么问题

阶段一只建立了 FastAPI 应用、统一生命周期和健康检查。它证明后端可以作为一个
长期运行的服务启动，但独立前端仍然不能真正聊天，因为当时还缺少以下能力：

1. 前端无法创建、列出或重新打开会话。
2. 前端无法提交一条用户消息。
3. 模型调用耗时较长时，普通 JSON 接口只能一直等待，无法显示进度。
4. LangGraph 遇到工具审批或长期记忆审批后会暂停，但 HTTP 层还不知道如何把
   暂停信息交给用户，也不知道如何恢复原来的 Graph。
5. 同一个会话若同时提交两条消息，可能竞争同一个 `thread_id`，造成 checkpoint
   顺序混乱。
6. 浏览器断开连接或用户点击停止时，后端需要有明确的协作取消机制。
7. CLI 的 TTS 会在后端机器扬声器播放；前后端分离后，这不再是正确的 Web 行为。

因此，本阶段不是简单增加几个路由，而是建立一个位于 FastAPI 和 LangGraph 之间的
“应用服务层”。它负责 Web 交互需要的运行管理，但不取代 LangGraph 的状态管理。

---

## 二、最终架构

本阶段形成了下面的调用关系：

```text
React 前端（下一阶段）
        |
        | HTTP + SSE
        v
FastAPI 路由层
  - 校验公开请求
  - 返回公开响应
  - 转换预期错误
        |
        v
ConversationService 应用服务层
  - 同一会话并发保护
  - 活跃 turn 生命周期
  - SSE 公开事件映射
  - 暂停、恢复、取消
        |
        v
ChatRuntime
  - thread_id / graph_config
  - SessionRecord 更新
        |
        v
LangGraph compiled graph + Checkpointer
  - 对话状态
  - 节点路由
  - interrupt / Command(resume=...)
  - 短期记忆 checkpoint
```

这套结构最重要的原则是：

> LangGraph 仍然拥有 Agent 的执行状态，ConversationService 只拥有 Web 进程内的
> 交互状态。

例如，“当前执行到了哪个 Graph 节点”“工具调用后下一步去哪里”“审批后从哪里恢复”
仍由 LangGraph 和 Checkpointer 决定。`ConversationService` 只记录当前 HTTP 客户端
对应的 `turn_id`、是否正在运行、是否等待用户确认，以及应该向浏览器发送什么事件。

这样不会出现两套互相冲突的状态机。

## 三、为什么新增 application 层

### 3.1 路由层不应该直接编排 Graph

如果在 FastAPI 路由中直接写下面的逻辑：

```python
result = graph.invoke({"question": payload.question})
return result
```

短期看代码很少，但会马上产生问题：

1. 每个路由都要理解 LangGraph 的内部 state。
2. 路由需要自己解析 `__interrupt__`。
3. 取消、并发锁、SSE、异常清理会全部堆在路由函数里。
4. 将来增加桌面端、WebSocket 或移动端接口时，逻辑只能复制。
5. Graph state 中的 `tool_messages`、工具参数、调试事件可能被不小心返回给用户。

因此新增 application 包，并进一步按职责拆成三个文件：

```text
human_chat/application/
  conversation_models.py    # turn 状态、公开事件、进程内模型和业务异常
  conversation_protocol.py  # Graph 更新到公开事件、审批决定到 resume 值
  conversation_service.py   # 会话占用、工作线程、队列和生命周期协调
```

这个拆分很重要。若把数据结构、协议转换和并发协调全部放进一个 Service 文件，功能
继续增加后仍会形成新的“大文件”。现在三个模块的变化原因不同：

- 增加一种 turn 状态时，修改 `conversation_models.py`。
- 调整前端事件或审批规则时，修改 `conversation_protocol.py`。
- 调整并发、取消和资源回收时，修改 `conversation_service.py`。

API 通过 `human_chat.application` 的公开导出使用这些类型，不依赖文件内部的私有布局。

FastAPI 只依赖 `ConversationService` 提供的用例，不直接操作 Graph 的内部细节。

### 3.2 应用服务不是 Repository

`ConversationService` 和 Repository 的职责不同：

- Repository 负责数据如何保存和读取。
- Service 负责一个业务操作怎样协调多个对象。
- FastAPI Router 负责 HTTP 协议。
- LangGraph 负责 Agent 工作流。

例如“开始一轮对话”需要：

1. 加载会话元数据。
2. 检查该会话是否已经有活跃 turn。
3. 创建 session-scoped `ChatRuntime`。
4. 分配 `turn_id`。
5. 在工作线程执行同步 Graph stream。
6. 把内部更新转换为公开 SSE 事件。
7. 完成、失败或中断时正确释放会话占用。

这显然不是单纯的持久化操作，所以应由应用服务协调。

## 四、会话接口

本阶段新增以下接口：

```text
GET  /api/v1/sessions
POST /api/v1/sessions
GET  /api/v1/sessions/{session_id}
```

### 4.1 创建会话

`POST /api/v1/sessions` 调用现有 `SessionRepository.create()`，返回：

```json
{
  "id": "...",
  "title": "新对话",
  "created_at": "...",
  "updated_at": "...",
  "message_count": 0,
  "recoverable": false
}
```

新增 `SessionRecord.title`，默认值为“新对话”。第一次真正提交问题后，
`ChatRuntime` 会把规范化后的问题前 48 个字符作为标题。这样前端会话列表不必展示
一串无意义的 UUID，也不需要额外调用模型生成标题。

这里暂时不使用模型生成标题，原因是：

1. 会增加一次额外模型调用和费用。
2. 会让第一条消息完成时间更长。
3. 当前项目首先需要稳定可用，自动摘要标题可以以后作为独立能力增加。

### 4.2 查询会话详情

`GET /api/v1/sessions/{session_id}` 返回会话元数据和公开历史消息。

历史消息不是从 Session JSON 中读取。Session JSON 只保存索引性质的元数据；真正的
短期对话状态仍从 LangGraph Checkpointer 读取：

```python
snapshot = runtime.app.get_state(runtime.graph_config)
messages = snapshot.values.get("messages", [])
```

随后只映射 `HumanMessage` 和最终 `AIMessage`。`ToolMessage`、内部模型工具请求、
Graph 临时字段不会进入公开 API。

这与项目已有设计保持一致：

- SessionRepository 管理会话目录信息。
- Checkpointer 管理可恢复的 Agent 短期状态。
- 两者不重复保存完整消息。

## 五、turn 和 session 的区别

一个 session 是长期存在的一段会话，一个 turn 是 session 中的一轮执行。

```text
session
  turn 1: 用户问题 -> 助手回答
  turn 2: 用户问题 -> 工具审批 -> 工具执行 -> 助手回答 -> 记忆审批
  turn 3: 用户问题 -> 助手回答
```

每个 turn 都有独立的随机 `turn_id`。它用于：

1. 查询本轮当前状态。
2. 取消正在运行的一轮。
3. 对本轮暂停产生的请求提交决定。
4. 把浏览器中的进度与具体执行对应起来。

`turn_id` 不是 LangGraph 的 `thread_id`：

- `thread_id` 等于 session 的稳定标识，负责跨多轮保存上下文。
- `turn_id` 只标识一次 Web 操作，负责传输层控制。

混用这两个 ID 会导致前端控制接口和 Graph 记忆边界耦合，因此必须分开。

## 六、为什么使用 SSE

### 6.1 普通 JSON 响应的问题

模型可能需要几十秒才能完成，工具调用和审批还会更久。如果使用普通响应：

```text
POST question
       ...长时间没有任何响应...
200 {完整结果}
```

前端无法区分：

- 后端正在思考；
- 后端正在获取信息；
- 后端已经失败；
- 网络连接已经断开。

### 6.2 SSE 的特点

Server-Sent Events 是基于 HTTP 的单向事件流。后端按下面的文本格式持续发送事件：

```text
event: turn.progress
data: {"stage":"thinking","message":"正在理解你的问题"}

event: message.completed
data: {"message":{"role":"assistant","content":"..."}}

event: turn.completed
data: {"turn_id":"..."}

```

每个事件以一个空行结束。`data` 使用 JSON，便于前端进行类型判断。

与 WebSocket 相比，本项目当前更适合 SSE：

1. 对话执行主要是服务器向浏览器发送事件，方向天然单向。
2. 提问、取消和审批仍可使用普通 HTTP POST，语义清楚。
3. SSE 使用普通 HTTP，更容易经过代理和调试。
4. 当前不需要一个长期双向连接承载所有功能。

以后如果加入实时语音、双向音频或高频协同状态，再评估 WebSocket 会更合理。

FastAPI 的 `StreamingResponse` 用于返回这个事件流：

```python
return StreamingResponse(
    event_source,
    media_type="text/event-stream",
)
```

相关实现集中在 `human_chat/api/sse.py`，路由不会重复拼接协议文本。

### 6.3 为什么不用浏览器原生 EventSource 发起问题

浏览器原生 `EventSource` 只能方便地发起 GET 请求，而提交问题需要 POST JSON。
下一阶段前端会使用 `fetch()` 发起 POST，然后通过 `response.body` 的
`ReadableStream` 逐块解析 SSE。

这样既保留正确的 HTTP 语义，也能读取流式事件。

### 6.4 心跳

某些模型调用在较长时间内没有 Graph 节点更新。反向代理或浏览器可能把长时间没有
字节的数据连接判断为闲置连接。

`ConversationService.iter_events()` 每 15 秒发送一次 `heartbeat`：

```json
{"time": "2026-08-26T...+08:00"}
```

前端不需要展示它，只需要用它维持连接和判断服务仍然存活。

响应同时增加：

```text
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no
```

它们用于减少缓存或代理缓冲破坏实时事件流的风险。

## 七、同步 Graph 与异步 FastAPI 如何协作

### 7.1 为什么没有直接使用 graph.astream()

项目当前默认使用同步版 `SqliteSaver`。LangGraph 的同步 `SqliteSaver` 明确不实现
异步 `aget_tuple()`；异步调用应配套 `AsyncSqliteSaver`。

如果为了表面上“全异步”直接改为：

```python
async for event in graph.astream(...):
    ...
```

在内存 checkpointer 下可能能运行，但默认 SQLite 环境会失败。这种实现并不可靠。

本阶段采用兼容现有持久化结构的桥接方式：

```text
FastAPI event loop
        |
        | asyncio.to_thread(...)
        v
工作线程执行 graph.stream()
        |
        | loop.call_soon_threadsafe(queue.put_nowait, event)
        v
asyncio.Queue
        |
        v
StreamingResponse 异步读取并发送 SSE
```

### 7.2 asyncio.to_thread

FastAPI 运行在 asyncio event loop 上。同步的模型网络调用和 Graph 循环如果直接在
event loop 中运行，会阻塞同一进程里的健康检查、取消请求和其他会话。

`asyncio.to_thread()` 把同步工作放到线程中执行：

```python
outcome = await asyncio.to_thread(
    self._execute_phase,
    ...,
)
```

这不会把整个项目重写成异步，也不会破坏现有同步 Checkpointer。

### 7.3 asyncio.Queue

工作线程产生事件，FastAPI 的异步生成器消费事件。`asyncio.Queue` 是二者之间的
缓冲通道。

工作线程不能直接调用属于 event loop 的异步对象，所以使用：

```python
loop.call_soon_threadsafe(queue.put_nowait, event)
```

`call_soon_threadsafe` 会把“放入队列”这个操作安全地安排回主事件循环，而不是让
工作线程直接修改 event loop 内部状态。

## 八、公开事件与内部 Graph 更新隔离

Graph 的 `updates` 中包含节点名和内部字段，例如：

```text
tool_messages
tool_events
tool_review_request
memory_review_request
```

这些字段适合 Graph 和调试代码，不适合作为长期稳定的前端协议。直接转发会带来：

1. 前端与 Graph 节点实现强耦合。
2. 重构节点后前端立即损坏。
3. 工具参数和结果可能泄露。
4. 用户会看到没有价值的内部执行过程。

因此 `ConversationService` 使用白名单映射，只发送以下类型的公开事件：

```text
turn.started
turn.resumed
turn.progress
message.completed
review.required
memory.saved
turn.completed
turn.cancelled
turn.failed
heartbeat
```

普通只读工具调用不会显示工具名、参数和结果，只显示“正在获取回答所需的信息”。

只有当一个外部操作本身被工具策略标记为需要人工确认时，`review.required` 才会展示
脱敏后的操作详情。这不是调试轨迹，而是用户做出安全决定所必需的信息。凭据类参数
仍由现有 `redact_tool_arguments()` 脱敏。

## 九、LangGraph interrupt 的 Web 化

### 9.1 暂停仍由 LangGraph 完成

Graph 中已有：

```python
decision_data = interrupt({...})
```

LangGraph 会在 checkpointer 中保存暂停点。Web 层读取 `__interrupt__`，转换为
`review.required`，但不会自行执行工具或保存记忆。

### 9.2 恢复仍使用 Command(resume=...)

用户决定通过：

```text
POST /api/v1/turns/{turn_id}/decision
```

传入：

```json
{
  "decision": "approve",
  "selected_item_ids": []
}
```

应用服务根据服务端保存的 `PendingReview` 构造真正的 resume 值，然后调用：

```python
Command(resume=value)
```

因此恢复的是原来的 Graph checkpoint，而不是重新发送一次用户问题。

### 9.3 为什么不接受前端直接提交 accepted_texts

长期记忆审批中，前端只提交服务端分配的候选 ID：

```json
{
  "decision": "approve",
  "selected_item_ids": ["memory-0"]
}
```

服务端再从 `PendingReview.memory_items` 找回对应文本。这样前端不能伪造一段从未展示
过的任意文本，借审批接口直接写入长期记忆。

无效 ID、工具审批携带选择列表、拒绝时仍携带选择等矛盾输入都会被拒绝。

## 十、并发控制

LangGraph 的 `thread_id` 对应一个 session。若两个请求同时修改同一个 thread，
checkpoint 的先后关系就会不明确。

`ConversationService` 使用：

```python
self._active_sessions: dict[str, str]
```

记录每个 session 当前占用它的 turn。开始新 turn 时：

1. 在 `asyncio.Lock` 内检查 session 是否已被占用。
2. 若已占用，返回 HTTP 409 `session_busy`。
3. 若空闲，创建 turn 并占用 session。
4. turn 完成、失败或取消后释放。
5. 等待审批时继续占用，因为原 Graph 尚未完成。

这里只限制“同一会话内串行”，不同 session 可以并行。它既保护 checkpoint 顺序，
又不会不必要地阻止不同会话同时工作。

## 十一、取消机制

接口：

```text
POST /api/v1/turns/{turn_id}/cancel
```

使用 LangGraph 1.2 的 `RunControl.request_drain()` 请求协作停止。它不是强制终止线程：

1. 若模型 HTTP 请求正在执行，Python 无法安全地杀死该工作线程。
2. 当前节点结束后，LangGraph 在步骤边界停止继续调度。
3. 取消请求发出后，服务不再把该节点晚到的回答事件发送给浏览器。
4. 最终返回 `turn.cancelled` 并释放 session。

这比直接杀线程更安全，因为强制杀线程可能让 SQLite 写入、MCP 调用或文件更新停在
不可预测的位置。

同时新增 `HUMANCHAT_LLM_TIMEOUT_SECONDS`，默认 60 秒，并传给 `ChatOpenAI`。
它限制单次模型请求无限挂起，也使协作取消有明确的最坏等待边界。允许范围为
1 到 600 秒。

浏览器若在一个 phase 尚未结束时断开 SSE，`finally` 会调用 `disconnect()` 请求取消，
避免没有消费者的后台任务继续占用资源。

## 十二、FastAPI 依赖注入语法

`dependencies.py` 新增：

```python
ConversationServiceDependency = Annotated[
    ConversationService,
    Depends(get_conversation_service),
]
```

这里涉及两个概念。

### 12.1 Depends

`Depends` 告诉 FastAPI：路由执行前，先调用依赖函数取得对象。

服务对象是在 lifespan 中创建并放到：

```python
application.state.conversation_service
```

每个路由拿到的是同一个 application-scoped 服务，因此活跃 turn 和并发锁能够跨请求
工作。如果每个请求都创建一个新服务，同一 session 的并发保护将完全失效。

### 12.2 Annotated

`Annotated[T, metadata]` 表示这个参数在 Python 类型上仍是 `T`，但额外携带框架需要
的元数据。

路由可以写成：

```python
def list_sessions(service: ConversationServiceDependency):
    ...
```

编辑器知道 `service` 是 `ConversationService`，FastAPI 知道它来自 `Depends`。

## 十三、Pydantic 请求模型

本阶段新增：

```text
SessionSummary
SessionListResponse
SessionDetailResponse
StartTurnRequest
ReviewDecisionRequest
TurnStatusResponse
CancelTurnResponse
```

`StartTurnRequest.question` 限制为最多 20,000 个字符，并使用 `field_validator` 去除
首尾空白：

```python
@field_validator("question")
@classmethod
def normalize_question(cls, value: str) -> str:
    normalized = value.strip()
    if not normalized:
        raise ValueError(...)
    return normalized
```

单纯设置 `min_length=1` 不能拒绝由很多空格组成的字符串，所以还需要 validator。

公开响应全部由明确模型约束，没有直接返回 `SessionRecord.__dict__` 或 Graph state。
这可以防止后端未来新增内部字段时，它们自动泄露到 API。

## 十四、Web 模式关闭服务器扬声器 TTS

原 Graph 的 `synthesize_speech` 会：

1. 调用 GPT-SoVITS。
2. 把 WAV 写入服务器文件。
3. 使用 `simpleaudio` 在服务器扬声器播放。

CLI 和后端运行在同一台个人电脑时这是合理的，但浏览器可能位于另一台设备。Web
请求让服务器突然播放声音既不符合用户预期，也会阻塞 Graph 后续节点。

本阶段给 Graph 构建增加 `enable_tts`，给应用资源增加 `enable_server_audio`：

```python
with open_chat_application(
    settings,
    enable_server_audio=False,
):
    ...
```

FastAPI 使用 `False`，CLI 保持默认 `True`，因此没有破坏现有 CLI 行为。

将来 Web 语音应采用以下方式之一：

1. 后端提供音频生成/下载接口，由浏览器播放。
2. 浏览器使用 Web Speech API。
3. 使用专门的流式音频协议。

无论哪种，都不应复用“服务器本地扬声器播放”作为前端语音功能。

## 十五、CORS 与自定义响应头

启动 turn 后，后端在响应头返回：

```text
X-Turn-ID: ...
```

前端需要这个 ID 才能调用取消和审批接口。

跨域浏览器默认不能让 JavaScript 读取任意响应头。因此 CORS 的
`expose_headers` 从只有 `X-Request-ID` 扩展为：

```python
expose_headers=["X-Request-ID", "X-Turn-ID"]
```

如果只在后端返回头但忘记暴露，使用 curl 能看到，浏览器 JavaScript 却读不到，
这是前后端分离中常见且不容易立即发现的问题。

### graph_interrupts.py 的意义

原来的 `extract_interrupt_payloads()` 位于 `human_chat/cli/interrupts.py`。Web 应用也
需要解析相同的 LangGraph interrupt，但让应用服务依赖 CLI 会造成错误的依赖方向：

```text
application -> cli   # 不合理
```

因此把纯解析函数移动到与界面无关的 `graph_interrupts.py`：

```text
cli ---------> graph_interrupts
application -> graph_interrupts
```

CLI 的提示输入仍留在 CLI 模块，Web 的公开模型仍留在 API/Application 模块。

## 十七、错误语义

应用服务使用明确异常表达预期业务失败：

```text
SessionNotFoundError
SessionBusyError
TurnNotFoundError
TurnStateError
ReviewDecisionError
```

路由把它们转换为稳定 HTTP 错误：

```text
404 session_not_found
404 turn_not_found
409 session_busy
409 invalid_turn_decision
409 turn_not_cancellable
```

真正未知的异常仍由阶段一的统一异常处理器记录完整日志，并只向客户端返回通用
`internal_error`，避免泄露内部路径、密钥或堆栈。

已经开始流式传输后，HTTP 状态码不能再改成 500，所以运行期失败使用
`turn.failed` SSE 事件。事件只包含用户可理解的通用信息，详细堆栈写入服务器日志。

## 十八、生命周期与资源清理

FastAPI lifespan 现在按以下顺序工作：

```text
打开 ChatApplication 共享资源
    -> 创建 ConversationService
        -> 接受 HTTP 请求
        -> shutdown() 请求活跃 Graph 协作停止并等待回收
    -> 关闭 Checkpointer / Memory / MCP 等资源
```

必须先等待活跃 turn，再关闭 SQLite 或 MCP 资源。反过来关闭会导致仍在工作线程中的
Graph 访问已经销毁的连接。

`ConversationService` 只保留有限数量的最近 turn 元数据，默认 100 个。完成的旧 turn
会被淘汰，避免 Web 进程无限增长；运行中或等待审批的 turn 不会被错误删除。

当前 turn 注册表是进程内结构。这符合当前单进程本地应用的部署目标。如果将来使用
多个 Uvicorn worker 或多台服务器，需要把 turn 控制、事件通道和 session 锁提升到
Redis 等共享基础设施，或者采用 LangGraph Platform 提供的运行管理能力。

## 二十一、这一阶段完成后拥有什么

阶段二完成后，HumanChat 后端已经具备一个独立聊天前端所需的核心协议：

1. 可创建、列出和恢复会话。
2. 可读取经过过滤的历史消息。
3. 可通过 SSE 接收长任务进度和最终回复。
4. 可在 LangGraph interrupt 处向用户发起安全确认。
5. 可通过原 checkpoint 继续工具或长期记忆流程。
6. 可防止同一 session 的并发写入。
7. 可取消活跃 turn，并在断连和停机时清理任务。
8. 不向普通用户暴露内部工具执行轨迹。
9. Web 服务不会在后端机器错误播放 TTS。

这仍不是整个项目的终点。下一阶段将基于这些稳定接口创建 React + TypeScript
前端，把会话列表、消息区、输入区、进度、停止按钮和审批界面组合成真正可用的聊天
体验。
