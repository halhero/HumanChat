# 第十一步：按任务用途选择上下文

## 本步实际改变

新增 `memory/context.py`：`MemoryContextBuilder.build` 接收当前问题和近期对话，消费第九步候选，返回 `MemoryContext`，其中每个 `ContextBundle` 是不可随意拆开的上下文组合。本步还不构造最终模型请求。

过去“召回后再按主题相似度排序”会误伤没有主题相似度、却影响任务完成方式的长期指导。现在模型要分别回答：它是什么用途、是否适用、为什么适用，而不是只打一个相关性分数。

## 怎么设计，为什么

`Applicability` 的用途包括 constraint（约束）、guidance（处理/表达指导）、background（项目背景）、evidence（问题事实）、history（过去事实）。决策为 needed、optional、exclude、uncertain。这些是本次任务中的用途，不是给长期记忆重新加固定 category。

例如当前问题是 Python 代码审查：“代码审查先给风险结论”可作为 needed guidance，即便关键词和向量不相似；“家用机Windows”应排除。反过来，日常聊天不应自动套用代码审查偏好。因此并非“所有偏好都优先”，而是“适用的关键约束和指导不受主题排名误伤”。

当前明确用户要求优先于旧偏好。历史版本必须以 history 用途进入，不能扮演当前约束。程序不允许模型改写正文或引用未知ID，重复ID也不会被接受。

## 数据流

```text
当前问题 + 近期对话 + 带召回原因/状态的候选
   -> 结构化用途判断
   -> 当前性和ID边界检查
   -> 依赖分组 ContextBundle
   -> critical/required 标识 -> 第十二步预算装配
```

同 bundle 的记录后续整体保留或移除，避免只留下结论、丢掉限定条件。needed 的 constraint/guidance 标为 critical；其余 needed 标为 required；optional 再后考虑。这些标志来自当前任务判断，不是固定类别排名。

## 边界与失败处理

目录或判断请求超预算时返回明确诊断 `context_catalog_budget_exceeded`；外部模型失败记录日志和 `context_assessment_unavailable`。不会把失败称为“没有可用记忆”。诊断是内部信息，不向用户显示后台记忆保存通知。

模型适用性判断仍有误判概率。本步没有声称程序能够完全验证语义适用；程序能强制的是ID、状态、分组和后续预算策略。大规模目录超预算的分片选择不在本轮引入，当前以明确降级体现限制。
