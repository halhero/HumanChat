# 第十一步：按任务用途选择上下文

## 本步实际改变

新增 `memory/context.py`：`MemoryContextBuilder.build` 接收当前问题和近期对话，消费第九步候选，返回 `MemoryContext`，其中每个 `ContextBundle` 是不可随意拆开的上下文组合。本步还不构造最终模型请求。

过去“召回后再按主题相似度排序”会误伤没有主题相似度、却影响任务完成方式的长期指导。现在模型要分别回答：它是什么用途、是否适用、为什么适用，而不是只打一个相关性分数。

## 怎么设计，为什么

**本步只解决“这条记忆对眼前任务有什么用”，不再回答“它和问题有多像”。** 两个问题可能得到不同答案：解释协程时，“学习新概念先看例子”主题不相似，却能直接改变解释方式。

`Applicability` 的用途包括 constraint（约束）、guidance（处理/表达指导）、background（项目背景）、evidence（问题事实）、history（过去事实）。决策为 needed、optional、exclude、uncertain。这些是本次任务中的用途，不是给长期记忆重新加固定 category。

例如当前问题是 Python 代码审查：“代码审查先给风险结论”可作为 needed guidance，即便关键词和向量不相似；“家用机Windows”应排除。反过来，日常聊天不应自动套用代码审查偏好。因此并非“所有偏好都优先”，而是“适用的关键约束和指导不受主题排名误伤”。

当前明确用户要求优先于旧偏好。历史版本必须以 history 用途进入，不能扮演当前约束。程序不允许模型改写正文或引用未知ID，重复ID也不会被接受。

## 数据流

```text
当前问题 + 近期对话 + 带召回原因/状态的候选
   -> 结构化用途判断
   -> 当前性和ID边界检查
   -> 依赖分组 ContextBundle
   -> critical/required 标识 -> 第十二步预算装配
```

同 bundle 的记录后续整体保留或移除，避免只留下结论、丢掉限定条件。needed 的 constraint/guidance 标为 critical；其余 needed 标为 required；optional 再后考虑。这些标志来自当前任务判断，不是固定类别排名。

### 用完整任务而不是一个关键词做判断

设当前问题“解释 Python 协程”，近期对话表明用户刚开始学习异步。资料72把下列记录送入候选，模型应按任务给出这样的区别（是教学示例，不是逐字实测结果）：

| 记录 | 本次用途 | 判断与理由 |
| --- | --- | --- |
| 学习新概念通常先看例子 | guidance | needed，解释新概念符合范围 |
| HumanChat 的目标暂停 | background | exclude，纯概念解释暂不需要项目进度 |
| 家用机使用 Windows | background | exclude，当前不涉及安装或平台差异 |
| 旧版计划曾进行中 | history | exclude，用户没问过去 |

如果问题改为“继续推进 HumanChat”，暂停状态可能变成关键约束；如果改为“今天只给结论”，先例子指导可能与当前要求冲突而排除。用途是**本次调用的判断结果**，不写回数据库形成新的 category。

### build 的输入与输出分别是什么

`build(question, recent_context)` 内部召回候选，然后向模型发送：当前问题、有限近期对话、带来源状态和召回原因的候选。模型返回的 `Applicability` 只含：

```python
class Applicability(BaseModel):
    id: str
    purpose: Literal["constraint", "guidance", "background", "evidence", "history"]
    decision: Literal["needed", "optional", "exclude", "uncertain"]
    reason: str
    bundle: str = ""
```

它没有返回改写后的正文，也没有写入权限。id 对应真实 MemoryView，reason 解释本次判断，bundle 表示哪些已选条目应一起保留。程序用 id 从原候选取正文，避免选择器一边选择一边凭空改造事实。

### 独立召回之后，为什么不会再按相似度筛一遍

在 [context.py](../human_chat/memory/context.py) 中，循环处理的是模型用途判断，根本没有按 `candidate.score` 再取 top-k。核心检查为：

```python
if decision.decision in ("exclude", "uncertain"):
    continue
if candidate.view.status != "current" and decision.purpose != "history":
    context.diagnostics.append("historical_not_current")
    continue
key = decision.bundle or decision.id
grouped.setdefault(key, []).append((candidate, decision))
```

之前还检查 id 存在且只出现一次。这样 B 不会因为 RRF 分数为0而被机械淘汰；历史记录也不能被模型标成“当前约束”后混入。

但是模型仍可能把 B 错判为 exclude 或遗漏 B。代码会为缺失决定记录 context_decision_missing，却没有自动再调用另一个模型挽救。**本次设计消除了统一主题排名造成的结构性漏选，并没有证明语义选择零漏选。** 不应把这两项承诺混在一起。

### bundle 到底保护什么

假设同一任务需要“目标是完成记忆模块”和“当前阶段暂停”两条共同理解。只保留前者可能让模型继续安排开发，而忽视暂停限制。模型可将二者归入同一 bundle，预算层就整体保留或舍弃。

程序计算优先标志的实际条件是：

```python
any(d.decision == "needed" and d.purpose in ("constraint", "guidance") for _, d in entries)
```

它产生 critical；只要有任意 needed 则 required。`any` 表示组内至少一个条目符合条件。没有显式 bundle 时使用条目自己的 ID，成为单条组，避免不相关内容被强行捆绑。

这里只是保留模型**已经选入同组**的内容。若模型一开始遗漏限定条件，分组不会自动找回来；若记录自己的 scope 已保存在 Assertion 中，该条目的 payload 会包含它，不需要人为拆成两条。分组是额外关系保护，不是语义依赖发现的完备算法。

## 边界与失败处理

目录或判断请求超预算时返回明确诊断 `context_catalog_budget_exceeded`；外部模型失败记录日志和 `context_assessment_unavailable`。不会把失败称为“没有可用记忆”。诊断是内部信息，不向用户显示后台记忆保存通知。

模型适用性判断仍有误判概率。本步没有声称程序能够完全验证语义适用；程序能强制的是ID、状态、分组和后续预算策略。大规模目录超预算的分片选择不在本轮引入，当前以明确降级体现限制。

实际降级返回的是空 bundles 加诊断，回答仍可使用当前输入和近期历史。因此 context_assessment_unavailable 不能在排查时解释成“库里没有记忆”。选择调用也发生在回答前，会增加首个回答的等待时间；保存转后台并没有把所有记忆相关调用都移出前台。
