# 记忆模块重构第五步：纠错与撤销

日期：2026-10-15。前置资料67；前置提交 `dc477c7`。

## 改了什么

Service.apply 支持 correct 和 retract。普通 update 留下 historical，纠错留下 revoked；撤销使当前记录退出有效供给，并撤销该认识的历史版本。显式说明“从来就记错”的纠正可撤销全部历史。

普通更新不能改对象或范围；明确范围纠错允许在 correct 中修改 scope，并保留错误旧版。主体或关系变化仍不能当成一次普通覆盖，必要时撤销误记后建立正确认识。

## 为什么这样改

“以前 Windows，现在 Linux”有真实过去；“之前 Windows 是误记”没有同样的含义。若都只覆盖 text，未来历史问答无法区分。revoked 允许以后回顾“为什么误记”，但不能作为当时真实状态的证据。

原文本记录没有结构，不能随意把“暂停”当成完整新目标。旧文本只允许有明确新依据的完整纠正，不自动做无法证明的局部字段修改。

## 案例与数据流

```text
correct：当前认识 -> 保存 revoked 旧版 -> 合入明确纠正字段 -> 新版本
update ：当前认识 -> 保存 historical 旧版 -> 合入变化字段 -> 新版本
retract：当前认识 -> 撤销当前及历史 -> 不再进入 load()
```

原目标期限为年底，用户明确纠正为明年且范围只限代码审查。仅修改 deadline/scope，目标内容保留，旧版标错。旧来源重放为新增时，匹配到被撤销的旧认识及来源水位则拒绝。

本步仅运行纠错相关的JSON/真实 Store 两个用例，均通过，覆盖范围纠正、旧错误来源重放以及撤销后的有效供给。没有再次运行第4步所有用例。

指纹用于识别规范化文本及结构化核心，不是通用语义等价证明；不能保证拦截所有改写。用户后来明确重新表达同一事实与旧来源重放不同，仍需重新验证。删除正文、派生索引清理和持续禁记由下一步及后续接入完成。

阅读顺序：Mutation.revoke_history → apply 的身份检查 → 历史状态分支 → load 的有效性过滤。重点理解“历史存在”不等于“历史真实”。
