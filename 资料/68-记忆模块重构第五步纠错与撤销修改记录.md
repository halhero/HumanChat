# 记忆模块重构第五步：纠错与撤销

日期：2026-10-15。前置资料67；前置提交 `dc477c7`。

## 改了什么

Service.apply 支持 correct 和 retract。普通 update 留下 historical，纠错留下 revoked；撤销使当前记录退出有效供给，并撤销该认识的历史版本。显式说明“从来就记错”的纠正可撤销全部历史。

普通更新不能改对象或范围；明确范围纠错允许在 correct 中修改 scope，并保留错误旧版。主体或关系变化仍不能当成一次普通覆盖，必要时撤销误记后建立正确认识。

## 为什么这样改

**本步的重点是：被替换的旧内容，是否还能被当成真实过去使用？** 单纯保留“历史版本”还不够，错误也会被保存进历史，后续历史问答可能把错误再次讲给用户。

“以前 Windows，现在 Linux”有真实过去；“之前 Windows 是误记”没有同样的含义。若都只覆盖 text，未来历史问答无法区分。revoked 允许以后回顾“为什么误记”，但不能作为当时真实状态的证据。

原文本记录没有结构，不能随意把“暂停”当成完整新目标。旧文本只允许有明确新依据的完整纠正，不自动做无法证明的局部字段修改。

### 用同一条 Windows 记忆比较三个动作

| 用户说法 | 可能的操作 | 当前记录 | 旧内容的意义 |
| --- | --- | --- | --- |
| “我以前用 Windows，现在换 Linux 了” | update | Linux 有效 | Windows 曾经有效，historical |
| “你记错了，我一直用 Linux” | correct，必要时 revoke_history | Linux 有效 | Windows 是错误，revoked |
| “之前关于系统的说法不成立，先别用它” | retract | 不再供给当前认识 | 这条认识及历史撤回，revoked |

这是意图区别，不是按关键字自动匹配的实现。第5步只实现操作执行规则；资料73才介绍模型如何结合完整原话作决定。来源不充分时不能因为表格里有一种操作就强行选一种。

“项目暂停”属于认识内容改变，通常是 update；“撤回这条认识”才是 retract。项目暂停并不意味着系统应忘掉项目存在。

## 案例与数据流

```text
correct：当前认识 -> 保存 revoked 旧版 -> 合入明确纠正字段 -> 新版本
update ：当前认识 -> 保存 historical 旧版 -> 合入变化字段 -> 新版本
retract：当前认识 -> 撤销当前及历史 -> 不再进入 load()
```

原目标期限为年底，用户明确纠正为明年且范围只限代码审查。仅修改 deadline/scope，目标内容保留，旧版标错。旧来源重放为新增时，匹配到被撤销的旧认识及来源水位则拒绝。

### 代码在哪决定旧版本是否可信

在 [Service.apply](../human_chat/memory/service.py) 的非 duplicate 分支，构造历史快照时包含这一行：

```python
status="historical" if mutation.kind == "update" else "revoked"
```

条件表达式的含义是：正常变化保留真实过去，纠错或撤销保存被否定的旧认识。此前流程已经限制了能够进入此分支的操作种类，不能把这行单独搬到任意输入上解释。

随后决定是否把更早的历史一起撤销：

```python
if mutation.kind == "retract" or (mutation.kind == "correct" and mutation.revoke_history):
    for version in item.history:
        version.status = "revoked"
if mutation.kind == "retract":
    item.status = "retracted"
```

例如第1版 Windows、第2版 Linux，如果用户只纠正第2版的范围，不应无条件否定所有第1版事实；只有明确需要撤销整段认识时才使用 `revoke_history`。这也是为什么纠错有一个范围开关，而不是“correct 一律清空过去”。

### 让 scope 可纠正，但不允许任意换主体

原记录“用户使用 Windows”，实际原话是“家里的电脑用 Windows”。误记发生在范围，correct 可以在 `fields` 中明确包含 scope。普通 update 改 scope 会被拒绝，因为那很可能把家用机记录变成公司机记录。

主体/关系不允许通过同一条更新换掉。把“朋友用 Linux”记成“我用 Linux”，不能仅把 subject 改一改就声称完成了普通更新；应先撤回误记，再依据正确来源形成另一条认识。本轮没有跨多条操作的原子纠错事务，不能承诺两者必然同时完成。

### 纠错之后，读取与旧任务怎样受影响

```text
旧原话 -> 错误 Windows 认识 -> 用户纠正 -> 当前 Linux + revoked 的 Windows
                                              |
旧原话再次形成 Windows ------------------------+-> 识别旧来源后拒绝新增
```

`load()` 会排除 retracted 记录；后续 `memory_views` 会区分 revoked 与 historical，回答召回排除 revoked。**第5步只建立状态和重放规则，索引及读取链的实际消费由资料71、72完成。** 保存了 revoked 标记还不等于所有读取位置已经接线。

撤销仍保留正文和依据，方便解释维护过程，所以它不适合代替隐私删除。真正清除本模块正文是下一篇的 delete。理解这一点，才不会把“回答时看不到了”误认成“数据已经删掉”。
