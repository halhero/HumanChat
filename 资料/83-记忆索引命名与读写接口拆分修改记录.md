# 记忆索引命名与读写接口拆分修改记录

日期：2026-11-11。

## 1. 本步修改范围

本步只整理记忆索引层的命名和接口职责，没有修改：

- SQLite 或 PostgreSQL 表结构；
- 词法检索 SQL；
- sqlite-vec 或 pgvector 的语义检索；
- identity 检索；
- RRF 排名；
- 召回数量；
- `current_documents()`；
- `task_background_catalog`；
- 主数据库中的记忆结构和 mutation 语义。

索引条目 ID 继续使用：

```text
{parent_id}@{version}
```

## 2. 为什么需要统一名称

旧文件和类型使用了较宽泛的 `search`、`SearchDocument` 和 `MemorySearch`：

```text
human_chat/memory/search.py
SearchDocument
MemorySearch
SqliteMemorySearch
PostgresMemorySearch
```

这些名字容易造成两种误解：

1. `SearchDocument` 像通用搜索文档，但它实际上是长期记忆的轻量索引条目。
2. `MemorySearch` 同时包含写入和读取方法，使依赖方看起来都能使用整个索引接口。

本项目的真实结构是：主数据库保存完整记忆，索引 store 保存可检索投影。因此本步把名称调整为与职责一致的形式。

## 3. 重命名前后映射

| 修改前 | 修改后 | 含义 |
| --- | --- | --- |
| `search.py` | `index_store.py` | 保存并查询记忆索引投影 |
| `SearchDocument` | `MemoryIndexEntry` | 一条可检索的当前或历史版本投影 |
| `MemorySearch` | `MemoryIndexWriter` + `MemoryIndexReader` | 将写入与读取能力分别声明 |
| `SqliteMemorySearch` | `SqliteMemoryIndexStore` | SQLite FTS5 与 sqlite-vec 实现 |
| `PostgresMemorySearch` | `PostgresMemoryIndexStore` | PostgreSQL FTS 与 pgvector 实现 |
| `documents_for_item()` | `_index_entries_for_item()` | 索引 store 内部的投影转换函数 |
| `RecalledMemory.view` | `RecalledMemory.entry` | 明确召回对象持有索引条目 |

旧文件、旧类名和兼容别名均未保留，避免项目同时存在两套术语。

## 4. Reader 与 Writer 的职责

### 4.1 MemoryIndexWriter

Writer 只声明：

```python
def upsert_item(self, item: MemoryItem) -> None:
    ...
```

`LongTermMemoryService` 在主记录写入成功后调用它，增量更新该 `parent_id` 的索引条目。Service 不需要知道词法查询、语义查询或 catalog 读取方法。

### 4.2 MemoryIndexReader

Reader 声明召回所需能力：

- `semantic_enabled`
- `search_lexical()`
- `search_semantic()`
- `search_identity()`
- `current_documents()`
- `has_documents()`

`MemoryRetriever` 只依赖 Reader。它不应调用写入方法，也不负责把主记录转换为索引条目。

### 4.3 为什么具体实现同时满足两个接口

SQLite 和 PostgreSQL 各自仍只有一个 index store 实例。该实例既能接收增量写入，也能执行检索，但不同业务对象只声明自己需要的能力：

```text
LongTermMemoryService ──依赖──> MemoryIndexWriter

MemoryRetriever       ──依赖──> MemoryIndexReader
```

接口拆分用于表达调用方向，不会创建第二份索引，也没有复制业务数据。

## 5. Repository 与 Index Store 的区别

`MemoryRepository` 是权威数据访问层：

- 保存完整 `MemoryItem`；
- 包含 evidence、history、operation 信息等业务数据；
- 按 ID 定向读取供 mutation 和请求装配使用。

`MemoryIndexStore` 是检索投影：

- 保存用于搜索的正文、状态、版本、identity 和向量；
- 负责快速返回候选索引条目；
- 不替代主数据库，也不是第二个完整记忆真相来源。

命名为 store 是因为具体对象不仅执行查询，还持有并增量维护索引投影；命名为 index 是为了避免把它误认为通用业务搜索服务。

## 6. 内部投影函数为何改为私有

`_index_entries_for_item()` 只服务于 SQLite 和 PostgreSQL 索引写入。第一步完成后，请求装配已经直接读取 `MemoryItem` 或 `MemoryVersion`，索引层之外不再需要调用该函数。

使用下划线明确它不是跨模块业务接口，避免以后其他模块再次依赖索引内部表示。

## 7. 调用方同步调整

以下真实调用点已统一更新：

- `retrieval.py`：依赖 `MemoryIndexReader`，召回对象字段改为 `entry`；
- `service.py`：只依赖 `MemoryIndexWriter`；
- `context.py`：通过 `candidate.entry` 判断 ID 和状态；
- `formation.py`：通过 `recalled.entry.parent_id` 收集目标；
- `request.py`：生成 reference 时读取 `candidate.entry`；
- `resources.py`：创建重命名后的 SQLite/PostgreSQL store；
- 相关测试：导入路径、类名和字段名同步更新。

## 8. 未改变的业务行为

本步是结构重命名和依赖收窄。以下行为保持原样：

1. 当前版本和历史版本的索引条目生成规则不变。
2. deleted 记录不保留索引条目。
3. active、retracted、expired 的索引状态映射不变。
4. SQLite FTS5 查询和 BM25 排名不变。
5. sqlite-vec 查询向量和距离计算不变。
6. PostgreSQL FTS 和 pgvector 查询不变。
7. RRF 融合窗口与最终召回数量不变。
8. identity 精确召回不变。
9. `current_documents()` 的行为和全量读取现状不变。
10. Service 写入主记录后仍增量更新同一个索引 store。

## 9. 定向验证

本步验证聚焦于受重命名和接口拆分影响的路径：
