# 原始记忆定向读取与增量检索重构记录

日期：2026-10-28。

## 1. 本次重构要解决的核心问题

修改前，HumanChat 虽然已经区分 `MemoryService`、`MemoryRepository` 和语义索引，但回答、维护、请求装配和后台同步仍反复执行同一件事：先把全部长期记忆读取到应用内存，再在 Python 中筛选。

主要全量路径包括：

1. `MemoryRetriever.recall()` 调用 `service.inventory()`，再为全部正文临时构造 BM25 语料。
2. `MemoryFormation.prepare()` 读取完整 inventory，为每个候选匹配旧记录。
3. `assemble_request()` 再次读取完整 inventory，只为重新找到已经选中的少量引用。
4. `MemoryService.apply()` 读取全部记录，扫描 receipt、source、fingerprint 和禁记身份。
5. `MemoryIndex.sync()` 读取全部原始记录并重写完整索引文件。
6. `MemoryWorker` 即使没有新记忆，也会周期性调用 `sync()`。
7. JSON 后端的 `get_item()` 看似按 ID 获取，实际仍解析完整 JSON 文件；更新一条记录也会重写整个文件。

当原始数据库达到数 GB 甚至更大时，这种设计无法通过增加内存解决。真正的问题不是 Python 循环写得慢，而是在线调用链没有区分：

- 原始数据库负责保存完整、权威的业务记录。
- 检索投影负责快速找到少量候选 ID。
- 应用只应根据候选 ID 回原始库读取必要记录。

本次重构目标是把这三个职责真正落到代码中，而不是在旧全量流程外再包一层新接口。

## 2. 重构后的总体结构

新的回答召回流程：

```text
用户问题
  ├─ 全文索引进行词法检索
  ├─ Embedding 模型生成查询向量
  └─ 向量索引进行语义检索
             ↓
      RRF 合并两份排名
             ↓
  轻量目录补充非主题型协作约束
             ↓
      LLM 判断任务适用性
             ↓
   收集被选中的 parent_id
             ↓
MemoryService.get_items(parent_ids)
             ↓
从原始库读取少量完整 MemoryItem
```

新的记忆形成与保存流程：

```text
每个候选独立检索轻量投影
             ↓
汇总命中的 parent_id
             ↓
一次 get_items() 定向读取旧记录
             ↓
Review 形成 add/update/delete 等决策
             ↓
apply() 只读取 target_id 对应记录
             ↓
写入一条原始记录
             ↓
只更新该 parent_id 的检索文档和向量
```

两条流程都不需要在线读取全部原始记忆。

## 3. 原始数据库为什么改成逐条存储

### 3.1 删除整文件 JSON 运行后端

旧 `JsonMemoryRepository` 把所有记录放在一个 JSON 对象中：

```text
读取一条 -> 读取完整文件 -> 解析全部 items -> Python 查找
更新一条 -> 读取完整文件 -> 修改列表 -> 重写完整文件
```

因此它无法满足“按 ID 读取”，即使方法名叫 `get_item()` 也没有改变实际 I/O。

本次将本地正式后端改为 `SqliteMemoryRepository`。表中一行对应一个完整 `MemoryItem`：

```sql
PRIMARY KEY (namespace, item_id)
```

读取使用主键条件，批量读取使用有限 ID 集合：

```sql
WHERE namespace = ? AND item_id IN (?, ?, ...)
```

写入使用 SQLite 的 `ON CONFLICT ... DO UPDATE`。这表示插入和更新共用一个原子 SQL 操作，不需要先加载其他记录。

### 3.2 Repository 的新契约

运行时 Repository 只保留：

```python
get_item(namespace, item_id)
get_items(namespace, item_ids)
upsert_item(namespace, item)
delete_item(namespace, item_id)
```

`list_items()` 已从 Protocol、SQLite 实现和 LangGraph Store 适配器中删除。没有保留一个内部仍然全量扫描的兼容方法。

`LongTermMemory` 整份文档容器和旧 categories 迁移逻辑也已删除。根据此前确认，旧 JSON 是优化前残留数据，本次不会自动导入，也不会删除原文件。

## 4. 检索投影保存什么

新增 `human_chat/memory/search.py`，检索文档只保存召回和上下文初筛需要的字段：

```text
view_id
parent_id
parent_version
view_version
text
status
identity_key
assertion
observed_at / ended_at
embedding
```

它不保存完整 Evidence、后台任务、回执集合或其他大字段。

这里的 `view_id` 同时表示当前版本和历史版本，例如：

```text
<parent_id>@<version>
```

搜索命中历史版本时，系统仍能通过 `parent_id` 定向读取完整父记录，再验证父版本和具体历史版本是否仍然有效。

## 5. 词法召回与语义召回如何执行

### 5.1 本地 SQLite 模式

本地检索文件为：

```text
user_profile.search.sqlite
```

词法召回使用 SQLite FTS5。中文正文会先拆分为汉字和相邻双字 token，避免把一整段中文当成单个不可匹配词。FTS5 的 `bm25()` 负责排名，应用只接收排名靠前的检索文档。

语义召回使用 `sqlite-vec`：

1. 保存记忆时对新增或正文变化的 view 调用 `embed_documents()`。
2. 向量按检索文档 row ID 写入 `vec0` 虚表。
3. 提问时调用 `embed_query()` 生成查询向量。
4. `sqlite-vec` 在数据库中执行 KNN 距离计算。
5. 查询只返回候选检索文档，不读取完整 MemoryItem。

SQLite 模式适合本地开发和中小规模。`sqlite-vec` 当前使用精确 KNN，因此它解决的是“不要把完整原始记录读入应用”，并不假装具备大规模 HNSW 的性能。

### 5.2 PostgreSQL 模式

生产检索投影使用独立表：

- PostgreSQL 原生全文索引负责词法检索。
- `pgvector` 保存 embedding。
- HNSW 索引使用余弦距离运算符进行近似最近邻搜索。

查询形态为：

```sql
ORDER BY embedding <=> query_vector
LIMIT candidate_window
```

有 HNSW 索引时，数据库不需要对全部向量执行精确余弦计算。它先在图索引中寻找近似候选，应用再根据排名合并结果。

需要明确一个实现边界：本地 FTS5 使用 BM25；PostgreSQL 当前使用原生 `ts_rank_cd`，不是严格的 BM25 公式。这样可以避免为 PostgreSQL 再强制安装一个不普遍可用的搜索扩展。如果未来业务要求所有后端使用完全一致的 BM25，可把生产检索换成 Elasticsearch/OpenSearch 等专用检索服务，而不改变上层 `MemorySearch` 契约。

### 5.3 RRF 为什么保留

词法分数与向量距离不是同一量纲，不能直接相加。Retriever 使用 Reciprocal Rank Fusion：

```text
score += 1 / (60 + rank)
```

它关注候选在各自结果列表中的名次。一个候选在词法和语义两路都靠前时会自然得到更高总分，不需要人为猜测两个原始分数应该如何归一化。

每一路先取得比最终数量更宽的候选窗口，再合并裁剪。最终数量由 `HUMANCHAT_MEMORY_RECALL_LIMIT` 控制，默认 24；内部窗口为该值的四倍，不再把向量搜索简单固定为 12 条。

## 6. 为什么仍保留轻量目录通道

第一次集成检查发现，如果回答阶段只保留 BM25 和向量 Top-K，那么“始终解释修改原因”这类协作约束，在用户只说“你好”时既没有关键词重合，也没有足够语义相似度，可能完全没有机会进入适用性判断。

因此回答阶段仍将当前检索文档作为 `task_background_catalog` 候选，但数据源已经改变：

- 修改前：读取全部完整 `MemoryItem`，再生成 view。
- 修改后：只读取轻量检索投影中的 current document。
- 最终：只有被适用性模型选中的 parent ID 才回原始数据库读取完整记录。

这保留了非主题型约束的召回能力，同时完成了本次“不全量读取原始数据库”的目标。

需要诚实说明：检索目录本身仍可能随记忆数量增长，影响适用性模型的输入规模。它是后续需要单独优化的召回质量与预算问题，不能在本次重构中假装已经解决。

## 7. 增量索引如何维护

旧 `MemoryIndex.sync()` 会：

```text
读取全部原始记录
生成全部 views
补算缺失向量
重建完整 rows
重写整个索引文件
```

新 `upsert_item(item)` 只处理一个 parent：

1. 查询该 parent 已有的轻量 view。
2. 计算新旧 view 差异。
3. 删除已经失效的 view。
4. 对正文没有变化的 view 复用已有向量。
5. 只为新增或正文变化的 view 请求 embedding。
6. 更新对应全文索引和向量行。

删除记忆时，tombstone 不会产生检索文档，因此该 parent 的全文和向量记录会被删除。

后台 `MemoryWorker` 中的周期性 `index.sync(service)` 已删除。应用空闲时不再每五秒触发全量原始库读取。

## 8. Formation 和 Request 如何定向回源

### 8.1 MemoryFormation

每个候选仍独立召回，避免不同主题竞争同一批目标。变化在于：

```python
target_ids = 所有候选召回结果中的 parent_id 去重
records = service.get_items(target_ids)
```

Review payload 中每个候选只收到本候选命中的完整记录。模型只能选择该候选召回范围内的 target ID。

批次级 `inventory` 和全量 policies 已删除。

### 8.2 请求装配

`context_references()` 现在显式保存 `parent_id`。最终请求装配时先收集已经选中的 parent ID，然后一次 `get_items()`：

```text
selected references
  -> unique parent IDs
  -> bounded get_items()
  -> 从这些父记录重建所需 view
  -> 校验 parent_version / status / purpose
```

不再为少数已选引用重新读取全部原始记忆。

## 9. apply() 如何简化

旧 `apply()` 同时承担执行、去重、删除来源封锁、撤销指纹匹配、禁记身份策略和全库 receipt 查找。它需要先读取全部记录，代码复杂度也掩盖了真正的写入语义。

新 `apply()` 只做：

### add

1. 验证用户和新增 assertion。
2. 根据 operation ID 生成确定性 item ID。
3. 只查询这个 item ID。
4. 不存在则新增；已经由同一 operation 写入则返回 `already_applied`。

### update / correct / duplicate / retract / delete

1. 只查询 `target_id`。
2. 验证目标存在且处于可修改状态。
3. 验证 `expected_version`，防止旧计划覆盖新版本。
4. 按 Review 已决定的动作写入一个目标。
5. 增量更新该目标的检索投影。

保留 `last_operation_id` 是因为后台任务存在真实的故障窗口：原始写入已经成功，但进程可能在标记 job 完成前退出。重试时必须识别同一次操作，并补做可能中断的检索投影更新。

删除的防御机制包括：

- 每条记录不断增长的 `receipts` 字典。
- `seen_sources` 全库来源扫描。
- `suppressed` 和 fingerprint 历史匹配。
- `blocked_identity` 与持续禁记策略。
- 删除时扫描全部未完成 job 并解析每份 plan。
- 为旧 JSON 或旧 assertion 形态保留的兼容写入分支。

这些机制不是换成另一组辅助表，而是直接从当前运行数据流中移除。

仍保留的边界检查包括：用户归属、目标存在、版本匹配、更新 payload 完整性和数据库异常。这些检查分别对应跨用户写入、错误目标、并发覆盖和无效 LLM 输出，属于明确风险。

```env

```

新增依赖：

## 12. 验证范围与结果

本次验证只覆盖直接受影响的真实风险：

1. SQLite 原始库按指定 ID 读写，不依赖列表接口。
2. LangGraph Store 适配器只读取调用方提供的 ID。
3. 写入一条记忆只新增该 parent 的检索文档和 embedding。
4. FTS5 词法召回和 sqlite-vec 语义召回能够返回正确 parent ID。
5. 删除后对应检索文档和向量不再可召回。
6. 检索文件重新打开后向量仍可使用。
7. BM25 与语义结果通过 RRF 合并，identity 精确命中仍用于维护。
8. Formation 按候选独立召回并批量定向读取目标。
9. Request 只回源已选 parent，并能发现引用版本变化或删除。
10. 后台 plan 在原始写入后发生进程中断，重试不会重复写入。
11. 非主题型协作约束仍能通过轻量 catalog 进入上下文判断。
12. 应用资源、后台 worker、Graph 和 HTTP 集成仍能运行。

执行结果：

```text
记忆模块直接相关测试：29 passed
Graph 与 HTTP 受影响集成测试：7 passed
Ruff：All checks passed
compileall：通过
SQLite / sqlite-vec：真实执行通过
PostgreSQL 依赖导入：通过
```

第一次 pytest 没有进入业务代码，因为系统临时目录拒绝访问。之后指定项目内独立 `--basetemp`，同一测试集合正常执行。没有修改生产代码来掩盖环境权限问题。

## 13. 当前仍未解决的事项

1. 当前任务背景目录来自轻量检索投影，已经不读取原始数据库，但仍可能随记忆数量增长。后续需要单独设计目录分层或结构化范围索引，不能简单删除后牺牲非主题约束召回。
2. SQLite `sqlite-vec` 是本地精确 KNN，不适合冒充大规模生产 ANN。大量数据应使用 PostgreSQL `pgvector HNSW` 或独立检索服务。
3. 当前环境没有 PostgreSQL 服务，因此 pgvector 建表、HNSW 查询和真实 PostgresStore 写入尚未远端实测；本次只完成代码、依赖和导入检查。
4. 旧 JSON 不自动迁移。根据此前确认，它属于无用残留；如果未来需要恢复其中数据，应编写一次性、显式、分页导入工具，而不是把兼容读取重新塞回在线 Repository。
5. 原始记录先提交、检索投影后更新。后台任务重试可通过 `last_operation_id` 修复中断；如果未来出现多个写入进程，需要再引入数据库事务边界或 outbox，而不是现在为尚不存在的多进程场景堆叠实现。
6. PostgreSQL 词法排名目前是原生 FTS，不与 SQLite BM25 完全等价。只有建立跨后端检索评测并证明差异影响业务后，才值得引入专用搜索服务。

## 14. 本次重构的结论

本次完成的是存储与检索数据流的结构性替换：

- 原始数据库从“先全部读取再筛选”改为“按候选 ID 定向读取”。
- 语义匹配没有取消，而是由持久检索投影保存 embedding 并执行向量搜索。
- 词法与语义结果继续混合召回。
- 写入后只更新变化记录的检索投影。
- `apply()` 回到执行 Reviewed Decision 的职责，不再充当全库防御规则集合。
- 旧全量接口和后台同步已经删除，不会在新路径之外继续偷偷运行。

这解决了本轮明确要求的“去除所有在线全量读取原始记忆数据库”。它不代表记忆召回质量、目录规模和多进程一致性已经全部完成，这些需要在后续步骤中根据实际数据和评测继续完善。
