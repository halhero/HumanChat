# 记忆管理入口与旧审批残留清理记录

日期：2026-10-20。实施前版本：`83b8755`。分支：`codex/memory-approved`。

## 1. 本次纠正的是什么

此前已经将自动记忆形成移到后台，取消了“用户勾选候选后才能保存”的流程，但仍保留了侧栏的“长期记忆”窗口、手动增删 API，以及两处识别旧 `memory_review` 中断的兼容代码。

这实际实现的是“自动保存不打扰，用户仍可主动管理”，没有完全符合本项目“记忆作为内部能力，不向用户提供显式管理入口”的要求。本次清理的是这条旧人工管理链路，不是删除长期记忆能力，也不是删除已存数据。

**本次重点有三个：入口从前端一直清理到 Service；自动维护继续统一使用 Mutation；过时审批兼容退出当前运行代码。**

## 2. 前后调用关系

### 清理前：自动与手动两条写入路径并存

```text
聊天完成
  -> MemoryWorker -> FormationPlan -> Service.apply -> Repository

侧栏“长期记忆”
  -> MemoryDialog -> POST/DELETE /api/v1/memories
  -> Application.add_memory/delete_memory
  -> Service.add/delete_by_id -> Repository
```

两条路径最终访问同一主存储，但语义不同。手动 `add` 直接接收一段文本，建立人工来源后写入，不执行自动形成流程中的候选复核、结构化认识比较与 Mutation 版本检查。它最初服务于管理界面；界面退出后，没有必要只为测试方便保留这个生产写入入口。

### 清理后：面向用户只有对话，维护使用同一个执行边界

```text
用户正常对话
  -> Graph 回答并保存消息
  -> Application 登记后台任务
  -> MemoryFormation 根据原话提出受限 Mutation
  -> MemoryService.apply
       -> 新增 / 确认 / 更新 / 纠错 / 撤回 / 删除 / 持续禁记
       -> 主记录保存、索引通知、删除时清理相关待执行计划

危险工具操作
  -> 独立的工具审批
  -> 用户批准后才执行
```

“不要再使用之前那个错误说法”“不要再保留这个目标”等明确表达，仍可由自动形成模块识别为维护要求。没有另造命令面板或人工管理后门。这里仍依赖模型理解，歧义可能暂缓；本次没有承诺任意自然语言删除请求都立即成功。

## 4. 为什么连 Service 的方法也删

原手动调用链的核心是：

```python
# 已删除的 Application 方法
return self._memory.service.add(text, source="manual")
```

`add` 接受文本，不要求维护提案中的 expected_version、目标、结构化认识及字段范围。`delete_by_id` 则提供另一条以 ID 直接删除的业务入口。两者原本为手动管理服务；保留会让后续开发者仍有机会绕过自动维护边界。

现在自动新增与删除都经过既有 `apply`。例如下面是用于解释的提案结构，不是新开放给浏览器的请求：

```text
kind             delete
target_id        m1
expected_version 2
evidence         新用户消息的原文依据
id               本后台计划的稳定操作 ID
```

执行时仍检查归属、回执、目标版本和来源时间，再清空正文并保存删除标记。重试同一删除返回 already_applied；不会因删了手动方法就丢失防复活逻辑。

以下内部能力保留：

- `inventory()`：维护与检索需要完整记录，包括被撤销或删除的状态。
- `load()`：读取当前有效记录的内部服务视图，不再通过 Application/API 暴露为用户列表。
- `_tombstone()`：清除正文、引文和历史内容，保留最小抑制信息。
- `_persist()`：保存主记录，并通知索引及删除监听。
- `apply()`：全部自动维护操作的执行边界。
- Repository 与旧记录的读取契约：已有手动来源的记录仍可读取，不进行数据迁移、清空或重新解释。

“删除人工入口”不等于“删除所有包含 memory 字样的内部方法”。例如健康接口的 memory_backend 是运行诊断，不是人工增删入口；本次没有扩大到无关的运维协议改造。

## 5. memory_review 两处兼容代码怎样处理

原来两处逻辑分别位于：

1. `start_memory_worker`：启动扫描会话时，若遇到 memory_review，调用 discard_pending_turn，再登记来源。
2. `get_pending_review`：查询审批时，若遇到 memory_review，结束旧阶段并返回 None。

本次删除上述专用判断及对应清理调用。应用不再为旧记忆审批专门识别、批准或退役中断。Graph 本身早已没有记忆审批节点，本次没有再添加替代节点。

保留 `get_pending_review`，因为真实工具审批重启恢复仍需要它。保留 `discard_pending_turn`，因为用户取消待处理的工具回合时仍要清除 Graph continuation。它的说明也改为当前对话/工具职责，不再提旧记忆批准。

### 对旧会话的实际影响

本次没有读取真实会话数据来确认是否仍有旧审批中断，也没有修改任何检查点。如果确实存在停在已移除节点上的旧会话，它不再享有专用兼容恢复；现有协议不会把未知类型当成工具批准。需要恢复这类会话时，应单独分析与处理，不自动重置数据库或批量丢弃状态。

普通已完成聊天历史及当前工具审批仍按原机制使用。代码清理不等于已有记录被删除。

## 6. 测试为何也需要调整

删除生产入口后，测试不能为了构造数据而要求它继续存在。本次只修改已有测试文件，没有新建测试文件或额外测试框架。

### 测试数据走真实 Mutation 边界

在已有 `test_memory_maintenance.py` 中加入一个很小的 `remember` 帮助函数，复用已有 operation 构造器，向 Service.apply 提交合成 add，再取回对应记录。它只用于测试，避免多个文件重复组装相同数据。

Graph、索引、检索、请求装配、资源测试用它替代旧 service.add。删除场景直接提交 delete Mutation，并断言 applied；不能只发出删除请求后假定成功。

这保留了原风险断言：

- 删除后不再进入回答上下文；
- 删除时慢索引同步不能恢复旧内容；
- 删除会清掉相关待执行计划；
- 同一删除操作重试不重复生效；
- 旧来源不能恢复已删除认识；
- 纠错、撤回、禁记和局部字段更新仍成立。

### 旧兼容测试与 API 测试的变化

专门构造旧 memory_review 节点并要求自动退役的测试退出，因为该兼容行为明确停止支持，不是为了掩盖失败而删测试。

HTTP 测试改为验证旧管理路由不再对外开放、请求不写入任何记录。原有工具审批跨重启恢复、批准后只执行一次、过期 selected_item_ids 被422拒绝，以及不产生 memory.saved 事件的断言继续保留。

因此测试中仍出现 selected_item_ids 或 memory.saved 是拒绝旧协议的证据，不代表这些旧功能仍在运行。

## 8. 阅读顺序与后续边界

建议先看 [Application](../human_chat/application.py) 的变更，确认不再对外提供记忆增删，再看 [MemoryService](../human_chat/memory/service.py) 的 apply，最后看 [API 注册](../human_chat/api/app.py) 和 [侧栏](../web/src/components/Sidebar.tsx)。这次理解重点是调用入口退出，而不是重新学习整套记忆算法。

本次没有增加旧会话迁移框架，没有修改存储格式，也没有引入用户管理或新的审批。后台最终一致性、模型误判、模糊删除要求暂缓等限制仍在；取消人工窗口不会自动解决这些问题。需要更可靠的自然语言维护时，应围绕真实误判案例另做明确设计。

历史资料仍保留实施时的说明和验证证据，相关篇章顶部已指向本篇；不能把旧步骤中的“保留手工管理”当成当前产品行为。
