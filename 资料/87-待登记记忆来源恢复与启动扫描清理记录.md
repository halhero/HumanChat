# 待登记记忆来源恢复与启动扫描清理记录

日期：2026-11-11。

## 1. 原来的启动恢复问题

记忆 Job 与 LangGraph checkpoint 分属不同持久化资源。旧实现为了处理“回答 checkpoint 已提交，但进程在 Job 登记前崩溃”的间隙，会在每次应用启动时执行：

```python
for session in self._sessions.list_recent(limit=2**31 - 1):
    snapshot = self._graph.get_state(...)
    ...
```

随后把每个 snapshot 的完整消息历史转换成 `SourceMessage`，再依靠 Job ID 幂等跳过已经登记的来源。

Job 幂等只能防止重复写入，不能减少前面的全会话读取、checkpoint 加载和消息转换。启动成本因此随着全部历史会话持续增长。

## 2. 为什么不能只增加 session limit

把扫描数量改成最近 100 个会话会缩短启动时间，但不能正确解决恢复问题：

- 第 101 个会话可能恰好处于 checkpoint 已提交、Job 未登记状态；
- limit 会让该来源永久无法进入记忆维护；
- 排序或分页只能改变扫描方式，仍然需要反复检查大量已经完成的历史。

正确做法是持久记录“哪些来源尚未完成交接”，而不是从全部会话中重新推断。

## 3. 新增的 pending source 表

在现有 `MemoryJobs` sidecar 数据库中新增专用表：

```text
memory_pending_sources
- source_id
- user_id
- thread_id
- source_time
```

它只保存恢复 Job 登记所需的四个标识，不保存消息正文、完整 checkpoint、LLM 输出或 mutation。

这不是通用事件总线或可扩展 outbox 框架，只解决本项目已经存在的一个明确跨资源交接间隙。

## 4. 正常交接流程

每轮开始时，应用已经创建 `SourceMessage`，因此在执行 Graph 前登记：

```text
register_pending(source_id, thread_id, user_id, source_time)
```

回答完整结束后：

```text
确认 checkpoint 中最后一对消息为当前用户来源和助手回答
   ↓
promote_pending(source_id, checkpoint_id)
```

`promote_pending()` 在同一个 SQLite 事务中：

1. 读取 pending source；
2. 用现有确定性 Job ID 插入 `memory_jobs`；
3. 删除 pending source。

如果插入后发生重试，`INSERT OR IGNORE` 仍保证同一来源只有一个 Job。

## 5. 崩溃恢复流程

应用启动不再调用 session repository 的 `list_recent()`。新的流程是：

```text
读取 memory_pending_sources
   ↓
只按其中的 thread_id 读取对应 checkpoint
   ↓
来源已完整回答 -> 提升为正式 Job
来源不存在       -> 清理无效 pending
来源仍在工具审批 -> 保留 pending 等待恢复或取消
```

因此启动恢复成本由“未完成交接的轮次数量”决定，不再由全部历史会话和消息总量决定。

## 6. 中断与取消处理

### 6.1 工具审批

工具审批中断时尚未形成最终助手回答，因此 pending source 保留。用户批准或拒绝后继续同一个 Graph 来源，完成时再提升为 Job。

### 6.2 用户取消

`discard_pending_turn()` 在终止 Graph pending task 时同步删除该 source 的 pending 记录，取消内容不会进入长期记忆形成。

### 6.3 执行异常

如果 Graph 在当前进程内抛出异常，应用清除该 checkpoint 当前来源的 pending 记录并继续抛出原异常。失败轮次不会成为后台记忆任务。

### 6.4 进程硬崩溃

进程无法执行清理时，pending 记录保留下来。下次启动只检查这条记录对应的 thread：

- checkpoint 已完成则补登记；
- checkpoint 没有该来源则清理；
- checkpoint 仍处于审批 interrupt 则保留。

## 7. MemoryJobs 新增职责

新增方法均围绕 pending source：

- `register_pending()`：开始轮次前持久登记；
- `pending_sources()`：读取需要恢复的少量来源；
- `clear_pending()`：取消、失败或无效来源清理；
- `promote_pending()`：原子创建 Job 并删除 pending。

已有 `enqueue()`、Job 计划持久化、重试和幂等 mutation 行为没有修改。

## 8. 删除的无界路径

应用启动已删除：

```python
self._sessions.list_recent(limit=2**31 - 1)
```

同时删除启动恢复专用的 `_reconcile_memory_sources()`，因此启动不再：

- 加载全部 SessionRecord；
- 对每个 thread 读取 Graph snapshot；
- 转换每个 thread 的完整消息历史；
- 重复尝试为所有历史来源登记 Job。

## 9. 定向测试

本步验证覆盖：

- pending source 能跨 `MemoryJobs` 关闭和重开持久保存；
- pending 到正式 Job 的提升在一个事务中完成；
- 重复提升不会生成第二个 Job；
- 没有 pending 时应用启动不会调用 session repository `list_recent()`；
- 一条 pending 只读取它对应的一个 thread；
- 完成的 checkpoint 能恢复成正式 Job；
- 工具审批取消会清除 pending；
- 原有 Job 计划恢复、幂等 mutation 和后台记忆形成继续工作。

## 10. 未处理事项

pending source 数量原则上只包含正在执行、等待审批或异常中断的轮次，不再与历史会话数量同步增长。本步没有为它增加通用调度器、分页框架或额外线程。

LangGraph checkpoint 本身的存储大小和历史裁剪不属于本步；这里解决的是应用启动对所有会话 checkpoint 的主动扫描。
