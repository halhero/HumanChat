# 第九步：混合召回与独立背景入口

## 做了什么，为什么

**本步最核心的设计不是“把 BM25 换成混合检索”，而是让“描述当前话题的内容”和“影响怎样完成任务的背景”有不同入口。** 前者适合按主题排名；后者即使不相似，也必须有被判断的机会。

新增 `memory/retrieval.py`，由 `MemoryRetriever` 统一读取主记录，使用 rank-bm25 的 BM25Okapi 做词法召回，使用第八步的真实向量索引做语义召回。中文使用单字和相邻双字分词，英文按词；这是初期小库的词法适配，不声称是成熟中文分词器。

两路通过 RRF（Reciprocal Rank Fusion，倒数排名融合）合并：每个名次贡献 `1/(60+rank)`，避免直接比较 BM25 分数和余弦相似度。分数只用于候选入口，不直接决定是否把记忆交给回答模型。

最重要的改变是**不让所有内容挤进一个主题相关性排名**：

1. 普通主题入口：词法与语义混合 top-k。
2. 维护入口：同一主体/关系/范围的记录直接加入，不被 top-k 挤走。
3. 回答入口：当前有效记忆进入独立 `task_background_catalog`，后续按任务判断其中哪些是约束、指导或背景。代码审查表达偏好即便和“Python”没有字面或向量关联，也有被判断的机会。

`RecalledMemory.reasons` 保存每一路召回原因。后面不会再用统一主题重排把背景入口的成果抹掉。

## 关键数据流

```text
主记录 -> 当前/历史视图 -> BM25 + 向量 -> RRF主题候选
                         同身份直取 -> 维护候选
                         当前目录   -> 任务背景候选
候选与召回原因 -> 第十/十一步的不同用途判断
```

索引命中必须在当前主记录中存在，且父版本一致才被接受。索引延迟不会使已删除、已撤销正文直接成为当前事实。回答候选只接收当前/正常历史；错误撤销版本仅供维护判断，不进入回答候选。

外部向量服务故障时记录 `semantic_unavailable` 并写后台日志，不把“检索失败”伪装成“确实没有记忆”。现有词法和背景入口仍可工作。

### 用同一问题看三类候选

当前问题是“解释 Python 协程”。库里有：

| 记录 | 主题检索可能怎样 | 本次潜在用途 |
| --- | --- | --- |
| A：HumanChat 使用 Python | 关键词和语义都可能命中 | 项目背景，是否需要仍待判断 |
| B：学习新概念时通常先看例子 | 未必与协程相似 | 影响解释方式的指导 |
| C：家用机使用 Windows | 可能完全不命中 | 若只解释概念，通常无需使用 |

如果只有主题 top-12，B 可能连复核机会都没有；独立目录让 B、C 都进入任务判断。随后应选 B、排 C。**独立入口不等于把所有背景都塞进回答**，它只是避免在问题还没被理解之前就因不相似丢掉 B。

### RRF 为什么用排名相加，而不是分数相加

BM25 的分数与向量余弦分数没有共同单位，直接 `bm25_score + cosine_score` 容易让量级较大的一路主导。当前按排名计算：

```python
candidate.score += 1 / (60 + rank)
```

假设 A 在词法第1、语义第3，B 在词法无名次、语义第1，则 A 得 `1/61 + 1/63`，B 得 `1/61`。这是演示公式的例子，不是本项目某次模型检索的实测排序。

RRF 奖励被多路较靠前找到的内容，但它不知道“缺少 B 会让回答不符合学习方式”。所以它只负责主题候选合并，不能直接担当最终任务判断。

### 哪几行保证背景不被 top-k 挤掉

以下为 [MemoryRetriever.recall](../human_chat/memory/retrieval.py) 的关键片段，省略同身份分支：

```python
hybrid = sorted(ranked.values(), key=lambda c: c.score, reverse=True)[:self.limit]
ranked = {c.view.id: c for c in hybrid}
for view in views:
    if purpose == "answer" and view.status == "current":
        enter(view, "task_background_catalog")
```

先截取主题候选，再加入所有 current 视图。因此 limit=12 **不意味着最终只返回12条**。`enter` 以视图 ID 合并：A 已在主题候选里，再添加目录原因不会生成第二条 A；B 不在主题结果里，仍能进入。

`reasons` 会保留 lexical、semantic、task_background_catalog 等来源，但目录不额外贡献主题分数。下游消费候选用途，而不是又按该 score 重新裁一次。这正是防止“独立召回后又被统一相关性精排删掉”的接线要求，资料74接着解释。

### 为什么维护与回答不能完全共用候选策略

回答时，只接受 current/historical；revoked 旧错误不能当事实提供。维护时则可能需要看到已撤销的旧内容，判断是不是旧任务在试图重新写入。

另外，“那个目标暂停”可能不复述旧目标正文，纯相似度未必找到目标。Retriever 提供 identity 直取入口；实际 `formation.prepare` 处理一批候选时，还会将候选身份集合与完整 inventory 比对，把相同主体/关系/范围的记录并入维护目标。它们不受主题 top-k 限制，但相同 identity 不代表可以自动覆盖，仍要复核 value 和原话。

### 退化时为什么要保留诊断

| 诊断 | 表示什么 | 对业务意味着什么 |
| --- | --- | --- |
| semantic_not_configured | 没有语义索引 | 词法/目录仍可用，但维护不能当成完整检索 |
| semantic_unavailable | 外部查询失败 | 不应据此认定旧记录不存在 |
| semantic_projection_stale | 返回项与主记录版本不符 | 丢弃这条过期命中 |
| semantic_projection_incomplete | 当前视图未被完整索引 | 可能漏掉刚更新/新增内容；最终集成补充 |

索引命中通过 `by_id.get(item_id)` 及 parent_version 检查回源；最终正文来自本次主记录视图。正常“没找到”和“没有完成可靠检索”必须区分，否则重复写入会在检索故障时增多。
