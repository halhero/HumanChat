# 第九步：混合召回与独立背景入口

## 做了什么，为什么

新增 `memory/retrieval.py`，由 `MemoryRetriever` 统一读取主记录，使用 rank-bm25 的 BM25Okapi 做词法召回，使用第八步的真实向量索引做语义召回。中文使用单字和相邻双字分词，英文按词；这是初期小库的词法适配，不声称是成熟中文分词器。

两路通过 RRF（Reciprocal Rank Fusion，倒数排名融合）合并：每个名次贡献 `1/(60+rank)`，避免直接比较 BM25 分数和余弦相似度。分数只用于候选入口，不直接决定是否把记忆交给回答模型。

最重要的改变是**不让所有内容挤进一个主题相关性排名**：

1. 普通主题入口：词法与语义混合 top-k。
2. 维护入口：同一主体/关系/范围的记录直接加入，不被 top-k 挤走。
3. 回答入口：当前有效记忆进入独立 `task_background_catalog`，后续按任务判断其中哪些是约束、指导或背景。代码审查表达偏好即便和“Python”没有字面或向量关联，也有被判断的机会。

`RecalledMemory.reasons` 保存每一路召回原因。后面不会再用统一主题重排把背景入口的成果抹掉。

## 关键数据流

```text
主记录 -> 当前/历史视图 -> BM25 + 向量 -> RRF主题候选
                         同身份直取 -> 维护候选
                         当前目录   -> 任务背景候选
候选与召回原因 -> 第十/十一步的不同用途判断
```

索引命中必须在当前主记录中存在，且父版本一致才被接受。索引延迟不会使已删除、已撤销正文直接成为当前事实。回答候选只接收当前/正常历史；错误撤销版本仅供维护判断，不进入回答候选。

外部向量服务故障时记录 `semantic_unavailable` 并写后台日志，不把“检索失败”伪装成“确实没有记忆”。现有词法和背景入口仍可工作。

## 验证与局限

执行 `python -m pytest tests/test_memory_retrieval.py -q -p no:cacheprovider --basetemp .validation-step09b-20261015`：1项通过，证明背景不依赖主题 top-k、旧向量版本不被接受、删除后候选不再出现。首次用例把“代码”同时放在查询和指导中，BM25合理选中了指导，不能证明“无关键词联系”；改用单独 `Python` 查询后验证真正的非主题入口。

当前目录入口会随记忆数量增长。下一步判断有明确输入预算，超出时报告降级而不是无声截断；本轮不引入未需要的分类库或第二套持久化标签系统。Graph 尚未切换，统一在第十四步接入。
