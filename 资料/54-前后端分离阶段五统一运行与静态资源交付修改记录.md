# 前后端分离阶段五：统一运行与静态资源交付修改记录

## 1. 本阶段目标

阶段四完成后，开发环境可以通过 Vite 访问前端，但生产使用仍需要分别理解两个服务。
本阶段完成前后端分离工作的最后一段交付链路：

1. 开发环境继续保持 Vite 和 FastAPI 两个独立进程；
2. 生产环境先构建 React，再只运行 FastAPI；
3. FastAPI 在同一个端口交付 HTML、JavaScript、CSS、图片和 API；
4. 前端客户端路由可以回退到 `index.html`；
5. 未知 API 和不存在的静态文件不能被误判成前端页面；
6. 静态资源获得合适的浏览器缓存策略；
7. 前端构建目录可以通过环境变量调整；
8. 不重新引入已经删除的 CLI runtime 或额外业务入口。

本阶段没有增加测试文件，也没有提交 `web/dist`。构建产物由源码和锁文件确定，部署时
生成。

## 2. 开发环境和生产环境为什么采用不同运行方式

### 2.1 开发环境：两个进程

开发时分别运行：

```text
Vite      http://127.0.0.1:5173
FastAPI   http://127.0.0.1:8000
```

Vite 负责 React 热更新、TypeScript 错误反馈和源码映射；FastAPI 负责 Python 自动重载、
Agent 资源生命周期和 API。Vite 将 `/api` 代理到 FastAPI。

这里没有添加自制的长期驻留“开发 runtime”。同时启动两个开发进程只是开发工具问题，
不应重新创建一个能访问 Repository、Graph 或 MemoryService 的业务入口。需要调试某一端
时，也可以单独启动该端。

### 2.2 生产环境：一个进程和一个来源

生产步骤是：

```text
pnpm build
    -> web/dist
python -m human_chat.api
    -> http://127.0.0.1:8000
       ├── /api/v1/*
       ├── /assets/*
       ├── /assistant-avatar.png
       └── /
```

浏览器页面和 API 具有相同的 scheme、host 和 port，即“同源”。这样部署时不需要额外
配置前端服务器，也减少生产 CORS、Cookie、安全头和反向代理路径不一致的问题。

Vite 仍然只负责构建，不作为生产服务器。`vite preview` 适合本地预览，不是本项目的
正式服务入口。

## 3. 新增 frontend.py 的职责

`human_chat/api/frontend.py` 是 FastAPI 的静态交付适配器。它只关心 HTTP 文件响应，不
创建 Application、Graph 或存储资源。

公开函数是：

```python
def install_frontend(app: FastAPI, dist_path: Path) -> None:
```

如果 `dist_path/index.html` 不存在，函数记录 API-only 模式并直接返回。这样：

- 后端开发者无需构建 React 也能运行 API；
- 首次安装依赖时不会因为缺少前端产物导致后端启动失败；
- 只有完整构建存在时才注册前端 catch-all 路由。

该函数没有返回未使用的“前端是否安装”布尔值。调用方只需要安装路由这一副作用，额外
返回值会让接口显得存在第二种控制流程，当前没有必要。

## 4. 为什么前端路由必须最后注册

FastAPI 按路由匹配顺序处理请求。应用创建顺序现在是：

```text
系统 health route
会话 route
轮次 route
前端 catch-all route
```

前端路由使用：

```python
@app.get("/{full_path:path}", include_in_schema=False)
```

它可以匹配任何 GET 路径，因此必须放在所有 API route 之后。合法的
`/api/v1/sessions` 会先匹配 API；只有没有对应 API route 的请求才进入 catch-all。

`include_in_schema=False` 防止这个交付细节出现在 OpenAPI 文档中。前端资源不是业务
API，不应让 API 使用者误以为它是一个通用路径接口。

## 5. SPA 回退与错误边界

单页应用将来可能加入 `/conversation/abc` 等客户端路由。服务器磁盘上没有对应文件，但
浏览器仍需先获得 `index.html`，再由 React Router 等前端路由解析。

处理规则如下：

```text
已存在文件                 -> 返回该文件
不存在且带扩展名           -> 404 resource not_found
不存在、无扩展名、非 API   -> 返回 index.html
未知 /api/*                -> 404 API not_found
解析后越出 dist 根目录      -> 404 resource not_found
```

不能简单地让所有 404 都返回 `index.html`，否则会出现两个问题：

1. `/api/v1/unknown` 返回 HTTP 200 和 HTML，前端会在 JSON 解析处产生含糊错误；
2. `/assets/missing.js` 返回 HTML，浏览器会报告 JavaScript MIME 类型错误。

现在这两种请求都返回项目既有的 `ApiError` JSON 信封和 HTTP 404。

## 6. 路径安全检查

静态文件路径不能直接使用用户提供的字符串读取。实现先执行：

```python
candidate = (root / full_path).resolve()
candidate.relative_to(root)
```

`resolve()` 规范化 `..`、符号链接和绝对路径成分，`relative_to(root)` 验证最终路径仍位于
构建目录内。验证失败时返回 404，不读取文件。

这属于目录穿越防护。例如恶意请求即使尝试构造 `../.env`，也不能借静态路由读取项目
配置。

## 7. 缓存策略

不同文件不能使用同一个缓存周期。

### 7.1 index.html

```text
Cache-Control: no-cache
```

`no-cache` 允许浏览器保存副本，但每次使用前必须向服务器重新验证。部署新版本后，用户
可以及时拿到引用新资源文件名的 HTML。

### 7.2 Vite assets

Vite 输出的资源名包含内容 hash，例如：

```text
assets/index-KDcxQz5.js
```

文件内容变化时文件名也变化，因此可以安全使用：

```text
Cache-Control: public, max-age=31536000, immutable
```

浏览器一年内无需重复下载相同 hash 文件，可以显著降低重复访问流量。

### 7.3 public 目录文件

头像等没有 hash 的资源使用一小时缓存。它们可能在不改文件名的情况下被替换，不能使用
一年 immutable 策略。

## 8. 配置项

`Settings` 新增：

```python
frontend_dist_path: Path = PROJECT_ROOT / "web" / "dist"
```

环境变量：

```env
HUMANCHAT_FRONTEND_DIST_PATH="web/dist"
```

相对路径继续通过项目已有 `_parse_path()` 解析为相对项目根目录的绝对语义路径，部署系统
也可以提供绝对路径。这个配置属于交付层，而不是 `HumanChatApplication` 资源，所以由
FastAPI factory 使用，没有传入 Graph。

## 9. 完整运行方式

### 9.1 开发

终端一：

```powershell
python -m human_chat.api
```

终端二：

```powershell
Set-Location web
pnpm install
pnpm dev
```

访问 `http://127.0.0.1:5173`。

### 9.2 生产式本地运行

```powershell
Set-Location web
pnpm install --frozen-lockfile
pnpm build
Set-Location ..
python -m human_chat.api
```

访问 `http://127.0.0.1:8000`。运行期只需要 FastAPI 进程；`web/dist` 是构建阶段输入。

## 10. 为什么不提交 dist

`dist` 是可再生构建产物：

- 源码已经位于 `web/src`；
- 直接依赖位于 `package.json`；
- 完整依赖版本位于 `pnpm-lock.yaml`；
- 构建配置位于 `vite.config.ts` 和 `tsconfig`；
- `pnpm build` 可以重复生成相同功能的产物。

把 `dist` 提交到 Git 会造成源码和产物可能不同步、每次修改产生大量压缩文件差异，并
扩大代码审查噪声。成熟部署流程应在 CI 或发布阶段构建它。
