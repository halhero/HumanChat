# 记忆模块重构第二步：数据契约

日期：2026-10-15。前置资料64；前置提交 `fed15f2`。

## 改了什么

将 `memory_models.py` 的职责移到 `human_chat/memory/models.py`，建立正式记忆包，更新全部业务与测试导入，不保留旧转发模块。新增 Assertion、Evidence、MemoryVersion、Mutation 与 MutationResult，扩展 MemoryItem 的来源、状态、版本、历史和回执字段。

这是契约增量，不是自动维护已经启用。原 Service 仍按原方式工作，后面逐步接入新规则。

## 为什么这样改

**本步的重点是把“一条认识”“支持它的原话”“准备对它做的修改”拆开。** 它们的生命周期不同：认识会变化，旧原话不会因为更新而被改写；修改提案也可能被拒绝，不能把提案直接当作已保存事实。

只保存 text 无法可靠表达“目标内容保持不变，只有状态暂停”。Assertion 将内容 value、状态 state、期限 deadline 分开；scope 保留设备或任务范围，negated 保留否定。identity 用于比较主体/关系/范围，不是数据库唯一约束，因此 Python 与 Rust 偏好可以并存。

Evidence 保存用户发言引用，MemoryVersion 保存变更前认识。历史状态 historical 表示曾经有效；revoked 表示纠错或撤回后不能作为真实过去使用。active/retracted/deleted 表示当前记录的维护状态。

## 数据流和关键字段

原始消息以后转换为 Evidence；Assertion 由候选表达认识；Mutation 是执行建议，包含目标 ID、预期版本和允许修改字段；MutationResult 是程序执行结果。它们不授予 LLM 直接存储权限。

例如目标 value=完成记忆模块、state=进行中、deadline=年底。未来暂停操作只提交 state 字段，不能因为没有重复说目标内容就将 value 清空。

`usable_now()` 区分明确过期时间 expires_at 与目标期限 deadline。期限过去不意味着完成；只有明确的使用过期规则影响供给。

### 把一句话逐层拆成对象

假设输入是“我想年底完成 HumanChat 记忆模块，目前正在做”。下面是**字段含义示例，不是声称模型每次都会提取出完全相同的词**：

```python
assertion = Assertion(
    subject="default", relation="项目目标", scope="HumanChat",
    value="完成记忆模块", state="进行中", deadline="年底",
)
```

`value` 回答“做什么”；`state` 回答“现在处于什么状态”；`deadline` 回答“计划何时完成”。把它们都拼进一个 text，暂停时就必须重写整句，容易顺便丢掉期限。结构化后仍有 `text`，但自动写入会通过 `Assertion.render()` 从结构生成正文，避免维护两份互相矛盾的内容。

证据则保存原话而不是提取后的改写：

```python
evidence = Evidence(
    message_id=source.id, user_id=source.user_id,
    session_id=source.session_id, message_time=source.occurred_at,
    quote="我想年底完成 HumanChat 记忆模块，目前正在做",
)
item = MemoryItem(
    text=assertion.render(), user_id=source.user_id,
    assertion=assertion, evidence=[evidence], observed_at=source.occurred_at,
)
```

这里 `source` 指资料64中的可信新消息。`Evidence` 不让模型自己决定归属和接收时间；形成模块之后负责把引用映射回这个来源。调用 `MemoryItem(...)` 只是建立内存对象，真正保存要经过资料66的仓储。

### 五种类型各管什么

| 类型 | 用例 | 不要误解成 |
| --- | --- | --- |
| `Assertion` | 目标内容、范围、状态和期限 | 固定 facts/notes 分类 |
| `Evidence` | u1 的哪句原话支持这个判断 | 模型“我认为可信”的理由 |
| `MemoryItem` | 当前认识及它的版本、历史和回执 | 只用于展示的文本 |
| `MemoryVersion` | 更新之前的状态及依据 | 一定真实有效的过去；还要看 historical/revoked |
| `Mutation` | 请求将 m1 的第2版只改 state | 已执行成功的数据库写入 |

`MutationResult` 则回答执行情况：`applied` 已执行，`already_applied` 此操作以前已执行，`conflict` 依据版本等条件不再成立，`rejected` 请求违反边界。将这些区别保留下来，后台才不必把每种失败都当成网络异常重试。

### 三种“时间”和两种“状态”不能混用

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `Evidence.message_time` / `observed_at` | 程序何时收到支持认识的消息 | 今天收到用户说明 |
| `effective_time` | 用户说明事实何时发生/生效 | “上周已经改用 Linux”中的上周 |
| `created_at` / `updated_at` | 这份记录何时写入/修改 | 后台几秒后写入 |
| `deadline` | 目标期限 | 年底，不等于年底自动完成 |
| `expires_at` | 明确的供给失效时间 | 过此时刻不再当有效当前记忆 |

同理，`assertion.state="暂停"` 是项目状态；`item.status="active"` 是这条认识仍然有效。一个暂停中的项目完全可以由一条 active 记忆表示。`retracted` 表示撤回认识，不能拿来表示项目暂停。

### 两处容易看不懂的 Python 写法

```python
history: list[MemoryVersion] = Field(default_factory=list)
status: Literal["active", "retracted", "deleted"] = "active"
```

`default_factory=list` 为每个实例创建自己的列表；`Literal` 限定状态只能是列出的值，避免拼错后悄悄形成第四种状态。`Assertion` 的 `extra="forbid"` 会拒绝契约之外的字段，模型不能临时创造一个 `category` 让程序误以为已经支持。

`identity()` 返回规范化的 `(subject, relation, scope)`，用于找可能相关的旧认识。它**没有包含 value，也不是唯一键**：同一个人可以同时喜欢 Python 和 Rust，不能见到 identity 相同就覆盖旧记录。究竟并存还是更新，由后面的维护判断结合原话决定。

## 旧数据与接口

旧分类仅用于读取兼容，不成为新保存类别。转换 ID 根据旧类别、位置和正文确定，不在每次加载时随机变化；缺失来源和时间保持未知，不编造当前时间。

因此 API 的记忆日期允许 null，前端记忆列表显示“时间未知”。这几处同步修改属于同一个数据契约，避免后端允许未知、前端却强制格式化错误日期。新创建记录仍产生真实写入时间。
