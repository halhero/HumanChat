# 双执行模式第二步：基线契约纠正修改记录

日期：2026-11-21。

## 1. 本步修改了什么

本步先纠正资料 96 中已进入代码、但不属于最终方案的两个额度概念，并把后续 Graph 将使用的数据契约固定下来。

删除的配置是：

```text
plan_initial_execution_limit
plan_execution_limit_increment
```

最终只保留：

| 配置 | 默认值 | 唯一职责 |
| --- | ---: | --- |
| `react_tool_call_limit` | 3 | 一次 ReAct Agent 运行允许的工具请求数 |
| `plan_initial_max_steps` | 6 | 首次计划最大步骤数，同时是首次自动尝试额度 |
| `plan_hard_execution_limit` | 12 | 本轮最多可形成的真实步骤尝试记录数 |
| `plan_step_tool_call_limit` | 4 | 一次单步骤 Agent 运行的工具请求数 |

## 2. 为什么删除两个配置

旧方案把“首次计划规模”和“首次自动执行额度”拆成两个配置，又为用户选择继续时增加固定 `+3` 的续批量。这会导致两个实际问题：

1. 同一个“可以自动尝试多少步”的业务意图被多个参数重复表示，容易出现相互冲突的配置。
2. 固定增量会让同一任务重复中断并询问，而最终设计只需一次软额度确认。

因此，`plan_initial_max_steps` 同时表示首次计划规模和首次已授权的累计尝试数。用户选择继续后，一次性授权到 `plan_hard_execution_limit`，不再引入第五种额度概念。

## 3. 配置边界怎样落地

`Settings` 只保留一条跨字段不变量：

```text
plan_hard_execution_limit >= plan_initial_max_steps
```

每个字段自身仍由 Pydantic 限制为正整数。这些检查集中在外部配置进入系统的边界，后续节点不重复校验。

`.env.example` 和环境变量映射已同步删除两个旧变量，防止配置表面上仍可用、实际上已无任何消费者。

## 4. 执行契约的最终边界

`human_chat/execution.py` 现在只保存已确认的结构化契约和四个模型 Prompt：

- `PlanStep`：当前要做什么、如何判断成功、是否需要之后重规划；
- `StepResultSubmission`：单次尝试的 `completed | failed | blocked` 结果；
- `StepExecutionRecord`：真实执行过的步骤和结果；
- `ExecutionPlan`：至少包含一步的线性首次计划；
- `ReplanDecision`：互斥的 `continue | revise | finish` 决定；
- `PlanEndReason`：仅允许 `completed | planner_finished | blocked | user_stopped | hard_limit`。

Prompt 规定了 Planner、Step Agent、Replan 和最终汇总器各自的输入与输出边界。它们不创建新节点或流程，只是为下一阶段已经确认的四类 LLM 职责提供单一契约。

## 5. 为什么本提交没有先删除旧 ChatState

旧手写 ReAct 节点仍然在当前已提交 Graph 中读写 `tool_messages` 等字段。如果先单独删除这些字段，这个分步提交会制造一个必然无法运行的中间版本。

因此状态替换会与官方 `create_agent` 真正接管 ReAct 的同一提交完成：新 Agent 接通后同时删除旧节点和旧状态。这只调整分步提交的分界，不改变最终数据设计。
