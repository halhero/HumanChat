# 50 前后端分离阶段一：后端应用基础修改记录

## 一、本阶段目标

本阶段是 HumanChat 前后端分离的第一步，目标不是立刻实现聊天页面，而是先建立一个
可以长期运行、能够被浏览器安全调用的后端应用基础。

本阶段完成以下内容：

1. 新增 FastAPI HTTP API 入口。
2. 把 Checkpointer、Memory、ToolRegistry 和编译后的 LangGraph 提升为应用级资源。
3. 保留现有 CLI，并让 CLI 和 API 复用同一套资源创建逻辑。
4. 建立版本化 API 路径 `/api/v1`。
5. 增加健康检查、请求 ID、统一错误格式和受限 CORS。
6. 增加 API 启动配置和正式启动命令。

本阶段暂不实现会话、聊天流、审批和前端页面。这些内容将在后续阶段建立在当前稳定
边界上，而不是直接操作 LangGraph 内部状态。

## 二、为什么先做后端应用基础

### 1. 原来的 Runtime 生命周期适合 CLI，不适合 HTTP

原来的 `open_chat_runtime()` 每打开一次就会创建：

```text
Checkpointer
MemoryResource
ToolRegistry
MCP 后台事件循环
CompiledStateGraph
```

CLI 在一次启动过程中只打开一个 Runtime，所以这种方式没有问题。但 HTTP 服务会连续
处理很多请求。如果每个请求都重新创建上述资源，会产生：

1. MCP Server 反复发现工具。
2. SQLite 或数据库连接反复建立。
3. 后台事件循环和线程反复创建。
4. Graph 反复编译。
5. 请求延迟显著增加。

因此需要把昂贵资源提升到 FastAPI 应用生命周期，只在进程启动时创建一次。

### 2. 浏览器不能直接使用 Python Runtime

React 运行在浏览器，不能直接导入：

```python
from human_chat.runtime import ChatRuntime
```

浏览器与 Python 后端之间必须通过 HTTP 协议通信。FastAPI 的作用是把内部 Python
对象转换成稳定的 JSON API，同时保证 API Key、MCP 凭据、数据库连接和 Graph State
不会进入浏览器。

### 3. API 契约需要与内部实现解耦

后续前端只能依赖：

```text
/api/v1/sessions
/api/v1/turns
/api/v1/events
```

而不能依赖 `ChatState`、Graph 节点名称或 Repository 类。这样以后重构 Graph 时，前端
不需要跟着修改。

## 三、总体结构

本阶段建立后的结构如下：

```text
CLI -----------------------+
                           |
FastAPI /api/v1 -----------+--> ChatApplication
                                      |
                                      +--> CheckpointerResource
                                      +--> MemoryResource
                                      +--> ToolRegistry
                                      +--> CompiledStateGraph
                                      |
                                      +--> ChatRuntime(thread_id=A)
                                      +--> ChatRuntime(thread_id=B)
```

`ChatApplication` 持有共享资源。`ChatRuntime` 仍然表示具体会话，通过不同
`thread_id` 保持 LangGraph Checkpoint 隔离。

## 四、ChatApplication 设计

### 1. 应用级资源对象

在 `human_chat/runtime.py` 中新增：

```python
class ChatApplication:
    def __init__(
        self,
        settings,
        app,
        session_repository,
        checkpoint,
        memory,
        tool_registry,
    ):
        ...
```

这里的 `app` 是编译后的 LangGraph，不是 FastAPI 对象。

`ChatApplication.create_runtime()` 只创建轻量的会话 Runtime：

```python
runtime = application.create_runtime(session)
```

它不会重新加载 MCP 工具或重新打开数据库，而是复用共享资源，并为会话设置独立的：

```python
{"configurable": {"thread_id": session.thread_id}}
```

### 2. 上下文管理器

新增：

```python
@contextmanager
def open_chat_application(settings):
    ...
```

Python 上下文管理器的基本语法是：

```python
with open_resource() as resource:
    use(resource)
```

进入 `with` 时获取资源，离开时无论正常结束还是发生异常，都会执行清理逻辑。

HumanChat 使用嵌套上下文管理器保证关闭顺序与打开顺序相反：

```text
打开 Checkpointer
  打开 Memory
    打开 ToolRegistry
      使用 Graph
    关闭 ToolRegistry
  关闭 Memory
关闭 Checkpointer
```

这对 MCP 后台线程和数据库连接尤其重要。

### 3. CLI 兼容

原 `open_chat_runtime()` 没有删除，而是改为复用：

```python
with open_chat_application(...) as application:
    yield application.create_runtime(...)
```

因此：

```powershell
python main.py
```

仍然使用原来的 CLI 行为，同时避免维护两套资源创建逻辑。

## 五、FastAPI 应用工厂

### 1. 为什么使用应用工厂

新增：

```python
def create_api(settings: Settings | None = None) -> FastAPI:
    ...
```

相比在模块顶层写死所有配置，应用工厂允许：

1. 正式启动时读取 `.env`。
2. 临时验证时传入隔离 Settings。
3. 将来为桌面版或不同部署创建不同应用实例。
4. 避免导入模块时立刻连接数据库或 MCP Server。

模块仍然导出：

```python
app = create_api()
```

这是 ASGI Server 查找应用对象的标准形式。

### 2. FastAPI lifespan

官方推荐使用 `lifespan` 管理启动和关闭资源：

```text
https://fastapi.tiangolo.com/advanced/events/
```

代码使用：

```python
@asynccontextmanager
async def lifespan(application: FastAPI):
    with open_chat_application(settings) as chat_application:
        application.state.chat_application = chat_application
        yield
```

`yield` 之前在服务接收请求前执行，`yield` 之后在服务停止时执行。这样共享 Agent
资源覆盖完整的 Web 进程生命周期。

这里使用 `application.state` 保存资源，而不是模块级全局变量，原因是一个 Python
进程可能创建多个 FastAPI 实例，应用状态应属于具体实例。

## 六、FastAPI 依赖注入

新增 `human_chat/api/dependencies.py`：

```python
def get_chat_application(request: Request) -> ChatApplication:
    return request.app.state.chat_application
```

路由使用：

```python
def get_health(application: ChatApplicationDependency):
    ...
```

FastAPI 会自动调用依赖函数，并把返回值传给路由。这样路由不需要导入全局对象，也便于
后续替换为不同应用资源。

`Annotated` 的语法：

```python
Annotated[ChatApplication, Depends(get_chat_application)]
```

左侧是参数的 Python 类型，右侧告诉 FastAPI 如何获得它。

## 七、Pydantic response_model

健康接口定义：

```python
@router.get("/health", response_model=HealthResponse)
```

`response_model` 的作用包括：

1. 校验后端返回结构。
2. 生成 OpenAPI 文档。
3. 过滤未声明字段，避免内部对象意外暴露。
4. 为未来 TypeScript 客户端提供 Schema 来源。

健康接口只返回安全状态：

```json
{
  "status": "ok",
  "service": "HumanChat API",
  "version": "0.1.0",
  "features": {
    "checkpoint_backend": "sqlite",
    "checkpoint_persistent": true,
    "memory_backend": "json",
    "mcp_enabled": false,
    "registered_tool_count": 3
  }
}
```

它不会返回 API Key、数据库 URI、本地路径或 MCP Header。

## 八、请求 ID 与错误协议

### 1. 请求 ID 中间件

FastAPI 中间件包裹每一个 HTTP 请求：

```python
@application.middleware("http")
async def attach_request_id(request, call_next):
    ...
```

每个请求都会获得 `X-Request-ID`。前端报告错误时可以提供这个 ID，后端日志可以据此
定位同一个请求。

客户端可以传入请求 ID，但后端限制最大 128 个字符，避免不受控 Header 进入日志。

### 2. 统一错误结构

公开错误统一为：

```json
{
  "error": {
    "code": "validation_error",
    "message": "请求参数格式不正确。",
    "request_id": "..."
  }
}
```

后端日志保留真实异常，浏览器只收到安全信息，不会看到堆栈、文件路径和凭据。

## 九、CORS 是什么

前端开发服务器通常运行在：

```text
http://localhost:5173
```

后端运行在：

```text
http://127.0.0.1:8000
```

端口不同就属于不同 Origin。浏览器默认阻止跨 Origin 请求，后端必须通过 CORS 明确
允许可信前端。

本项目没有使用危险的：

```python
allow_origins=["*"]
```

而是通过环境变量配置精确来源：

```env
HUMANCHAT_API_CORS_ORIGINS="http://127.0.0.1:5173,http://localhost:5173"
```

同时只开放需要的 HTTP 方法和 Header。

## 十、API 版本路径

所有业务 API 使用：

```text
/api/v1/...
```

版本号放在 URL 中的意义是：未来出现不兼容协议时，可以新增 `/api/v2`，而不立即破坏
已经发布的前端。

当前接口：

```text
GET /api/v1/health
```

## 十一、配置与启动

新增环境配置：

```env
HUMANCHAT_API_HOST="127.0.0.1"
HUMANCHAT_API_PORT="8000"
HUMANCHAT_API_CORS_ORIGINS="http://127.0.0.1:5173,http://localhost:5173"
```

默认绑定 `127.0.0.1`，不会直接暴露到局域网或公网。未来正式部署应由反向代理处理
HTTPS 和外部访问。

启动命令：

```powershell
python -m human_chat.api
```

Uvicorn 是运行 FastAPI ASGI 应用的 Server。FastAPI 负责路由和数据模型，Uvicorn
负责监听端口、接收 HTTP 请求并调用应用。
