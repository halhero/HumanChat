# 误删功能修复阶段四：长期记忆管理恢复修改记录

## 1. 本阶段目标

前后端分离删除旧 CLI 后，长期记忆的自动提取、用户审核和底层持久化仍然存在，但用户
失去了主动查看、添加和删除记忆的入口。本阶段恢复这一产品能力，同时不恢复旧的 CLI
命令体系。

完成内容如下：

1. MemoryService 提供稳定 ID 删除能力；
2. Application 暴露查看、添加、删除记忆三个业务用例；
3. FastAPI 提供版本化的长期记忆管理接口；
4. React 侧边栏增加长期记忆入口；
5. 新增紧凑的记忆管理对话框；
6. 删除操作需要二次确认；
7. 自动提取和手动管理继续共用同一个 MemoryService；
8. Repository 和具体存储后端仍不暴露给 API 与前端。

## 2. 原来的功能缺口

旧 CLI 曾提供：

```text
/memory
/memory add 内容
/memory delete 序号
```

删除 CLI 文件本身是合理的，因为项目已经转向 Web；问题在于新的 API 和 React 页面没有
接替这些用户能力。结果是系统可以自动写入长期记忆，但用户不能查看系统记住了什么，也
不能修正不准确或已经过期的信息。

长期记忆会进入后续对话的系统上下文，所以可查看、可纠正和可删除不是装饰功能，而是
数据可控性的基本要求。

## 3. 为什么不恢复“按序号删除”

旧实现先读取列表，再把用户输入的序号减一：

```python
item = items[index - 1]
```

序号只是某一次显示结果的位置，不是记忆的业务身份。Web 环境中可能同时发生：

- 自动记忆审核保存新内容；
- 用户在另一个页面添加记忆；
- 存储后端采用不同排序；
- 页面刷新后列表顺序变化。

如果客户端请求“删除第 2 条”，服务端重新加载后的第 2 条可能已经不是用户看到的那条。
因此新接口使用创建 MemoryItem 时生成的稳定 `id`：

```http
DELETE /api/v1/memories/{memory_id}
```

服务端先按 ID 查找，再删除相同 ID。不存在时返回 404，重复删除不会误伤其他记忆。

## 4. MemoryService 返回 MemoryItem 的原因

旧 `add()` 只返回布尔值：

```python
True   # 已添加
False  # 空文本或重复
```

Web API 创建成功后需要返回新记录的 `id`、时间和来源。如果仍只返回布尔值，Application
只能重新读取全部记录并按文本猜测刚创建的是哪一条，这会制造竞态和重复查询。

新签名是：

```python
def add(...) -> MemoryItem | None
```

- 成功时返回真正写入 Repository 的对象；
- 空文本或重复内容时返回 `None`；
- Graph 原有的 `if memory_service.add(...)` 判断仍然成立；
- API 可以直接序列化同一个对象，不需要了解 Repository。

删除同样返回被删除的 `MemoryItem | None`，Application 可以明确判断是否存在。

## 5. `source` 不是被取消的 `category`

当前 MemoryItem 没有 `preferences`、`facts`、`notes` 这类分类标签。本阶段没有把它们
恢复。

保留的 `source` 表示数据来源：

```text
manual                用户主动添加
extracted_confirmed   对话中提取并由用户确认
legacy                历史格式读取时产生
```

二者含义不同：

- `category` 试图判断“这条记忆属于什么语义类别”；
- `source` 只记录“这条记忆通过什么流程进入系统”。

来源信息可用于审计和界面说明，不参与 Prompt 分类，也不会重新形成之前已经取消的固定
事实/偏好/备注结构。

## 6. Service 内部并发保护

JSON Repository 的添加过程包含“读取现有内容、检查重复、写入新内容”三个步骤。如果
Graph 自动保存和 Web 手动添加在同一进程中并发执行，两个线程可能同时通过重复检查。

`LongTermMemoryService` 新增一个 `RLock`，把以下操作包在同一 Service 临界区：

- 读取；
- 检查重复并添加；
- 按 ID 查找并删除；
- 生成 Prompt 文本。

使用 `RLock` 而不是把锁放到 API，是因为 Graph 和 API 都会调用 MemoryService。锁位于
业务服务层，所有进程内调用路径都受到一致保护。

这解决的是当前单进程部署中的线程并发。未来多进程或多实例部署时，Postgres 后端还应
依靠数据库唯一约束和事务提供跨进程一致性；进程锁不能替代数据库事务。

## 7. Application 边界

`HumanChatApplication` 新增：

```python
list_memories()
add_memory(text)
delete_memory(memory_id)
```

调用方向保持为：

```text
FastAPI -> HumanChatApplication -> MemoryService -> MemoryRepository -> Store
```

FastAPI 不会获得 `MemoryResource.repository`，事实上 MemoryResource 也没有公开 repository
字段。这样 JSON、InMemoryStore 与 PostgresStore 的差异不会泄漏到 HTTP 层。

## 8. 新增 HTTP API

### 8.1 查看长期记忆

```http
GET /api/v1/memories
```

响应：

```json
{
  "items": [
    {
      "id": "...",
      "text": "用户正在开发 HumanChat。",
      "created_at": "...",
      "updated_at": "...",
      "source": "manual",
      "confidence": null
    }
  ]
}
```

### 8.2 添加长期记忆

```http
POST /api/v1/memories
Content-Type: application/json

{"text": "需要长期记住的内容"}
```

文本由 Pydantic 去除首尾空白并限制为最多 5000 字符。成功返回 HTTP 201 和新 MemoryItem；
完全相同的内容返回 HTTP 409 `memory_exists`。

### 8.3 删除长期记忆

```http
DELETE /api/v1/memories/{memory_id}
```

成功返回 HTTP 204，不返回多余 JSON；ID 不存在或过长时返回 HTTP 404
`memory_not_found`。

API 使用 ID，而不是让前端传完整对象或底层 namespace。当前默认用户的 namespace 仍由
MemoryService 初始化时确定。

## 9. 前端记忆管理界面

侧边栏顶部增加 Brain 图标按钮，打开 `MemoryDialog`。对话框包含：

- 已确认记忆列表；
- 每条记忆的文本；
- 来源说明；
- 创建日期；
- 删除按钮；
- 新记忆输入框和添加按钮。

界面不显示 namespace、Repository 类型、Store key 等内部概念。用户管理的是业务记忆，
不应理解持久化实现。

## 10. 删除为什么使用两次明确操作

删除会直接改变后续对话上下文，属于不可通过普通撤销按钮恢复的操作。点击垃圾桶后不会
立即发请求，而是在同一条记录旁切换为：

- 取消删除；
- 确认删除。

只有第二次点击确认按钮才调用 DELETE API。相比浏览器原生 `confirm()`，这种方式可以：

1. 保持界面风格一致；
2. 明确指出将删除哪一条；
3. 支持 loading 和 disabled 状态；
4. 不阻塞整个浏览器 JavaScript 线程。

## 11. 前端请求生命周期

`MemoryDialog` 使用 `AbortController` 管理列表、添加和删除请求：

- 新 mutation 开始前取消旧请求；
- 对话框关闭时取消当前请求；
- 被主动取消的 `AbortError` 不显示为系统错误；
- 真实 API 错误继续进入 App 统一错误提示。

添加和删除期间使用 `mutating` 锁住相关按钮，避免双击产生重复请求。添加成功后直接把
服务端返回的 MemoryItem 加入列表，不执行第二次全量读取。

## 12. 前端类型与 API 封装

`types.ts` 新增 `MemoryItem`，字段与后端公开模型一致。`api.ts` 新增：

```typescript
listMemories()
createMemory(text)
deleteMemory(memoryId)
```

DELETE 成功是 HTTP 204，没有 JSON Body，因此 `deleteMemory()` 单独检查 response.ok，
不调用通用 `requestJson()`。否则前端会在成功响应上执行 `response.json()` 并错误地报告
JSON 解析失败。

## 13. 可访问性和响应式处理

对话框使用 `role="dialog"`、`aria-modal="true"` 和标题关联；图标按钮包含 `aria-label`
与 `title`。加载完成后焦点进入新增记忆输入框，Escape 可以关闭。

桌面端输入框和添加按钮横向排列；窄屏下改为上下排列，按钮占满可用宽度。列表区域独立
滚动，长记忆使用自动换行，不会把对话框撑出视口。

## 16. 商业项目意义

这一阶段恢复的不只是三个旧 CLI 命令，而是长期记忆的数据治理能力：

- 用户知道 Agent 保存了什么；
- 用户可以主动补充重要背景；
- 用户可以删除错误、敏感或过期内容；
- 自动保存与手动管理不会形成两套数据源；
- API 使用稳定身份，不依赖界面顺序；
- 存储实现仍可在 JSON、内存和 Postgres 间替换。

这为未来增加认证、多用户隔离和记忆权限控制提供了清晰边界，但本次没有提前引入尚未
需要的多用户界面。
