# 回答记忆有界混合召回修改记录

日期：2026-11-11。

## 1. 原来的无界回答召回

旧 `MemoryRetriever.recall()` 先执行有界词法与语义召回：

```text
lexical Top-K
semantic Top-K
RRF 融合并截断
```

但在回答场景中，随后又调用无参数的 `current_documents()`，把索引库中所有 current 记忆加入候选集合。

这使前面的 Top-K 只限制两个搜索通道，不能限制最终发送给 applicability LLM 的候选数量。记忆越多，每轮回答读取、对象构造、JSON 序列化和模型输入就越大。

## 2. 为什么不能给 current_documents 随意增加 LIMIT

直接执行：

```sql
SELECT ... WHERE status='current' LIMIT 20
```

虽然能控制数量，却没有任何相关性或适用范围依据。重要的全局回答规则可能因为插入顺序落在第 21 条后，而无关背景事实可能占满前 20 条。

问题的根源不是缺少一个 LIMIT，而是全量 catalog 用无限读取掩盖了记忆适用范围信号不足。

## 3. 使用现有 Assertion.scope

项目已有：

```python
Assertion.scope
```

它原本用于保存“代码审查”“某项目”“某机器”等适用范围。本步没有新增 category、路由对象或第二套分类字段，而是明确 scope 契约：

- 明确适用于所有未来任务的长期规则：`scope="全局"`；
- 只适用于某类任务：保存具体任务范围，例如 `代码审查`；
- 普通没有任务范围的事实：scope 留空，不能自动解释成全局规则。

形成 Prompt 同步增加了这项说明；Review Prompt 明确只有用户原话确实不限任务时才能使用全局 scope，不能把局部偏好放大。

## 4. 新的有界召回通道

回答召回现在包含：

```text
词法检索窗口
   +
语义向量检索窗口
   +
明确 global scope 查询
```

### 4.1 词法与语义通道

原有 FTS5/PostgreSQL FTS、sqlite-vec/pgvector 和 RRF 分数保持不变。索引正文由 Assertion 渲染，已经包含 subject、relation、value 和非空 scope。

### 4.2 有界 recent context

只使用当前一句问题会漏掉承接上文的表达，例如：

```text
上一轮：继续 HumanChat 的代码审查
当前轮：那下一步呢
```

`MemoryContextBuilder` 现在把已经受 `memory_history_tokens` 限制的 recent context 与当前问题组合成检索查询。因此项目名、任务类型和范围词可以进入词法与语义检索，但不会重新读取无界历史。

### 4.3 global scope 通道

全局规则不要求与问题主题相似。Reader 新增：

```python
search_global_scope(limit, statuses)
```

SQLite 使用：

```sql
json_extract(assertion_json, '$.scope') = '全局'
```

PostgreSQL 使用：

```sql
assertion_json->>'scope' = '全局'
```

两个后端都为 scope 表达式建立索引，并在数据库侧排序、限制结果，不会把全部 current 条目加载到 Python。

## 5. 候选配额与最终上限

默认 `memory_recall_limit=24`。回答召回最多为全局规则保留三分之一位置：

```text
global_limit = recall_limit // 3
```

实际全局规则少于该数量时，剩余位置全部由词法/语义结果补足。所有通道合并、去重后，最终候选总数不超过 `memory_recall_limit`。

这个设计解决两个相反风险：

- 全局规则不会因为与当前主题不相似而完全丢失；
- 全局规则和普通事实都不能无限扩大 applicability 输入。

维护场景仍保留 exact identity 召回。identity 用于防止更新和新增判断遗漏对应旧记录，不受回答候选配额语义影响。

## 6. 删除 current_documents

以下内容已经删除：

- `MemoryIndexReader.current_documents()`；
- SQLite 的全量 current 查询；
- PostgreSQL 的全量 current 查询；
- `task_background_catalog` recall reason；
- applicability Prompt 中对全量 catalog 的说明。

项目中不再存在 `current_documents` 或 `task_background_catalog` 调用点。

## 7. 数据库结构变化

没有修改权威记忆数据库结构。变化只发生在可重建的检索投影：

- SQLite 增加 assertion scope 表达式索引；
- PostgreSQL 增加 namespace + scope + status 表达式索引。

现有 `assertion_json` 数据无需复制或新增列。`CREATE INDEX IF NOT EXISTS` 会在打开 index store 时为已有检索数据库补齐索引。

索引条目 ID 继续保持：

```text
{parent_id}@{version}
```

## 8. 修改后的回答数据流

```text
当前问题 + 有界 recent context
            ↓
      lexical Top-(limit*4)
      semantic Top-(limit*4)
      global scope Top-(limit/3)
            ↓
        合并并去重
            ↓
   保留 global scope 配额
            ↓
    用 RRF 填充剩余位置
            ↓
最终候选数 <= memory_recall_limit
            ↓
      LLM applicability
            ↓
按 parent_id 定向读取权威记录
```

## 10. 设计限制

任何有界检索都无法可靠找回一条“与当前任务完全不相似、同时也没有适用范围信号”的记忆。旧实现通过发送全部 current 记录回避了这个事实，但代价是系统不可扩展。

因此新设计要求真正跨任务适用的规则使用明确 `scope=全局`。现有无 scope 记录仍可通过词法和语义相关性召回，但不会被无条件加入每轮回答。

PostgreSQL 的 SQL 和表达式索引代码已更新并可导入；当前环境没有外部 PostgreSQL + pgvector 服务，因此没有声明真实远程数据库查询已经执行。
