# 前后端分离阶段三：会话与流式对话接口修改记录

## 1. 本阶段要解决什么问题

阶段一建立了 FastAPI 进程入口，阶段二把资源创建收口到了
`HumanChatApplication`，但浏览器仍然没有完整的聊天接口。本阶段补齐从“选择会话”
到“得到回答、处理中断、取消请求”的后端闭环，为下一阶段的精简 React 前端提供稳定
契约。

本阶段完成以下能力：

1. 创建、列出和读取会话；
2. 从 LangGraph checkpoint 读取可展示的历史消息；
3. 使用 Server-Sent Events（SSE）返回一轮对话的进度和结果；
4. 同一会话禁止并发执行多个轮次；
5. 支持客户端断开和用户主动取消；
6. 把 LangGraph `interrupt()` 转换为前端可理解的审批请求；
7. 审批后使用 `Command(resume=...)` 从原 checkpoint 继续执行；
8. 隐藏 Repository、Graph State 和普通工具调用细节。

本阶段没有添加测试文件。验证采用现有测试集、语法编译和临时的真实 API 冒烟脚本，
不会在仓库中留下额外测试代码。

## 2. 为什么需要三层边界

本阶段没有把全部代码都写进 FastAPI route，而是形成以下职责方向：

```text
FastAPI route
    -> ConversationService
        -> HumanChatApplication
            -> LangGraph / SessionRepository / MemoryService / ToolRegistry
```

### 2.1 FastAPI route：只处理 HTTP

Route 负责：

- 校验 URL 和 JSON 请求；
- 把业务异常映射为 `404`、`409` 等 HTTP 状态；
- 返回 JSON 或 SSE；
- 不直接读取 Repository，也不直接调用 Graph。

这样做的商业价值是让接口协议和核心执行逻辑可以分别变化。例如未来更换 WebSocket，
只需替换传输层，不需要改写 Agent 工作流。

### 2.2 ConversationService：管理进程内的“活动轮次”

LangGraph checkpoint 擅长保存可恢复的 Agent 状态，但浏览器还需要一些短生命周期状态：

- 本次请求的 `turn_id`；
- 当前是运行中、等待审批、取消中还是已完成；
- 当前 SSE 订阅使用的事件队列；
- 一个 session 是否已有活动轮次；
- 当前运行使用的 `RunControl`。

这些数据只在后端进程运行期间有意义，因此由 `ConversationService` 在内存中管理。它不
替代 LangGraph checkpoint，也不保存长期聊天历史。

### 2.3 HumanChatApplication：资源和用例边界

`HumanChatApplication` 继续负责：

- 访问会话 Repository；
- 调用编译后的 Graph；
- 读取 Graph checkpoint；
- 在 Graph 执行后更新会话元数据；
- 对上层隐藏具体持久化实现。

`ConversationService` 只依赖 `HumanChatApplication` 的公开方法。这样 Repository、
Checkpointer、MemoryService 和 ToolRegistry 都没有重新暴露到 API 层。

## 3. 会话接口设计

新增接口如下：

| 方法 | 地址 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/sessions` | 返回最近会话 |
| `POST` | `/api/v1/sessions` | 创建新会话 |
| `GET` | `/api/v1/sessions/{id}` | 返回会话元数据和历史消息 |
| `POST` | `/api/v1/sessions/{id}/turns` | 开始一轮对话并返回 SSE |
| `GET` | `/api/v1/turns/{id}` | 查询轮次状态和待审批内容 |
| `POST` | `/api/v1/turns/{id}/decision` | 提交审批并继续 SSE |
| `POST` | `/api/v1/turns/{id}/cancel` | 请求取消活动轮次 |

`SessionRecord` 新增了 `title`。第一次有效提问后，后端截取问题内容生成标题；标题属于
会话元数据，不从模型额外生成，因此不会增加模型调用成本和等待时间。

历史消息通过 `HumanChatApplication.get_session_with_messages()` 一次性读取会话与消息，
避免 route 先加载会话、再为了历史消息重复加载同一份元数据。这个方法只返回
`HumanMessage` 和 `AIMessage` 的文本映射：

```python
@dataclass(frozen=True)
class ChatMessage:
    id: str
    role: Literal["user", "assistant"]
    content: str
```

它有意过滤 `ToolMessage`、系统提示词、审批内部状态和 `tool_events`。浏览器得到的是聊天
产品所需的信息，而不是 LangChain/LangGraph 的内部对象。

## 4. 为什么选用 SSE

本阶段的通信方向主要是“一次请求，服务端持续返回多个事件”。SSE 很适合这种场景：

- 建立在普通 HTTP 之上，反向代理和调试工具支持成熟；
- 后端可以逐个推送进度、结果和审批事件；
- 比 WebSocket 少一层连接协议和双向消息管理；
- 前端通过 `fetch()` 的 `ReadableStream` 就能消费 POST 响应。

这里没有使用浏览器原生 `EventSource`，因为 `EventSource` 只方便发起 GET，而聊天请求和
审批请求都需要携带 JSON POST body。SSE 是响应格式，不要求客户端必须使用
`EventSource`。

响应包含以下关键头：

```text
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no
X-Turn-ID: <turn id>
```

`X-Accel-Buffering: no` 用于提示 Nginx 等代理不要把事件攒成完整响应后再发送；
`X-Turn-ID` 让前端可以取消或审批当前轮次。CORS 的 `expose_headers` 同时增加了该响应
头，否则跨域前端无法在 JavaScript 中读取它。

当 15 秒内没有业务事件时，服务会发送 `heartbeat`。它可以维持长连接，并让中间代理
知道请求仍然活跃。

## 5. 事件协议及信息隐藏

浏览器事件协议集中在 `human_chat/conversation/protocol.py`，而不是散落在每个 route
中。当前公开事件包括：

| 事件 | 含义 |
| --- | --- |
| `turn.started` | 新轮次开始 |
| `turn.resumed` | 审批后的 Graph 恢复执行 |
| `turn.progress` | 粗粒度进度，如理解问题、获取信息、组织回复 |
| `message.completed` | 最终助手消息可展示 |
| `memory.saved` | 已确认并保存的长期记忆数量 |
| `review.required` | Graph 已暂停，等待用户确认 |
| `turn.completed` | 本轮正常完成 |
| `turn.cancelled` | 本轮已取消 |
| `turn.failed` | 本轮执行失败，返回安全的通用错误说明 |
| `heartbeat` | 连接保活 |

普通工具调用不会把工具名、参数、逐步结果直接展示在聊天界面。这样既避免把 Agent 内部
推理流程当成产品界面，也减少路径、项目内容或外部系统数据意外泄漏的风险。

高风险工具是例外：用户必须知道将要执行什么才能做出有效授权。因此
`review.required` 会返回原有 `ToolReviewRequest` 中已经脱敏的参数。敏感键对应的值在
进入审批模型时已递归替换为 `[REDACTED]`，前端不会接触原始凭据。

## 6. LangGraph 流式执行

`HumanChatApplication` 使用：

```python
graph.stream(
    graph_input,
    config={"configurable": {"thread_id": session.thread_id}},
    stream_mode=["updates", "values"],
    durability="sync",
    control=control,
)
```

两种 stream mode 的用途不同：

- `updates`：取得每个节点刚刚产生的增量，用来生成浏览器进度事件；
- `values`：取得完整状态快照，用来在结束或暂停时同步会话消息数和标题。

`durability="sync"` 要求 checkpoint 写入完成后再继续暴露结果。对聊天产品来说，稍微
增加一点写入等待，换来“前端已看到完成，但服务重启后状态却不存在”这一风险的降低，
是更合适的默认选择。

项目默认使用同步的 SQLite checkpointer，因此不能直接改成 `graph.astream()`。当前做法
是通过 `asyncio.to_thread()` 在工作线程执行同步 Graph，同时用线程安全的
`loop.call_soon_threadsafe()` 把事件送回 asyncio 队列：

```text
worker thread: graph.stream() -> call_soon_threadsafe(queue.put_nowait)
async event loop: queue.get() -> SSE response
```

这保证模型请求和 SQLite Graph 执行不会阻塞 FastAPI 的事件循环，也保持了现有同步
checkpointer 的正确生命周期。

## 7. 审批暂停与恢复

工具审批和长期记忆审批仍然是 Graph 节点，HTTP 层没有自行执行工具或保存记忆。

第一次流式调用遇到 `interrupt()` 后：

1. LangGraph 把当前状态写入 checkpoint；
2. `ConversationService` 解析 `__interrupt__`；
3. 轮次变为 `awaiting_review`；
4. SSE 发送 `review.required` 后正常结束；
5. 同一 session 仍保持占用，不能插入另一轮对话。

前端提交决定后，后端通过：

```python
Command(resume={"approved": True})
```

或长期记忆的：

```python
Command(resume={"accepted_texts": ["..."]})
```

从同一个 `thread_id` 恢复。客户端只提交候选项 ID，真正的记忆文本保存在服务端
`PendingReview` 中。后端会拒绝未知 ID，避免客户端篡改请求直接写入任意长期记忆。

## 8. 并发与取消策略

### 8.1 同一会话串行执行

`ConversationService` 使用 `_active_sessions` 保证一个 session 同一时间只有一个活动
turn。原因是同一个 LangGraph `thread_id` 上并发写 checkpoint 可能造成上下文覆盖、
消息顺序错乱或审批恢复到错误状态。

不同 session 可以并发执行，它们具有不同 thread id，不会互相阻塞。

### 8.2 协作式取消

每个运行中的 turn 都持有 LangGraph `RunControl`。收到取消请求或浏览器在执行中断开时，
调用：

```python
control.request_drain("user_cancelled")
```

这是协作式取消：Graph 在安全边界停止继续调度节点，而不是强制杀死正进行中的线程。
强杀线程可能让数据库事务、MCP 调用或 checkpoint 写入停在不确定状态，因此不适合成熟
服务。

模型 HTTP 调用本身不能被线程强制中断，所以新增
`HUMANCHAT_LLM_TIMEOUT_SECONDS`，默认 60 秒。它限制单次模型请求的最长等待，避免取消
或服务关闭永久挂起。

如果轮次正在等待审批，取消可以立即完成并释放 session；已经完成或失败的轮次再次取消
会返回 `409`，保持状态机语义明确。

## 9. 错误与状态设计

活动轮次状态如下：

```text
running -> awaiting_review -> running -> completed
   |             |
   v             v
cancelling    cancelled
   |
   v
cancelled

任意执行阶段发生未处理异常 -> failed
```

预期业务错误使用稳定错误码：

- `session_not_found`：会话不存在，HTTP 404；
- `session_busy`：同一会话已有活动轮次，HTTP 409；
- `turn_not_found`：轮次不存在或已超出内存保留范围，HTTP 404；
- `invalid_turn_decision`：当前不等待审批或提交内容非法，HTTP 409；
- `turn_already_finished`：结束后的轮次不能再次取消，HTTP 409。

执行中的内部异常只写入服务端日志，SSE 返回 `turn.failed` 和通用中文提示，不把异常堆栈、
文件路径或第三方服务响应泄漏给浏览器。

## 10. 进程生命周期

FastAPI lifespan 现在按以下顺序工作：

```text
打开 HumanChatApplication 资源
    -> 创建 ConversationService
        -> 接受请求
        -> shutdown() 请求活动 Graph 安全停止并等待退出
    -> 关闭 MCP bridge、memory resource 和 checkpointer
```

必须先停止活动轮次，再关闭底层资源。否则后台 Graph 线程可能在 SQLite 连接或 MCP bridge
已经关闭后继续访问它们，产生间歇性故障。

已结束的 turn 只在内存中保留最近 100 个，用于前端短期查询状态；会话和消息仍由
SessionRepository 与 LangGraph checkpoint 持久化。turn 状态不是第二套聊天数据库。
