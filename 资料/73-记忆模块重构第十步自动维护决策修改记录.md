# 第十步：从有依据的候选到可执行维护计划

## 1. 本步改变了什么

在 `memory/formation.py` 增加 `Decision`、`Review`、`FormationPlan` 和 `MemoryFormation.prepare`。第七步仅提取候选，本步才产生可提交的 `Mutation`。仍然不直接写主存储，便于第十三步先持久化计划、再执行和安全重试。

普通批次最多两次结构化模型调用：一次提取，一次结合原话进行语义复核和维护决策。没有候选时不调用第二次。这不是“三个模型独立核验”，也不声称模型能证明用户陈述的客观真实性。

## 2. 为什么不直接 add

**本步的重点是把“值得记的句子”转成“对某条现有认识做哪一种、哪几个字段的修改”，并确保模型提案无法跳过程序的存储规则。**

“我也喜欢Rust”可能是补充；“开发机改用Linux”是变化；“之前Windows记错”是纠错；“那个目标暂停”只改变状态。直接 add 会重复或冲突，直接覆盖会丢失范围、期限和正确历史。决策必须结合旧记录，但新断言的依据只能来自新用户原话。

## 3. 实现流程

```text
SourceBatch完整新原话/必要前文
  -> extract：候选、精确引用和可信来源
  -> 混合召回 + 同身份直取：提供维护对象
  -> Review：支持/暂缓/拒绝，选择操作与目标
  -> 程序检查：候选ID、字段权限、破坏性意图、目标存在及当前状态
  -> FormationPlan（尚未落库）
```

模型不能生成可信用户ID、证据时间、记录版本或操作ID。程序从来源和当前主记录填入这些值。操作ID由 `job_id + candidate_id` 稳定生成，重试同一计划不会变成新写入。

更新只允许 `fields` 是 `supplied_fields` 的子集；用户只说暂停，模型就算建议同时清空 deadline，也会被拒绝。`delete/forbid/retract` 必须与候选明确意图一致；不能将“忘记它”当作新的事实保存。纠错必须有纠错意图。

同一批次若有多个候选修改同一目标，后续候选暂缓，避免共享旧版本造成错误覆盖。本轮不添加复杂的多候选合并器；这项限制明确记入诊断，不静默覆盖。补充项可以独立 add，同一关系不是唯一键。

检索故障且已有记录时，不通过“没有找到”推导“肯定是新增”。模糊对象和证据不足由模型暂缓，程序也拦截不可用目标。所有诊断供开发者排查，不展示保存提示、不要求用户批准。

### 3.1 沿“项目暂停”走完一次 prepare

假设库存有 m1，第2版内容为“完成记忆模块 / 进行中 / 年底”，新消息 u2 是“HumanChat 那个目标先暂停”。流程可展开为：

| 阶段 | 实际产物 | 不该在这里做的事 |
| --- | --- | --- |
| extract | candidate-0；意图 change；supplied_fields=[state]；u2 引用 | 不凭空补一个新截止日 |
| recall + inventory | 混合召回相关内容，再读 m1 完整当前记录 | 不拿过期索引正文作为最新版本 |
| Review | supported / update / target=m1 / fields=[state] | 不把 supported 当写入成功 |
| 程序组装 | Mutation 带 expected_version=2、可信来源和稳定操作 ID | 不采用模型自报的版本号 |
| 返回 | FormationPlan.operations=[该操作] | 此函数不调用 apply、不保存记忆 |

后续后台任务先保存 FormationPlan，再调用 Service.apply；这是资料76的职责。把“决定”和“执行”拆开，才能在进程中断后重放同一份操作，而不是让模型重新想一份可能不同的更新。

### 3.2 第二次模型调用究竟多看了什么

`prepare` 组装的 payload 包括完整 source_batch、已锚定的 candidates、相关记录 records、持续禁记 policies 和检索 diagnostics。候选引文提供定位，完整原话提供限定条件，旧记录提供比较对象，三者不可互相替代。

例如原话“以后**代码审查**先说风险”，第一次提取漏掉范围，写成“所有回答先说风险”。如果第二次模型只回答 supported/reject，程序仍可能保存漏范围的候选。最终集成为此新增必填 `reviewed_assertion`：复核模型可以返回修正后的范围，而程序真正采用的是它。

```python
# 当前最终实现；reviewed_assertion 是第15步实测后补充的。
assertion = decision.reviewed_assertion
if not set(decision.fields).issubset(claim.supplied_fields):
    error = "unsupported_patch_fields"
elif assertion is None and decision.operation not in ("delete", "retract"):
    error = "reviewed_assertion_missing"
```

这没有保证第二个模型绝不出错；它解决的是“复核指出有问题，执行却仍用原错误结构”的接口缺陷。对于 update，复核也不能凭空增添新的可改字段，fields 必须是最初从新原话提取出的 supplied_fields 子集。若第一次漏掉一个应改字段，当前实现可能暂缓/漏改，而不是扩大权限猜测。

### 3.3 哪些信息来自模型，哪些由程序决定

| 信息 | 来源 |
| --- | --- |
| 语义支持程度、操作种类、候选目标 | 模型复核，再受程序集合/意图约束 |
| 用户 ID、证据时间、消息 ID | SourceBatch 中的可信来源 |
| target 是否仍存在、当前版本 | 本次读取的 inventory |
| 操作 ID | 程序用 job_id 与 candidate.id 生成 |
| 能否最终写入 | Service.apply 的版本、来源、禁记与回执检查 |

实际构造操作时的关键行（省略其他参数）是：

```python
Mutation(
    id=uuid5(NAMESPACE_URL, f"{job_id}:{candidate.id}").hex,
    expected_version=target.version if target and decision.operation != "forbid" else None,
    evidence=candidate.evidence,
)
```

UUID5 根据同一输入生成同一 ID；它解决身份稳定性，不提供时间顺序。只保证重放**同一已保存计划**时稳定；如果还没保存就重新调用模型，候选内容可能变化，因此持久化计划仍然必要。

### 3.4 为什么既在 prepare 检查，也在 apply 检查

prepare 检查的是“模型提出的操作在当时能否成立”。apply 检查的是“到现在真正要落盘时，条件是否还成立”。这段时间用户可能手动删除、另一个操作可能更新版本，所以存储边界不能省略后者。

它们没有各自重新调一次语义审核模型：prepare 处理 LLM 输出契约，apply 处理存储并发与数据政策。职责不同，不能把所有检查都上移后让 Repository 无条件覆盖。

### 3.5 几个真实取舍

“我也喜欢 Rust”可以新增，与 Python 共存；“不再用 Python，改用 Rust”可能更新。共享 subject/relation 不代表只有一个 value。

同批次若“暂停目标”和“期限改到明年”被提取为两条候选且都指向 m1，当前只接受首个目标操作，后一个记录 `multiple_changes_to_same_target_deferred`。这里的 defer **只是诊断，没有另建一个保证会再执行的待办**。它避免覆盖，却可能漏掉第二个变化；将来应以实际案例决定是否增加受限合并或重新规划。

当 recall 有故障/不完整诊断且库存非空时，程序拒绝 add，避免把“没查全”当“没有重复”。即便索引完整，有限 top-k 也不是数学上的全库语义不存在证明；明确 identity 和模型对比只是降低风险，不能承诺没有语义重复。

## 4. 关键代码怎么读

- `prepare` 的前半段只收集证据和旧记录。
- `Review` 是模型输出契约，`structured_call` 在外部输出边界解析。
- 循环中先确定 `error`，不合法提案记录原因后跳过。
- 合法提案才构造 `Mutation`，目标版本来自 inventory，而不是让模型填写。
- `MemoryService.apply` 仍承担最终存储边界上的版本、时序、禁记与幂等检查。这不是重复语义审核，而是防止计划生成后主记录发生变化。
