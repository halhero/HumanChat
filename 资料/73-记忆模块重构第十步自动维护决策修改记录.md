# 第十步：从有依据的候选到可执行维护计划

## 1. 本步改变了什么

在 `memory/formation.py` 增加 `Decision`、`Review`、`FormationPlan` 和 `MemoryFormation.prepare`。第七步仅提取候选，本步才产生可提交的 `Mutation`。仍然不直接写主存储，便于第十三步先持久化计划、再执行和安全重试。

普通批次最多两次结构化模型调用：一次提取，一次结合原话进行语义复核和维护决策。没有候选时不调用第二次。这不是“三个模型独立核验”，也不声称模型能证明用户陈述的客观真实性。

## 2. 为什么不直接 add

“我也喜欢Rust”可能是补充；“开发机改用Linux”是变化；“之前Windows记错”是纠错；“那个目标暂停”只改变状态。直接 add 会重复或冲突，直接覆盖会丢失范围、期限和正确历史。决策必须结合旧记录，但新断言的依据只能来自新用户原话。

## 3. 实现流程

```text
SourceBatch完整新原话/必要前文
  -> extract：候选、精确引用和可信来源
  -> 混合召回 + 同身份直取：提供维护对象
  -> Review：支持/暂缓/拒绝，选择操作与目标
  -> 程序检查：候选ID、字段权限、破坏性意图、目标存在及当前状态
  -> FormationPlan（尚未落库）
```

模型不能生成可信用户ID、证据时间、记录版本或操作ID。程序从来源和当前主记录填入这些值。操作ID由 `job_id + candidate_id` 稳定生成，重试同一计划不会变成新写入。

更新只允许 `fields` 是 `supplied_fields` 的子集；用户只说暂停，模型就算建议同时清空 deadline，也会被拒绝。`delete/forbid/retract` 必须与候选明确意图一致；不能将“忘记它”当作新的事实保存。纠错必须有纠错意图。

同一批次若有多个候选修改同一目标，后续候选暂缓，避免共享旧版本造成错误覆盖。本轮不添加复杂的多候选合并器；这项限制明确记入诊断，不静默覆盖。补充项可以独立 add，同一关系不是唯一键。

检索故障且已有记录时，不通过“没有找到”推导“肯定是新增”。模糊对象和证据不足由模型暂缓，程序也拦截不可用目标。所有诊断供开发者排查，不展示保存提示、不要求用户批准。

## 4. 关键代码怎么读

- `prepare` 的前半段只收集证据和旧记录。
- `Review` 是模型输出契约，`structured_call` 在外部输出边界解析。
- 循环中先确定 `error`，不合法提案记录原因后跳过。
- 合法提案才构造 `Mutation`，目标版本来自 inventory，而不是让模型填写。
- `MemoryService.apply` 仍承担最终存储边界上的版本、时序、禁记与幂等检查。这不是重复语义审核，而是防止计划生成后主记录发生变化。

## 5. 验证

执行 `python -m pytest tests/test_memory_formation.py -q -p no:cacheprovider --basetemp .validation-step10-20261015`：2项通过。新增用例验证两次调用形成计划、同计划重放不重复写入、仅提供状态时不能清空期限。模型为脚本替身；真实模型理解能力留到最终合成数据验证。

## 6. 仍待完成

自动维护计划还没有进入应用后台，也没有替换旧用户确认节点；这些集中在第十三、十四步完成。相同目标的多候选批次暂不自动合并；语义复核仍可能出错，证据、版本和暂缓机制降低风险，但不能宣称零误判。
