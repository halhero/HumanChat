# 单轮记忆来源有界登记修改记录

日期：2026-11-11。

## 1. 本步解决的问题

修改前，每次 Graph 一轮执行结束后，应用都会取得完整 checkpoint snapshot，然后执行：

```python
messages = snapshot.values.get("messages", [])
sources = history_sources(messages, ...)
```

即使正常场景最终只需要登记当前 `input_source`，程序也会先把当前 thread 中全部 Human/AI 消息转换成 `SourceMessage`，再遍历转换结果寻找当前来源。

Worker 处理 Job 时还会再次把同一 checkpoint 的完整消息历史转换一次，然后才按 token 预算截取少量上下文。

因此长会话每轮都会重复处理此前所有消息，累计转换成本可能接近平方增长。

## 2. 本步修改边界

本步只优化正常轮次结束后的来源登记和 Worker 的上下文读取，没有修改：

- 启动时的崩溃恢复扫描；
- MemoryJobs 数据库结构；
- 记忆提取、Review 和 mutation；
- LangGraph 消息状态；
- 回答记忆召回；
- token 预算数值。

启动扫描仍暂时使用 `_reconcile_memory_sources()`，由下一步单独替换，避免一次提交混合两个问题。

## 3. 正常轮次如何改为单来源登记

Graph state 已经保存当前轮次的：

```python
snapshot.values["input_source"]
```

因此新的 `_enqueue_memory_source()` 不再从全部历史中反向寻找当前来源，而是直接：

```text
读取 input_source
   ↓
确认 user_id 与 session_id
   ↓
检查消息尾部是该 HumanMessage + 一个 AIMessage
   ↓
使用当前 checkpoint_id 登记一个 Job
```

只检查消息尾部的原因是 Graph 完整结束时会把本轮用户来源和最终助手回答作为最后一对 conversation messages 写入 state。工具审批中断时，这一对消息尚未完成，因此不会提前形成记忆 Job。

正常轮次登记不再调用 `history_sources()`，也不再遍历旧消息。

## 4. Worker 如何有界读取历史上下文

新增 `recent_history_before(messages, before_id, budget)`，用于在指定来源之前选取上下文。

算法从当前来源附近反向读取：

```text
从列表尾部找到当前 source ID
   ↓
向前读取一个完整用户轮次
   ↓
计算加入后的 token 数
   ↓
超过 memory_history_tokens 时立即停止
```

它与旧逻辑保留相同的“按完整用户轮次保留历史”语义，但不会先调用 `history_groups()` 构造全部历史分组。

Worker 的新流程是：

```text
从 checkpoint.input_source 读取当前 SourceMessage
   ↓
核对 source_id 与 Job
   ↓
反向选择 token 预算内的原始消息
   ↓
只把选中的消息转换为 SourceMessage
   ↓
构造 SourceBatch
```

如果预算只允许最近一个轮次，程序只访问和转换尾部附近的消息，不会处理几百个更早的轮次。

## 5. 为什么不使用固定消息条数

没有采用：

```python
messages[-20:]
```

因为消息长度差异很大，20 条短消息和 20 条长消息的 token 成本可能相差数十倍。项目已经使用 `memory_history_tokens` 表达上下文预算，本步继续按 token 和完整轮次选择，避免引入第二套不一致规则。

## 6. 状态检查保持在哪里

必要检查集中在两个真实边界：

- Graph checkpoint 到 Job：核对来源所属用户、会话、时间和回答是否完成；
- Job 到 SourceBatch：核对 Job 的 `source_id/user_id` 与 checkpoint 中的来源一致。

没有为内部消息增加多格式 fallback，也没有捕获异常后静默跳过身份冲突。

## 7. 方法职责变化

| 修改前 | 修改后 |
| --- | --- |
| `_enqueue_memory_sources(..., all_completed=False)` 同时处理正常轮次与启动补偿 | `_enqueue_memory_source()` 只登记当前轮次 |
| 正常轮次先转换全部历史 | 直接读取 `input_source` |
| Worker 先转换全部历史再预算裁剪 | 先按预算反向选择，再转换少量消息 |
| 启动补偿与正常登记共用复杂分支 | 启动补偿暂时独立为 `_reconcile_memory_sources()` |

这种拆分也为下一步删除启动全会话扫描提供了清晰入口。

## 8. 定向测试

本步测试覆盖：

- 正常完成的轮次直接登记已知 source；
- 登记路径即使禁止调用 `history_sources()` 仍能完成；
- 旧历史不会在正常登记阶段被转换；
- 400 条历史消息存在时，有界读取只访问尾部少量消息；
- 最近完整用户轮次保持成组；
- 原有后台记忆形成、持久 Job 和 Graph 流程继续通过。

## 9. 未处理事项

本步刻意保留了启动时 `_reconcile_memory_sources()` 对已有会话的全量恢复扫描。下一步会通过持久 pending source 登记替代它。

LangGraph `get_state()` 返回的 state 本身仍包含完整 `messages` 列表；本步消除的是应用层对完整列表的重复遍历、转换和复制。若未来 checkpoint 反序列化本身成为瓶颈，需要单独调整会话状态存储，不应与本次来源登记修改混在一起。
