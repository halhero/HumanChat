# 第十五步：集成验收、真实调用修复与学习索引

日期：2026-10-15。正式分支：`codex/memory-approved`。起点：`7998476`。

## 1. 本轮完成范围

本轮按第0篇路线，连续、分步实现“长期记忆形成与维护”和“记忆读取与上下文构建”。每步代码和资料独立提交并推送，没有把旧撤回分支整批恢复，也没有合并 master。

这代表本轮记忆核心链路完成，不代表整个 HumanChat 项目已经商用成熟，更不代表语义零误判、分布式一致性或多用户部署已解决。

## 2. 现在的完整数据流

### 2.1 用户说话和记忆保存

```text
HTTP输入 -> new_source：用户/会话/稳定ID/接收时间
         -> Graph回答与工具流程
         -> finalize_reply：提交原用户消息和助手回复
         -> finish_turn -> 前台结束
                      -> Application登记持久后台任务
                      -> checkpoint原话 + 必要前文
                      -> 提取候选 -> 引文来源检查
                      -> 查旧记忆 -> 完整原话语义复核与维护决策
                      -> 先保存FormationPlan
                      -> MemoryService.apply
                      -> 主记录/版本/历史/来源/回执
                      -> 索引同步 -> 完成并清空任务计划正文
```

前台不执行提取和保存模型调用，不发保存数量通知，不等待批准；危险工具仍有独立确认。自动处理不足以确定的候选会暂缓，不为后台记忆追问用户。

“先保存计划”解决进程中断后的幂等重放；启动扫描已完成 checkpoint 来源，弥补主 Graph 提交与队列登记之间的间隙。它们不是同一事务，不宣称跨库原子提交。

### 2.2 下次回答前读取

```text
当前问题 + 近期对话
  -> BM25词法入口 + 真实embedding语义入口 -> RRF融合主题候选
  -> 当前有效目录独立进入任务背景候选
  -> 按约束/指导/背景/事实/历史判断适用性
  -> needed/optional/exclude/uncertain；必要依赖组成bundle
  -> 仅保存ID/父版本/用途引用
  -> 每次模型调用重新回源确认版本、删除与有效状态
  -> 角色提示 + 完整记忆组合 + 历史 + 当前问答/工具结果 + 工具Schema
  -> 计算输入预算并预留输出 -> 真实invoke
```

因此非主题指导不会先被关键词 top-k 漏掉，再被主题精排再次淘汰；是否采用由任务适用性决定。目录入口也不是全量塞进最终回答模型，最终请求仍经过选择、分组和预算。

### 2.3 四种状态数据各管什么

| 对象 | 权威/派生 | 保存位置和职责 |
| --- | --- | --- |
| 长期记忆记录 | 权威 | 原 JSON 或 LangGraph Store，Service 管业务，Repository 管存取 |
| 语义索引 | 可重建派生 | LangChain InMemoryVectorStore 与本地 `.index.json` 快照 |
| 后台任务 | 执行状态 | `.jobs.sqlite`，临时确定操作和持久来源引用，完成后清空计划 |
| 聊天与前台执行 | 权威聊天状态 | LangGraph checkpointer，不借它伪装后台任务队列 |

## 3. 本步真实运行发现的问题与修复

### 3.1 新认识缺核心内容

真实模型可能把“完成记忆模块”塞进主体/关系，然后 `value=null`。原存储检查正确拒绝了不完整 add，但仅有 Python 类型正确不能让整个流程可用。

在 `models.py` 为 Assertion 的主体、关系和值加入明确字段说明和非空边界；在 `formation.py` 说明新的完整认识必须有 value，局部状态更新才允许缺原目标内容。没有用候选 text 自动补 value 掩盖结构问题，也没有放宽服务保存条件。

### 3.2 来源时间和适用范围被模型混淆

实际样例曾把接收时间写进 effective_time，并漏掉“检查代码时”的范围。这不是可忽略的格式问题，会放大偏好适用范围。

第二次复核现在必须返回 `reviewed_assertion`：明确区分来源时间与事实时间，依据完整原话修复遗漏范围，再构造 Mutation。用户身份仍由程序填入，原始引文与时间仍来自可信 SourceBatch。更新只有指定 fields 会提交，不能用整个复核结构覆盖未授权字段。

这个复核仍由同一模型完成，不是独立事实证明。程序能保证来源、版本、操作权限和字段集合，不能数学证明所有语义都正确。本步真实样例及定向测试证明了所检查的范围/时间情形，不扩大为普遍准确率结论。

### 3.3 空候选时没有结构化结果

浏览器真实对话中，辅助模型曾返回 None；后续 JSON 尝试捕获到 `LengthFinishReasonError`，usage 中 reasoning_tokens 耗尽了原2048输出限额。根因是当前 Qwen 的思考输出占用了结构化结果预算，不应把 None 当成“没有记忆”。

- `llm.py` 的 `create_chat_model(..., for_memory=True)`：当前 Qwen 记忆辅助调用明确关闭思考，使用独立输出上限。
- `tokens.py`：JSON mode，提示中给出真实 Schema，用 LangChain/Pydantic 解析，解析不合法就失败，不静默变空列表。
- `config.py/.env.example`：`memory_output_tokens=4096` 可配置；聊天输出预留必须小于总窗口。

当前 `qwen3.5-flash` 支持的是相应非思考 JSON Object 模式；没有强行启用其未列出的严格 JSON Schema 模式，也没有添加多个格式之间的自动兜底。模式说明依据[百炼结构化输出文档](https://help.aliyun.com/zh/model-studio/qwen-structured-output)。不同服务/模型需要匹配实际支持能力。

JSON mode 只保证 JSON 格式，不保证所有枚举和语义。实际还发现一次 verdict 被写成 update，程序拒绝了它；随后在字段说明与提示中明确 verdict 是依据判断，operation 才是变更动作。没有把错误枚举强制转为 supported。后台保留有限重试，不无限消耗 tokens。

### 3.4 关闭自动提取时已有任务仍可能运行

索引仍需后台同步，但自动形成关闭后，不应继续处理以前的待办任务。`MemoryWorker.enabled` 控制处理，保留队列表和删除监听，只暂停形成/写入。重新启用后可继续待办，不能靠故意让 formation=None 报错来暂停。

### 3.5 索引尚未覆盖全部记录

索引启动重建期间，“查询没命中”并不意味着库内没有记录。`MemoryIndex.covers` 检查当前视图覆盖，Retriever 报 `semantic_projection_incomplete`；维护决策不会在降级状态下将空结果当作新增证据。单条旧命中还要核对父版本，最终请求再次回源。

### 3.6 旧保存选项不应混入工具批准

`ReviewDecisionRequest` 使用 extra=forbid，过期的 selected_item_ids 请求得到422。前端已改为只发送 approve/reject。工具确认恢复、执行和取消仍走 LangGraph，不被记忆改造绕过。

### 3.7 配置和说明同步

`.env.example` 列明新增预算、embedding 和开关；真实 `.env` 未修改和提交。README 更新目录、前后台链路、任务恢复、语义降级、单进程要求和删除范围，移除“记忆仍需用户批准”的旧说明。第0篇补记用户后来要求连续实施的授权，原基线记录保留。

### 贯穿案例自查

- 为什么“暂停”不清空期限？只提交明确支持的 fields，Service 按字段合并。
- 为什么再确认不是不写？它需要推进来源水位，防止更旧后台状态覆盖。
- 为什么代码审查指导能保留？独立背景入口，加用途适用性，不是统一主题排名。
- 为什么向量命中不能直接拼提示词？索引不是权威数据，可能落后于更正或删除。
- 为什么不用用户批准记忆？本轮要求无感；安全靠来源、受限操作、幂等、版本和暂缓，不靠弹窗。

## 6. 尚待改进与未验证范围

1. 当前仅适合单用户、单后端进程；namespace不是认证系统，不支持多个后台worker协同写。PostgreSQL适配保留，但没有真实数据库服务验收。
2. 语义复核和适用性仍可能误判；同义禁记主要依赖复核识别，确定性边界针对规范身份，不承诺任意措辞都能完美识别。
3. 大目录/超长原话可能超处理预算；明确诊断和暂缓，不无限截断/追加模型调用。任务重试最多3次，持续失败进入failed；当前没有专门运营重试界面。
4. 同一批次多个候选修改同一目标，后续项会暂缓，未构建复杂自动合并器。
5. 后台最终一致，下一轮可能先于保存完成；关键约束过大或当前工具结果过大时明确预算错误，不静默删约束或切断工具协议。
6. 删除覆盖本模块主记录正文、索引与相关计划，不覆盖原始对话、旧checkpoint、外部服务留存和备份；不承诺取证级擦除。
7. 本轮未重新验证STT/TTS硬件/远程服务或真实MCP服务，也未改动这些模块和角色配置。已有相关检查的结果不等于本次真实外部调用。
8. 没有声称干净机器安装已验收；使用现有Python环境和桌面Node运行时。用户原有 `.idea/.name`、`AGENTS.md`、`docs/` 保留在工作区，不随本轮提交。
