# 记忆模块重构第六步：删除与持续禁记

日期：2026-10-15。前置资料68；前置提交 `6c89626`。

## 改了什么

业务删除不再仅调用仓储物理删除：Service 清除当前正文、结构、证据、上下文引用和历史正文，保留最小来源身份、内容指纹和操作摘要回执。已删除记录不进入 load。底层 Repository.delete_item 仍是低层能力，不等同于完整业务删除。

Mutation 增加 delete 与 forbid。delete 针对确定记录及版本；forbid 保存主体/关系/范围的禁记身份，清除匹配认识，并阻止后续自动写入同一身份。禁记规则不保存原事实值，不能拿它回答用户事实。

## 为什么这样改

物理删除后没有任何标记，旧任务换个操作 ID 就可能重新新增。回执阻止同一操作重复，指纹与消息时间阻止已删除认识的旧来源重放，两者职责不同。

持续禁记与一次删除不同：旧来源保护允许后来明确的新表达；forbid 对新来源也生效。程序按规范化身份检查，不用“再调一次 LLM 就算新证据”绕过。

## 数据流与例子

```text
一次删除 -> 正文清除 + 最小抑制标记 -> 旧任务不恢复
持续禁记 -> 同身份内容清除 + blocked_identity -> 新来源也不自动写入
```

用户删除目标后，旧 seed 操作重试返回 already_applied，但不恢复正文；另一个旧任务的相同认识返回 deleted_source。用户明确禁止继续保存某范围认识，后来自动候选即使来源更新，仍返回 forbidden_identity。

本步5项直接相关检查通过，覆盖JSON/真实 Store 的删除重放、持续禁记及原有稳定 ID 删除行为。没有跑全量或重新验证所有前端功能。

## 还没完成什么

本步先完成主存储规则。第8步补索引同步，第13—14步补相关后台任务载荷清理与完整删除传播，不能现在就宣称派生数据已全部删除。

禁记身份的不同自然语言说法仍需要形成/决策阶段对齐；程序的身份相等和指纹不是通用语义等价判断。第一版优先明确范围，不能判断就暂缓，不能宣称所有类别表达都可靠识别。手动新增属于显式管理，与自动形成通道不同，不把普通聊天当成解除禁记。

原始聊天、既有检查点、备份和供应商留存不在本次彻底遗忘承诺内。持续禁止的解除尚无独立管理入口，本轮不偷偷自动解除。
