# 第十二步：把上下文真正装进 Graph 请求

## 1. 修改内容

- 新增 `memory/request.py`：上下文引用序列化、近期历史选择、完整模型请求装配。
- `graph.py` 增加 context_builder 依赖，初次回答、工具后回答、工具上限回答共享请求装配函数。
- `schemas.py` 增加 memory_context，仅保存记录引用、父版本、用途和组合信息，不复制另一份权威正文。
- `config.py/llm.py` 增加并使用聊天上下文上限与输出 token 上限。
- 修复工具达到上限后的悬空 tool_call：为未执行的每个调用补 ToolMessage，然后生成总结。

## 2. 为什么预算必须算完整请求

只控制记忆字符串长度无法保证请求可用：工具 JSON Schema、角色提示、长历史和本轮工具输出都占上下文。`assemble_request` 统一估算 messages、tools 和协议余量，并从总窗口扣掉输出预留。

默认总窗口32000、输出2048，可通过 `HUMANCHAT_CHAT_CONTEXT_TOKENS/HUMANCHAT_CHAT_OUTPUT_TOKENS` 配置。估算使用 cl100k_base 乘1.25的保守代理，不是百炼模型的精确分词器；配置必须小于实际模型支持窗口并留余量。

## 3. 关键流程

```text
prepare_context -> 按用途选择 -> 只存ID/父版本/组合
每次模型调用 -> 主存储重新读取 -> 验证当前版本与状态
            -> 整组装配关键约束/必要背景/可选内容
            -> 剩余预算加入近期完整对话组 -> invoke
```

重新读取解决“选择完成后用户删除/后台更新”的陈旧上下文问题。版本改变时整组移除并留诊断，不把旧正文继续交给模型。历史记录只有 history 用途可装入。

组合不可拆分，关键约束不能只截取一半。装不下关键组合就抛明确预算错误，不悄悄忽略约束。非关键组合装不下会记录省略原因。历史按完整用户轮次从最近向前保留，不修改 checkpoint 中完整对话。本轮工具调用和结果不可切断，单独已超预算就报错，不破坏协议凑请求。

## 4. 工具上限关联修复

既然本步统一所有模型入口，就检查了上限分支。旧代码把带 tool_calls 的助手消息直接交给无工具总结模型，缺少对应 ToolMessage，服务端可能拒绝。现在补未执行的错误结果，明确未执行，既不调用工具，也不伪造成功。

## 5. 验证

定向执行 request 用例及 Graph 的直接回答/工具结果用例：3项通过；再执行新增的 Graph 上下文接线用例：1项通过。证明选中正文确实出现在实际 invoke 输入中、删除后引用失效、整体估算在限额内、超长当前输入明确失败。没有在本步重复运行全量测试。
