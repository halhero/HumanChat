# 第十二步：把上下文真正装进 Graph 请求

## 1. 修改内容

- 新增 `memory/request.py`：上下文引用序列化、近期历史选择、完整模型请求装配。
- `graph.py` 增加 context_builder 依赖，初次回答、工具后回答、工具上限回答共享请求装配函数。
- `schemas.py` 增加 memory_context，仅保存记录引用、父版本、用途和组合信息，不复制另一份权威正文。
- `config.py/llm.py` 增加并使用聊天上下文上限与输出 token 上限。
- 修复工具达到上限后的悬空 tool_call：为未执行的每个调用补 ToolMessage，然后生成总结。

## 2. 为什么预算必须算完整请求

**本步的验收对象从“选择器选了哪些记忆”变成“回答模型实际收到什么”。** 中间还隔着版本回查、预算、工具消息和历史，如果不检查真实 invoke 输入，前面的选择做对了也可能在最后丢掉。

只控制记忆字符串长度无法保证请求可用：工具 JSON Schema、角色提示、长历史和本轮工具输出都占上下文。`assemble_request` 统一估算 messages、tools 和协议余量，并从总窗口扣掉输出预留。

默认总窗口32000、输出2048，可通过 `HUMANCHAT_CHAT_CONTEXT_TOKENS/HUMANCHAT_CHAT_OUTPUT_TOKENS` 配置。估算使用 cl100k_base 乘1.25的保守代理，不是百炼模型的精确分词器；配置必须小于实际模型支持窗口并留余量。

## 3. 关键流程

```text
prepare_context -> 按用途选择 -> 只存ID/父版本/组合
每次模型调用 -> 主存储重新读取 -> 验证当前版本与状态
            -> 整组装配关键约束/必要背景/可选内容
            -> 剩余预算加入近期完整对话组 -> invoke
```

重新读取解决“选择完成后用户删除/后台更新”的陈旧上下文问题。版本改变时整组移除并留诊断，不把旧正文继续交给模型。历史记录只有 history 用途可装入。

组合不可拆分，关键约束不能只截取一半。装不下关键组合就抛明确预算错误，不悄悄忽略约束。非关键组合装不下会记录省略原因。历史按完整用户轮次从最近向前保留，不修改 checkpoint 中完整对话。本轮工具调用和结果不可切断，单独已超预算就报错，不破坏协议凑请求。

### 3.1 为什么 Graph 只保存引用，不保存选中的正文

资料74得到 `MemoryContext` 后，`context_references()` 将它转成可以进入检查点的字典。每项只留下：

```python
{"id": c.view.id, "parent_version": c.view.parent_version, "purpose": d.purpose}
```

例如选择了 m1@3；用户在工具审批等待期间把 m1 删除。如果 Graph 保存一份已经拼好的提示词，下次恢复时可能继续用旧正文。现在 `assemble_request` 每次调用模型前重新读取 inventory，并检查引用是否还存在、父版本是否一致、状态是否合法。

检查失败会整组跳过，记录 `context_changed_since_selection`。这能避免继续使用已经失效的副本；当前实现**不会自动对新版本重做用途判断**，即使该组曾是 critical 也会因失效被跳过。因此它提供的是防陈旧使用，而不是“所有任务约束一定始终完整”。将来需要更强一致性时，应重新选择而非盲目替换正文。

### 3.2 实际装配顺序

在 [request.py](../human_chat/memory/request.py) 中可以按以下顺序读：

1. 将工具定义转换为真实工具 Schema，计算输入额度 `chat_context_tokens - chat_output_tokens`。
2. 先检查角色提示、本轮消息、已有工具调用/结果、工具定义是否独立装得下。装不下即失败。
3. 回源后的记忆组按 critical、其他 required、optional 顺序尝试加入。
4. 用剩余空间从最近向前加入完整历史轮次。
5. 返回真实消息列表和省略诊断，交给 `invoke`。

`required` 在当前实现中是优先级，不是不可删除承诺；非 critical 的 required 组装不下仍会被省略。critical 组只在通过当前性检查后，才获得“预算不足则报错、不默默裁切”的保护。

例如用一组**教学数字**：总窗口6000，输出预留1000，输入可用5000；固定输入估算3200，关键组600，其他背景900，加协议余量后仍可能装下；再加700的历史就可能超预算。程序会保留记忆组，舍弃放不下的旧历史，而不是把每段末尾随意切掉。

实际容量判断如下：

```python
messages = request(records, previous)
return payload_tokens({
    "messages": [m.model_dump(mode="json") for m in messages],
    "tools": schemas,
}) + 128 <= available
```

这里计算的是**序列化后的完整请求估计**，不是单个 text 长度；128是额外余量。tokenizer 是代理，不能保证与供应商线上编码完全一致，也不是服务端返回的实际 usage。

### 3.3 为什么整组处理，而不截取前几百字

“只有代码审查时先给风险结论”如果被裁掉“只有代码审查时”，剩下的偏好就扩大范围。当前把一条 MemoryView 的正文、结构、时间状态一起放进 payload；同 bundle 的条目还共同试算。

```python
if fits([*selected, *records], []):
    selected.extend(records)
elif bundle["critical"]:
    raise MemoryBudgetError("Applicable critical memory bundle cannot fit without losing its constraints")
else:
    diagnostics.append("memory_bundle_omitted_for_budget")
```

这是一种简单的分级贪心装配，不是数学最优的组合算法。相同优先级内延续已有顺序，可能不能装下最多有用信息；当前优先可解释、整组语义完整，暂不增加复杂优化器。

### 3.4 两种历史与本轮工具消息怎样处理

`recent_history` 给用途判断/形成提供有限前文；`assemble_request` 在最终剩余空间中再选择回答所需历史。二者用途和预算不同，不是同一段内容被重复加入请求。

`history_groups` 以 HumanMessage 开启一组，把其后的助手/工具消息放在同组，从最近一组向前加入；放不下就停止，避免留下孤立回答。checkpoint 里的完整历史没有被删除。

本轮 `current` 则作为完整固定输入，可能包含 user -> AI tool_calls -> ToolMessage -> AI 的多步序列。它不能像旧历史一样任意切半。工具结果过大时目前明确失败，没有偷偷截断工具 JSON；将来应在工具输出边界设计有语义的摘要或分页。

### 3.5 Graph 的三个入口怎样统一

在 [graph.py](../human_chat/graph.py) 中，`prepare_context` 选择一次本轮用途；内部 `build_request` 统一调用 assemble_request。首次 `call_agent_model`、工具返回后再次 `call_agent_model`、达到上限时 `generate_limit_reply` 都经它装配。这样不会出现普通回答用新检索、工具后回答又回到全量 memory_prompt 的两套行为。

## 4. 工具上限关联修复

既然本步统一所有模型入口，就检查了上限分支。旧代码把带 tool_calls 的助手消息直接交给无工具总结模型，缺少对应 ToolMessage，服务端可能拒绝。现在补未执行的错误结果，明确未执行，既不调用工具，也不伪造成功。

例如 AI 声明要调用 id=call-7，却因达到上限没执行，仍需对应 `ToolMessage(tool_call_id="call-7", content="...未执行...")` 来闭合协议。它报告的是未执行结果，不是取消工具权限审核，也没有调用真正的外部工具。
