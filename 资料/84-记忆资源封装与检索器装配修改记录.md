# 记忆资源封装与检索器装配修改记录

日期：2026-11-11。

## 1. 本步修改范围

本步只调整长期记忆资源的创建位置和对外接口：

- `open_memory_resource()` 内部创建 index store、service 和 retriever；
- `MemoryResource` 对外提供 `service` 与 `retriever`；
- 应用工厂不再取得底层 index store；
- SQLite、memory、PostgreSQL 三个后端沿用原生命周期。

本步没有修改索引表、检索算法、记忆数据、mutation、formation、prompt 或 catalog 行为。

## 2. 原来的资源暴露问题

旧的 `MemoryResource` 结构是：

```python
class MemoryResource:
    service: LongTermMemoryService
    search: MemoryIndexReader
    backend: str
    persistent: bool
```

应用工厂随后执行：

```python
retriever = MemoryRetriever(memory.search, settings.memory_recall_limit)
```

这意味着高层应用需要知道：

1. 长期记忆使用一个底层索引对象；
2. `MemoryRetriever` 应如何构造；
3. recall limit 应在何处注入；
4. service 和 retriever 必须共享同一个索引对象。

这些都属于记忆基础设施的装配细节，不是应用层需要操作的业务接口。

## 3. 新的 MemoryResource

修改后的结构是：

```python
class MemoryResource:
    service: LongTermMemoryService
    retriever: MemoryRetriever
    backend: str
    persistent: bool
```

它暴露两个业务角色：

- `service`：按 ID 读取权威记忆并执行已经形成的 mutation；
- `retriever`：根据查询从索引投影召回候选。

底层 repository 和 index store 都不再作为资源字段提供给应用层。

## 4. 新的依赖装配流程

三个后端都在 `open_memory_resource()` 内遵循同一顺序：

```text
创建 repository
      ↓
创建一个 index store
      ↓
index store 作为 MemoryIndexWriter 注入 service
      ↓
同一个 index store 作为 MemoryIndexReader 注入 retriever
      ↓
MemoryResource 只携带 service + retriever
```

具体关系如下：

```text
                       ┌─ LongTermMemoryService
repository ────────────┤       │
                       │       └─ MemoryIndexWriter
                       │
一个 index store ──────┤
                       │
                       └─ MemoryRetriever
                               └─ MemoryIndexReader
```

这里的 Reader 和 Writer 是同一个具体对象的两种接口视角，不是两份 store，也不会产生两份索引。

## 5. 三种后端的处理

### 5.1 SQLite

- `SqliteMemoryRepository` 保存完整主记录；
- `SqliteMemoryIndexStore` 保存持久检索投影；
- service 与 retriever 共享该 store；
- 退出时先关闭 index store，再关闭 repository。

### 5.2 Memory

- `LangGraphMemoryRepository(InMemoryStore())` 保存进程内主记录；
- 无文件路径的 `SqliteMemoryIndexStore` 保存进程内检索投影；
- service 与 retriever 共享该 store；
- 退出时关闭进程内 SQLite 连接。

### 5.3 PostgreSQL

- `LangGraphMemoryRepository(PostgresStore)` 保存主记录；
- `PostgresMemoryIndexStore` 保存 PostgreSQL 检索投影；
- 两个业务对象共享该 index store；
- 原有 `PostgresStore` context manager 和 index store 的关闭顺序保持不变。

## 6. 应用层如何简化

应用工厂删除了自行创建 `MemoryRetriever` 的代码，直接使用：

```python
memory.retriever
```

调用关系变为：

- `MemoryContextBuilder(memory.retriever, ...)`
- `MemoryFormation(..., memory.retriever)`

Graph 仍只接收 `memory.service` 和已装配的 context builder。应用层不再访问 index store，也不需要理解 Reader/Writer 如何共享实例。

## 7. 生命周期为什么保持不变

index store 仍在 `open_memory_resource()` 内创建，并由同一个 context manager 的 `finally` 关闭。改变的只是 retriever 的创建位置，不是资源所有权：

```text
进入 context -> 创建连接和业务对象
使用 resource -> service/retriever 共享连接
退出 context -> 停止使用业务对象并关闭连接
```

没有把 retriever 延迟到每次请求，也没有创建第二个 index store、manager 或 facade。

## 8. 定向验证

本步验证聚焦于资源装配和应用调用：

- SQLite resource 能启动、写入、检索并关闭；
- memory resource 能启动、写入、检索并关闭；
- service 的 writer 与 retriever 的 reader 是同一个 store 实例；
- 应用启动后 context builder 使用 `memory.retriever`；
- formation 使用同一个 `memory.retriever`；
- 后台记忆形成后的索引状态仍可通过 retriever 观察；
- PostgreSQL store 和资源模块可正常导入；
- 项目中不再存在 `memory.search` 或 `_memory.search` 调用；
- Ruff 和差异检查通过。

## 9. 未改变和未处理的内容

本步没有修改：

- `current_documents()` 的全量轻量目录读取；
- `task_background_catalog`；
- 词法、语义、identity 召回；
- 召回数量和排序；
- 主数据库或索引数据库 schema；
- 记忆保存和版本历史语义。

PostgreSQL 真实连接仍需要外部可用的 PostgreSQL + pgvector 环境，本步只处理现有装配代码，不引入模拟后端或额外兼容层。
