# 记忆模块重构第一步：消息来源统一

日期：2026-10-15。前置资料：63；前置提交：`5ca2fcc`。

## 1. 本步改了什么

新增 `human_chat/messages.py`，集中表达消息的 ID、归属、会话、角色、原文及接收时间。Application 接收问题时创建来源，Graph 在模型输入与最终历史中使用同一个用户消息 ID。`schemas.ChatState.input_source` 让该来源进入检查点。

本步仍保留原有记忆提取和审核，尚未切换无感保存。没有变更角色、工具、语音或前端协议。

## 2. 为什么这样改

**本步只抓一个重点：同一句用户输入，从接收、回答到后台处理，都必须能被认作同一条消息。** “内容相同”不能代替“消息相同”：用户今天和明天都说“项目继续”，是两次确认；同一条消息因任务失败处理两遍，才是重试。

原来用户消息在回答结束后才生成 ID。后续后台提取、失败重试和删除抑制都需要识别同一条原始消息，不能每次重造一个身份。接收时间也不能用记忆写入时间代替，否则晚完成的旧任务看起来像更新事实。

来源属于聊天与记忆共有的数据，所以放在 `messages.py`，而不是再造一套记忆专属聊天记录。`SourceMessage.to_message()` 仍转换成现有 LangChain HumanMessage/AIMessage，元数据附在 `additional_kwargs`，不复制另一份永久消息库。

### 2.1 修改前后的关键差别

基线 `finalize_reply` 在回答结束时才创建用户消息：

```python
# 基线实现节选：身份到这里才出现。
HumanMessage(content=state.question, id=uuid4().hex)
```

第1步把创建时机移到 `HumanChatApplication.stream_turn`。以下节选省去调用的其他参数：

```python
{"question": question, "input_source": new_source(
    question, user_id=self._settings.memory_user_id, session_id=session.id,
).model_dump(mode="json")}
```

`new_source` 生成一次 UUID 和带时区的接收时间。`model_dump(mode="json")` 把 Pydantic 对象转成可序列化字典，日期成为字符串，因此能跟随 Graph 状态保存。它没有调用模型，也没有保存长期记忆。

回答结束时改为复用它：

```python
SourceMessage.model_validate(state.input_source).to_message()
```

`model_validate` 从检查点中的字典恢复并校验来源对象；`to_message` 转为 LangChain 消息。两次转换没有重新生成 ID。新增的 `ChatState.input_source` 因而是“本轮输入的身份”，不是第二个问题文本入口。

### 2.2 为什么既有 SourceMessage，又有 HumanMessage

前者表达项目需要的来源契约，后者符合聊天模型与 LangGraph 的消息协议。`to_message` 的核心如下，实际位于 `messages.py`：

```python
return kind(id=self.id, content=self.content, additional_kwargs={
    "human_chat_source": self.model_dump(mode="json", exclude={"content"}),
})
```

`kind` 根据角色选择 `HumanMessage` 或 `AIMessage`。正文仍放在 `content`；归属和接收时间放在消息元数据里，避免元数据再存一份正文。这些字段供程序恢复来源，不是让回答模型自行编造可信时间。

## 3. 关键代码与数据流

```text
Application.stream_turn
  -> new_source(question)
  -> ChatState.input_source / checkpoint
  -> prepare_context 校验当前归属
  -> SourceMessage.to_message 交给回答模型
  -> finalize_reply 保存同 ID 用户消息和新助手消息
```

`SourceBatch` 区分 `new_messages` 与 `context_messages`。前者必须是有时间的用户发言；后者允许助手发言和未知旧时间。来源重复或归属混用在该边界拒绝，不靠后面的 LLM 猜测。

`history_sources()` 从既有消息恢复来源。旧消息没有接收时间时保持未知，不填当前时间；没有 ID 的旧上下文使用可重复的确定性身份，仅供理解，不伪装成新证据。

直接调用 Graph 而没有 Application 来源时，在入图处生成一次。若新一轮仍携带已提交的旧来源，会建立新身份；同一轮工具循环则始终使用原身份。

## 4. 贯穿案例

先沿一次具体调用看对象变化，下面的 `u1/u2/a1` 是便于阅读的示例 ID，真实 ID 由程序生成：

| 时刻 | 对象/行为 | 为什么重要 |
| --- | --- | --- |
| 10:00 收到“学习新概念通常先看例子” | 建立 u1，记录 user/session/10:00/原文 | 身份和时间来自输入边界 |
| 回答模型接收问题 | `HumanMessage(id=u1, ...)` | 模型所见消息与来源对应 |
| 回答完成 | 保存 u1 和新助手消息 a1 | 后台可以从检查点找到同一原文 |
| 10:02 收到“对，以后这样” | 新建 u2；u1/a1 可以作为前文 | 新的确认和旧的依据不会混成一次 |
| u2 的后台任务重试 | 仍引用 u2，而不创建 u3 | 后续回执才能识别重复处理 |

形成模块可以借 a1 理解“这样”指什么，但不能把 a1 的建议直接当成用户新事实。`SourceBatch` 为此分成两个列表：

```python
batch = SourceBatch(
    user_id="default",
    new_messages=[u2],          # 新证据，只能是有接收时间的用户消息。
    context_messages=[u1, a1], # 解释指代；不自动升级为本次新证据。
)
```

这是说明对象关系的示例，`u1/u2/a1` 在此指前面创建的 `SourceMessage` 对象。其 `@model_validator(mode="after")` 在整体对象建立后检查：ID 不重复、用户相同、新证据不能来自助手。放在批次入口检查，是因为错误通常发生在“把几条来源组合起来”时。

### 旧消息没有时间怎么办

`history_sources` 遇到旧消息不补当前时间，否则十天前的原话会被误当成最新确认。旧消息仍可作为上下文；无法确认接收时间的记录不能进入要求可信时间的 `new_messages`。这是保留旧聊天与不伪造证据之间的取舍，不是让模型猜一个时间。

用户说“以后学习新概念先举例”，Application 创建用户消息 u1。模型看到的 u1 和检查点保存的 u1 是同一个 ID。后来用户说“对，以后这样”，它是新消息 u2；未来形成模块可把前轮问答当上下文，但不能把 u1 重复计为新证据。

这只是来源基础。本步没有证明模型已正确提取偏好，也没有新增自动记忆写入。
