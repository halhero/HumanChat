# 记忆模块重构第一步：消息来源统一

日期：2026-10-15。前置资料：63；前置提交：`5ca2fcc`。

## 1. 本步改了什么

新增 `human_chat/messages.py`，集中表达消息的 ID、归属、会话、角色、原文及接收时间。Application 接收问题时创建来源，Graph 在模型输入与最终历史中使用同一个用户消息 ID。`schemas.ChatState.input_source` 让该来源进入检查点。

本步仍保留原有记忆提取和审核，尚未切换无感保存。没有变更角色、工具、语音或前端协议。

## 2. 为什么这样改

原来用户消息在回答结束后才生成 ID。后续后台提取、失败重试和删除抑制都需要识别同一条原始消息，不能每次重造一个身份。接收时间也不能用记忆写入时间代替，否则晚完成的旧任务看起来像更新事实。

来源属于聊天与记忆共有的数据，所以放在 `messages.py`，而不是再造一套记忆专属聊天记录。`SourceMessage.to_message()` 仍转换成现有 LangChain HumanMessage/AIMessage，元数据附在 `additional_kwargs`，不复制另一份永久消息库。

## 3. 关键代码与数据流

```text
Application.stream_turn
  -> new_source(question)
  -> ChatState.input_source / checkpoint
  -> prepare_context 校验当前归属
  -> SourceMessage.to_message 交给回答模型
  -> finalize_reply 保存同 ID 用户消息和新助手消息
```

`SourceBatch` 区分 `new_messages` 与 `context_messages`。前者必须是有时间的用户发言；后者允许助手发言和未知旧时间。来源重复或归属混用在该边界拒绝，不靠后面的 LLM 猜测。

`history_sources()` 从既有消息恢复来源。旧消息没有接收时间时保持未知，不填当前时间；没有 ID 的旧上下文使用可重复的确定性身份，仅供理解，不伪装成新证据。

直接调用 Graph 而没有 Application 来源时，在入图处生成一次。若新一轮仍携带已提交的旧来源，会建立新身份；同一轮工具循环则始终使用原身份。

## 4. 贯穿案例

用户说“以后学习新概念先举例”，Application 创建用户消息 u1。模型看到的 u1 和检查点保存的 u1 是同一个 ID。后来用户说“对，以后这样”，它是新消息 u2；未来形成模块可把前轮问答当上下文，但不能把 u1 重复计为新证据。

这只是来源基础。本步没有证明模型已正确提取偏好，也没有新增自动记忆写入。

## 5. 验证与待改进

实际运行 `tests/test_graph.py` 的5项相关检查，通过。直接回答检查补充了“模型所见 ID 与已保存 ID 相同、接收时间存在”的断言，原工具对话、审核恢复和取消路径仍通过。本步没有额外全量回归。

尚待处理：长期记忆的数据结构、实际持久化、版本规则、真实语义检索和后台维护。当前接收时间是消息时间，不是事实发生时间；可信的跨任务处理顺序将在后台任务登记中衔接，不把 UUID 当作时间序列。
