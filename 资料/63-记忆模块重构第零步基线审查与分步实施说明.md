# 记忆模块重构第零步：基线审查与分步实施说明

日期：2026-10-15。

## 先看懂这次重构的中心问题

2026-10-16 补充阅读导引。本文后半部分保留实施前的基线和计划；“尚未实现”指第0步当时的状态。当前已实施到第15步，不能拿下面的基线描述判断现在的代码。

原来的核心操作可以概括为：**把对话提取为几条文字，确认后追加；回答时把文字全部给模型。** 它能记住内容，却很难可靠地区分“新目标”“同一目标暂停”“以前记错了”。本轮主要改动因此是两条业务链，而不只是换一个检索算法：

```text
形成与维护：用户原话 -> 候选认识 -> 对照原话和旧记录 -> 有边界的修改 -> 持久保存
读取与使用：当前任务 -> 多路找候选 -> 判断这次有什么用 -> 按预算装配 -> 实际回答请求
```

贯穿各篇的例子是：“我想年底完成 HumanChat 记忆模块；学习新概念通常先看例子。”后来用户说：“项目先暂停，今天只给结论。”这段话至少提出四个不同问题：

| 问题 | 需要什么设计 | 对应资料 |
| --- | --- | --- |
| “暂停”依据的是哪句原话，何时收到？ | 来源身份、证据与前文分离 | 64、65、70 |
| 暂停后目标和年底期限还能保留吗？ | 结构化认识、真实落盘、局部更新 | 65～68、73 |
| 下次问项目时，该用当前暂停状态还是旧进行中状态？ | 当前/历史区分、回源检查、任务适用性 | 71、72、74 |
| “先看例子”没命中项目关键词，是否仍有机会影响回答？ | 独立背景入口；按用途选择；整组预算 | 72、74、75 |

“今天只给结论”通常只影响本轮，不应变成长期习惯；“项目暂停”则可能是值得维护的持续状态。区别依赖语义判断，不能仅凭某个字段的名字保证正确。

### 看源码时只先抓住六个边界

| 层 | 输入 -> 输出 | 它无权代替谁 |
| --- | --- | --- |
| `messages.py` | 原话 -> 稳定来源与时间 | 不判断这句话值得不值得记 |
| `memory/formation.py` | 来源批次和旧记录 -> `Mutation` 修改提案 | 不直接调用仓储保存 |
| `memory/service.py` | 提案 -> 版本/来源检查 -> 写入结果 | 不靠字符串相等判断全部自然语言含义 |
| `memory/repository.py` | 完整记录 <-> JSON 或 LangGraph Store | 不决定旧认识该更新还是撤销 |
| `memory/retrieval.py`、`context.py` | 候选 -> 本次任务需要的上下文组合 | 不保证所有 LLM 判断都正确 |
| `memory/request.py` | 组合、历史、当前消息、工具 -> 模型请求 | 不把“候选已选中”当成“必定已发给模型” |

`index.py` 是可重建的查询辅助，`jobs.py` 是后台执行进度，`application.py` 负责把这些组件创建起来并关闭。**长期记忆事实保存在 Repository 后端；向量索引和任务表不能替代它。** Graph 仍管理聊天与工具流程，长期记忆的后台维护不再成为等待用户点击的 Graph 节点。

### 为什么需要这么多步骤，阅读时又怎样减少负担

提交按风险边界拆小，所以“数据结构”和“真正保存”分了两步。学习时可以按五组阅读：64～66 理解数据如何保存；67～69 理解保存后如何变化；70～73 理解模型怎样提出修改；74～75 理解怎样进入回答；76～78 理解后台运行与验收。每组先读例子，再定位列出的函数，不需要先通读整个包。

以下源码短片段均用于解释已提交实现，不是要求你再手工应用一遍。资料会标明“本步原实现”和“最终集成补充”，避免把后来修复倒写成早期就已有的能力。原有测试结果只作历史证据；本次资料修订没有重跑运行验证。

目前最重要的限制也应先知道：这是单进程、小规模、后台最终一致的实现；模型仍会误判；目录过大可能超预算；删除长期记忆不等于删除原始聊天。后文会说明这些限制具体落在哪段代码，而不把“功能已接通”写成“整个项目已经成熟”。

后续授权说明：用户在第0步之后明确要求“一次性改完，但是分步完成”。因此后续按独立步骤连续实施、逐步写资料并推送，不再每步等待确认。本篇保留当时的基线描述和初始推进约定；最终实现、验证与提交索引见 `78-记忆模块重构第十五步集成验收与学习索引.md`。没有因此获得合并 master 或部署的授权。

本篇是正式实施的第0步，依据用户审核后的方案整理。它说明从哪里开始、原代码如何运行、旧修改如何取舍，以及后续怎样逐步实现和讲解。**本步只新增本文，没有修改业务代码，也不代表记忆新功能已经完成。**

## 2. 当前代码怎样工作

以下都是基线源码事实，不是未来设计，也没有借用旧分支的字段或能力。

```text
浏览器提交问题
  -> FastAPI / ConversationService
  -> HumanChatApplication.stream_turn
  -> Graph.prepare_context：读取并格式化全部长期记忆
  -> 回答模型；按需进行工具审核与工具调用
  -> finalize_reply：保存用户和助手两条消息
  -> extract_memory：从当前问题与助手回答提取文本候选
  -> review_memory：暂停，等待用户选择
  -> MemoryService.add：逐字去重并保存
  -> 前台回合结束
```

| 源码位置 | 当前行为 | 尚不具备什么 |
| --- | --- | --- |
| `application.py` 的 Application 与 `open_human_chat_application` | 管理会话、Graph、记忆、工具和语音资源；仓储不暴露给 API | 独立的后台记忆任务生命周期 |
| `graph.py` 的 `prepare_context` | 调用 `memory_service.format_for_prompt()` | 按任务召回、适用性选择与完整请求预算 |
| `graph.py` 的 `finalize_reply` | 在回答完成时生成问答消息 ID | 接收消息时就建立的来源时间及可信顺序 |
| `memory_extractor.py` | 用 LangChain 结构化输出提取文本，不给候选分类 | 来源引用、局部更新提案和相关旧记忆比较 |
| `memory_service.py` | 读、增、删、格式化；新增只检查文本完全相同 | 版本、来源水位、纠错、撤销与防重复操作 |
| `memory_repository.py` | JSON 原子替换；Store 按 namespace 分页列举和按 ID 存取 | 已配置并投入使用的语义索引 |
| `memory_resources.py` | 支持 JSON、内存 Store、PostgresStore；只向上提供 Service 与资源描述 | 新索引和后台任务的资源管理 |

Store 的 `search` 在当前仓储中用于分页列举，并没有传入语义查询。不能因为调用名叫 `search`，就认为项目已经实现了向量检索。

### 一个容易混淆的时间点

前端收到 `message.completed`，不等于后台维护已经完成，也不等于当前 HTTP 回合已经结束。目前 Graph 还会继续提取和审核，ConversationService 可能进入等待确认状态。无感保存要改变的是这个时序，不是单纯隐藏窗口。

## 3. 架构保留什么，准备调整什么

### 3.1 保留的基础

保留前后端分离、Application 资源组装、ConversationService 前台回合管理、LangGraph 对话与工具流程、Service/Repository 分层。`MemoryResource` 有实际资源描述作用，不因字段少而删除。现有工具审核、MCP、STT、TTS、角色配置不因记忆改造被删减。

JSON 已有临时文件替换机制，Store 已有分页和 namespace 边界处理，可以复用；不为了重构而重写相同行为。内存后端是临时数据，不承诺重启保留。PostgreSQL 后端保留适配，不因没有本轮实际数据库环境就声称已验证。

### 3.2 调整的是代码职责和依赖

计划逐步聚合为 `human_chat/memory/`，包括数据模型、维护服务、仓储、形成、检索、上下文、索引、后台任务和资源组装。**该目录本步尚未创建。** 不是先移动全部文件再解释，而是随每个职责的实施逐步迁入，并同步修正导入，不长期保留只负责转发的兼容包装。

- Graph 调用上下文组件，不直接编排记忆写入、索引或后台任务表。
- 形成模块接收原始依据与旧记录，提出受限操作，不直接改存储。
- MemoryService 执行保存、更新、纠错和删除规则，不包揽所有模型提示词和检索算法。
- Repository 只负责权威记录的存取，不判断一句话属于谁、是否值得长期保存。
- 后台维护由 Application 所属生命周期管理，不依赖前端确认，也不修改正在运行的聊天 Graph 状态。
- 消息来源是聊天与记忆共享的契约，不额外建立一套平行聊天存储。

### 3.3 四种存储不能混为一谈

| 保存对象 | 保存的是什么 | 计划中的处理 |
| --- | --- | --- |
| 长期记忆库 | 正文、范围、来源、版本、历史和操作回执 | 复用现有后端，在第3步独立讲解实际持久化 |
| 检索索引 | 检索表示、记录关联和编码器配置 | 第8步引入真实向量及快照，始终回源确认状态 |
| 后台任务表 | 来源引用、确定操作和执行进度 | 第13步用轻量 SQLite 支持恢复，不作为另一份记忆主库 |
| Graph 检查点 | 对话消息与执行状态 | 继续使用现有机制，不兼任后台维护队列 |

不强制把长期记忆迁到 SQLite 或 PostgreSQL，但存储结构和维护代码需要按已批准方案扩展。

第二册示例的 `NOOP` 不能直接作为重复确认的最终处理：内容不变仍可能出现了更新的有效证据，必须避免旧任务随后覆盖。这里需要保留来源水位，具体写入行为在第4步讲清，而不是本步先改代码。

无感保存也不是放宽依据要求。信息不足暂缓，不为后台记忆追问用户；用户当前任务确实需要消歧时，仍按正常对话需要澄清。

## 6. 正式分步路线

下面每一步是可单独解释的增量，不是要求一口气完成。一个步骤实际超过合理理解量时继续拆分，不为了压行数制造额外抽象。新模块先在隔离配置中运行，闭环具备后再切换前台主路径。

| 步骤 | 要改什么 | 为什么改 | 怎样讲解与直接验收 |
| --- | --- | --- | --- |
| 0. 基线审查（本篇） | 固定起点、旧改动取舍及正式路线 | 不把旧实现当成已批准成果 | 解释当前调用链；核对本步只有资料变更 |
| 1. 消息与来源 | 身份、归属、接收时间、顺序和必要前文 | 形成与重试需要同一证据身份 | 用“以后就这样”的问答，追踪新增证据与前文 |
| 2. 记忆数据结构 | 正文、范围、否定、状态、期限、来源、版本和历史 | 先约定保存什么，再解释保存方式 | 拆解同一目标的内容、状态、期限；未知不补造 |
| 3. 长期记忆持久化 | 存取契约、完整落盘与读回、资源生命周期 | 新字段必须真正保存，不能只停在内存模型里 | Service → Repository → JSON/Store；用隔离数据关闭后重开读回 |
| 4. 写入与局部更新 | 新增、重复确认、稳定操作、版本与局部字段更新 | 防重复、防覆盖、防丢字段 | 手工操作“暂停但保留期限”；重试与旧版本冲突 |
| 5. 纠错与撤销 | 区分真实变化、误记及不再有效 | 错误记录不能当真实历史 | 对比“以前 Windows”与“Windows 从来就记错了” |
| 6. 删除与持续禁记 | 清理内容、防旧任务恢复，区分一次删除与持续限制 | 仅不检索或 RETIRE 不等于删除 | 主存储删除与重放；索引/任务传播在8、13、14步补齐 |
| 7. 候选与依据检查 | 原话提取、来源引用、主体和持续性边界 | schema 合法不等于内容正确 | 朋友、假设、临时要求、完整原文与截断引文对照 |

| 9. 混合与分用途召回 | BM25、融合、对象线索与任务背景入口 | 一个主题排名会漏掉背景约束 | 对比各路候选，“解释协程”为何还需要初学者背景 |

## 7. 怎样让每一步都能读懂

### 7.1 文档始终围绕三个重点

1. **改了什么**：列明真正改动的文件、函数和前后行为，必要时展示短小差异，不复制整个文件。
2. **为什么改**：说明原问题、职责变化、方法选择和实际代价；新术语在理解本步需要时再解释。
3. **还有什么待改进**：哪些尚未接入、哪些只用模拟模型验证、有什么边界与下一步依赖，不能把“本步完成”写成“整个项目完成”。

每篇再给一个贯穿案例、建议阅读顺序和简短验证结论。测试不是讲解主体，不要求学习者先阅读全部测试代码；可设置少量自查问题，参考答案另列，不把答题当成继续实施的条件。

### 7.2 本步的贯穿案例

假设用户说：“我想年底完成 HumanChat 记忆模块，学习新概念时通常先看例子。”后来又说：“项目先暂停，今天只给结论。”

基线可能把多段文字作为不同条目追加，最终全量提供；没有独立状态更新和适用性选择机制，也需要用户确认保存。不能仅根据某次回答恰好正确，就声称这些机制已存在。

正式路线预期做到：来源身份可追踪；目标与偏好可独立维护；暂停保留目标与期限；“今天只给结论”只影响本轮；目标状态和适用偏好经不同用途判断后进入请求；维护在后台执行。**这里是待实现的预期，不是本步实测结果。**
