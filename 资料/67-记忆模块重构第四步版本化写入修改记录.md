# 记忆模块重构第四步：版本化写入与局部更新

日期：2026-10-15。前置资料66；前置提交 `b03304d`。

后续变更（2026-10-20）：本文记录第4步当时实现；其中手动 add 通道已在[资料79](79-记忆管理入口与旧审批残留清理记录.md)对应清理中移除。当前自动写入仍走本文讲解的 apply，版本、回执、局部更新规则不变。

## 改了什么

MemoryService 新增 inventory 和 apply。inventory 返回当前空间完整记录供内部维护比较，load 只供给有效记录。apply 执行新增、重复确认、局部更新并返回明确结果；操作回执、正文与历史通过一次仓储写入保存。

手动新增为明确用户输入建立来源；原文本提取路径暂时保留，不把其无依据的候选文本伪造成用户原话，最终在无感切换时移除。

## 为什么这样改

**本步最重要的变化：保存前先判断“这次修改是否仍有资格执行”。** 资料66的 Repository 能完整保存对象，但不知道两个后台任务是不是基于同一个旧版本，也不知道同一操作有没有成功过。

直接 upsert 只知道替换同一个 ID，不知道这个操作是否基于旧版本。apply 在共享读改写锁内先检查回执，再检查目标版本与来源时间。相同 ID 相同内容返回 already_applied；相同 ID 偷换内容拒绝；版本不符返回 conflict，不强行覆盖。

重复确认虽然内容没变，也要推进版本和证据水位。否则用户后来再次确认原状态，一个更旧但晚完成的改变仍可能覆盖它。这是对教材简单 NOOP 示例的必要修正，不是新增一次事实。

### 三个保护分别挡住什么

| 机制 | 检查的问题 | 没有它会发生什么 |
| --- | --- | --- |
| 操作 ID + receipts 摘要 | 同一操作是否已执行；内容有没有被偷换 | 网络/进程重试可能重复新增或重复推进版本 |
| expected_version | 提案依据的旧记录现在还是那个版本吗 | 同时基于第2版的两次更新互相覆盖 |
| observed_at + seen_sources | 证据是否更新；是不是旧来源重放 | 慢完成的旧原话被误当成最新情况 |

版本是记录的修订序号，时间是来源的接收顺序，操作 ID 是一次执行意图的身份。三个量不能互相替代：同一原话可以被错误地生成两个操作 ID；两个不同任务也可能都读到同一版本。

## 关键代码与案例

```python
patch = {field: getattr(mutation.assertion, field) for field in mutation.fields}
```

程序只把获准字段合入旧 Assertion，不拿缺省或缺失字段替换全部对象。目标“完成记忆模块、进行中、年底”收到 state=暂停时，value 和 deadline 保留。旧版作为 historical 保存，当前版本增加。

### 按一条 update 的执行顺序读 apply

假设记录 m1 当前第2版，输入“HumanChat 先暂停”。在形成模块尚未完成的本步，可以用一份人工构造的提案理解接口：

```python
mutation = Mutation(
    id="op-pause", user_id="default", kind="update",
    target_id="m1", expected_version=2,
    text="HumanChat 项目暂停",
    assertion=Assertion(
        subject="default", relation="项目目标", scope="HumanChat", state="暂停",
    ),
    fields=["state"], evidence=[pause_evidence],
)
result = service.apply(mutation)
```

`pause_evidence` 必须来自可信新消息；本例省略其构造，见资料65。注意提案的 `value` 没填，**不表示删除目标**，因为 `fields` 只允许改 `state`。

在 [service.py](../human_chat/memory/service.py) 中顺序是：

1. 获取同一资源的读改写锁，并核对用户归属。
2. 查所有记录中的操作回执。同 ID 同摘要，直接返回 `already_applied`；同 ID 不同内容则拒绝。
3. 读取 m1，检查仍是 active、版本仍为2、新证据比已知证据更新。
4. 将旧对象复制后保存历史，只合并获准字段；把版本升到3，更新依据。
5. 把操作摘要记入同一条记录，随后一次 `upsert_item` 保存正文、历史和回执。

这里的关键合并代码是：

```python
patch = {field: getattr(mutation.assertion, field) for field in mutation.fields}
item.assertion = type(item.assertion).model_validate({
    **item.assertion.model_dump(), **patch,
})
item.text = item.assertion.render()
```

`getattr` 在这里按明确的字段列表取值，不是在猜测对象是否兼容；`PatchField` 已限定字段集合。字典展开从左到右合并，后面的 state 覆盖旧 state，未出现在 patch 里的 value/deadline 原样保留。重新生成 text，保证展示正文跟结构一致。

结果可以直观看成：

```text
m1 第2版：完成记忆模块 / 进行中 / 年底
          |
          +-- history 保存第2版，status=historical
          v
m1 第3版：完成记忆模块 / 暂停   / 年底
          receipts[op-pause] = 这次提案的摘要
```

### 为什么先查回执，再检查版本

假设第3版已经写成功，但任务还没来得及标记完成就中断。重试仍带 `expected_version=2`。如果先检查版本，会得到冲突，无法识别这正是自己之前已经完成的操作；先查回执，才能返回“已执行”，而不再改一次。

如果另一个提案 op-deadline 也基于第2版，且没有自己的成功回执，则应得到 `version_changed`。程序不会把它的 expected_version 自动改成3后再写；这样做等于跳过重新理解新状态，可能把应当并存或已失效的变化强行应用。

### 内容没变，为什么 duplicate 还升版本

10:00 用户说目标暂停；10:05 再确认“仍然暂停”；10:03 的“准备恢复”任务因延迟最后执行。若把10:05当成什么都不做，10:03就可能覆盖更晚的确认。现在 `duplicate` 合并新依据、推进 observed_at 和版本，内容仍然是暂停，但程序知道已经收到更新确认。

这不是创建两条相同事实，也不是给旧正文制造一个多余的历史快照。它是在维护“我们最新知道到什么时候”。

模型以后只提出 Mutation；用户归属、目标版本、允许字段和幂等仍由程序控制。时间使用来源接收时间，不使用任务完成时间替代。UUID 标识身份，不用于比较时间顺序。
