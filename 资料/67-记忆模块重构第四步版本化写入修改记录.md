# 记忆模块重构第四步：版本化写入与局部更新

日期：2026-10-15。前置资料66；前置提交 `b03304d`。

## 改了什么

MemoryService 新增 inventory 和 apply。inventory 返回当前空间完整记录供内部维护比较，load 只供给有效记录。apply 执行新增、重复确认、局部更新并返回明确结果；操作回执、正文与历史通过一次仓储写入保存。

手动新增为明确用户输入建立来源；原文本提取路径暂时保留，不把其无依据的候选文本伪造成用户原话，最终在无感切换时移除。

## 为什么这样改

直接 upsert 只知道替换同一个 ID，不知道这个操作是否基于旧版本。apply 在共享读改写锁内先检查回执，再检查目标版本与来源时间。相同 ID 相同内容返回 already_applied；相同 ID 偷换内容拒绝；版本不符返回 conflict，不强行覆盖。

重复确认虽然内容没变，也要推进版本和证据水位。否则用户后来再次确认原状态，一个更旧但晚完成的改变仍可能覆盖它。这是对教材简单 NOOP 示例的必要修正，不是新增一次事实。

模型以后只提出 Mutation；用户归属、目标版本、允许字段和幂等仍由程序控制。时间使用来源接收时间，不使用任务完成时间替代。UUID 标识身份，不用于比较时间顺序。

## 验证与限制

相关7项检查通过，覆盖原手动行为、JSON/真实 InMemoryStore 的重复操作、旧版本冲突、目标字段保留、确认水位与用户归属。没有为直接转发辅助函数增加测试，也没有重跑全量。

当前只实现 add、duplicate、update；correct/retract 留给第5步，删除传播留给第6及后续索引/任务步骤。锁只在当前进程有效，多项操作不是跨资源事务，不能据本步称为多 worker 安全。

阅读顺序：Mutation → apply 的回执检查 → 目标版本检查 → 局部字段合并 → 单条 upsert。现在可以解释“存储成功”与“允许这次修改”的区别。
