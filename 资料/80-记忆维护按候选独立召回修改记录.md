# 记忆维护按候选独立召回修改记录

日期：2026-10-27。对应待办：记忆模块后续重构第一步。

## 1. 本步解决什么问题

长期记忆形成会先从一批新消息中提取一个或多个候选，再查找可能相关的旧记忆，最后让 Review 模型判断应该新增、更新、纠正、撤回还是删除。

修改前，多个候选虽然是不同的认识，却共用一次检索：

```text
候选 A 正文 + 换行 + 候选 B 正文
  -> 一次混合检索
  -> 一份 records
  -> 一份 retrieval_diagnostics
  -> Review 同时处理 A、B
  -> 一份全局可用 targets
```

这个设计存在三层串线。

第一层是查询串线。Atlas 项目目标和 Orion 部署地点会被拼成一个检索问题，它们需要共同竞争固定数量的 Top-K 位置。某个主题的强匹配可能挤掉另一个主题真正需要的旧记忆。

第二层是 Review 上下文串线。模型看到的是一份全局 `records`，无法从数据结构上判断某条旧记忆究竟是为哪个候选召回的。Prompt 可以提醒模型，但程序没有表达清楚候选与旧记忆的对应关系。

第三层是执行校验串线。所有召回结果的 parent ID 被合并成一个全局 `targets` 集合，因此候选 B 的决策可以引用只为候选 A 召回的记录。即使模型选错目标，程序也可能认为这个 ID “在召回结果中”而放行。

另外，检索诊断也是全局的。只要一次共享检索出现语义索引异常，本批所有 `add` 都会被当作无法证明是新记录。这会让一个候选的检索问题阻止其他无关候选保存。

## 2. 本步采用的设计

本步把“旧记忆匹配”改成以候选为单位，但没有把 Review 拆成多次模型调用：

```text
本批记忆快照：只读取一次

候选 A -> 用 A 的正文和身份独立召回 -> A.records / A.diagnostics / A.targets
候选 B -> 用 B 的正文和身份独立召回 -> B.records / B.diagnostics / B.targets

A、B 的独立上下文
  -> 合并为一次 Review 请求
  -> 每个决策只允许使用本候选的 targets
  -> 本候选的 diagnostics 只影响本候选
```

这里区分了两个容易混淆的概念：

- **独立召回**：每个候选分别生成检索查询、匹配记录和诊断。
- **一次 Review 调用**：所有已经准备好的候选上下文仍一次发给模型审查。

独立召回是为了保证语义边界；保留一次 Review 是为了避免候选数量直接放大模型调用次数、延迟和费用。本步没有证据表明必须“一候选一次 LLM 调用”，所以没有引入这种成本。

## 3. 修改了哪些代码

### 3.1 `MemoryRetriever.recall()` 可以使用已有快照

文件：`human_chat/memory/retrieval.py`

方法新增可选的 `items` 参数：

```python
def recall(self, query, *, purpose="answer", identity=None, items=None):
    views = memory_views(self.service.inventory() if items is None else items)
```

普通回答召回没有传 `items`，行为保持不变，Retriever 自己读取记忆。

记忆形成批次已经读取过 inventory，因此会把同一份 `items` 传给每个候选的召回。这样候选数量增加时，不会跟着重复访问 Repository，也保证同一批候选基于同一个记忆版本进行比较。

这里没有增加缓存类或快照抽象。`items=None` 只表达一个直接规则：调用方有本批数据就复用，没有就按原方式读取。

### 3.2 `MemoryFormation.prepare()` 为每个候选独立召回

文件：`human_chat/memory/formation.py`

修改前使用拼接文本：

```python
retriever.recall("\n".join(candidate.claim.text for candidate in candidates))
```

修改后按候选建立 `recalls`：

```python
recalls = {
    candidate.id: retriever.recall(
        candidate.claim.text,
        purpose="maintenance",
        identity=candidate.claim.assertion.identity(),
        items=inventory_items,
    )
    for candidate in candidates
}
```

每次查询只包含当前候选正文。`identity` 同时参与召回，是因为关键词或向量相似度不能替代结构化身份匹配；当旧记录与新候选具有相同的 subject、relation 和 scope 时，即使措辞不同，也应进入该候选的可比较记录。

### 3.3 Review 输入改为 `candidate_contexts`

修改前的关键结构是：

```json
{
  "candidates": ["A", "B"],
  "records": ["A和B共用的记录"],
  "retrieval_diagnostics": ["A和B共用的诊断"]
}
```

修改后是：

```json
{
  "candidate_contexts": [
    {
      "candidate": "A",
      "records": ["只为A召回的记录"],
      "retrieval_diagnostics": ["只属于A的诊断"]
    },
    {
      "candidate": "B",
      "records": ["只为B召回的记录"],
      "retrieval_diagnostics": ["只属于B的诊断"]
    }
  ]
}
```

这个结构本身表达了归属关系，不再只依赖 Prompt 让模型猜测。Review Prompt 也增加了对应说明：不得把其他候选的旧记录当作当前候选的更新目标。

`policies` 仍位于批次顶层，因为持续禁记策略需要对所有候选生效；它不是某次主题检索的结果，不应重复塞入每个候选上下文。

### 3.4 执行阶段按候选校验目标

程序现在建立：

```python
candidate_targets[candidate_id] = 当前候选召回记录的 parent ID 集合
```

处理某个 Decision 时，只读取对应候选的 `targets`。如果 Orion 候选错误引用了只为 Atlas 召回的记录，即使这个记录出现在同一批 Review 请求里，程序也会返回 `target_not_available`，不会生成 Mutation。

这不是额外的重复防御，而是召回结果与写入目标之间必要的业务边界：Review 可以做语义判断，但不能绕过程序提供给该候选的可选目标范围。

### 3.5 检索异常只影响对应候选

原来的 `recall.diagnostics` 属于整批。现在判断 `add` 时使用：

```python
recall_diagnostics = recalls[candidate.id].diagnostics
```

因此，候选 A 的语义检索不可用时，仍只暂缓 A 的新增；候选 B 召回完整时可以正常形成新增操作。

## 4. 为什么没有删除“诊断存在时暂缓新增”

本步只纠正诊断作用范围，没有直接删除这条规则。

它要防止的真实风险是：仓库已经存在相关旧记忆，但语义召回失败，关键词又因措辞变化没有命中，此时直接新增可能制造重复或冲突。因此它不是完全没有意义。

但当前规则仍然偏粗：只要本候选存在任意召回诊断且仓库非空，就暂缓新增，没有进一步区分“索引未配置”“索引部分过期”“查询完全失败”对当前候选的实际影响。这一点尚未证明是最佳取舍，后续必须结合召回设计单独审核。本次不借修复串线问题顺便扩大规则改造。

## 5. 验证了什么

本步只增加两个针对真实风险的测试：

1. Atlas 和 Orion 两个候选分别只收到自己的旧记录；Orion 决策若错误引用 Atlas 目标，会被 `target_not_available` 拒绝。
2. 第一个候选出现召回诊断时，只阻止第一个候选新增，第二个候选仍能生成 Mutation。

同时运行已有形成和检索测试，确认单候选形成流程和回答召回接口仍可工作。

验证结果：

```text
python -m pytest tests/test_memory_formation.py tests/test_memory_retrieval.py ...
6 passed

python -m ruff check human_chat/memory/formation.py human_chat/memory/retrieval.py tests/test_memory_formation.py
All checks passed
```

第一次 pytest 执行被系统临时目录权限阻止，测试没有进入业务逻辑；改用项目内独立临时目录后通过。没有把环境权限问题伪装成代码失败，也没有为此修改生产代码。

## 6. 本步明确没有修改什么

- 没有处理回答阶段把全部当前记忆加入候选的问题。
- 没有删除自由 `bundle` 分组。
- 没有修改索引后台同步策略。
- 没有重写 MemoryService 或 Repository。
- 没有新增持久化字段、缓存框架或数据库结构。
- 没有删除 receipts、seen_sources、suppressed、blocked_identity 等机制。
- 没有把一次 Review 拆成多次模型调用。

## 7. 仍待改进的地方

1. 候选独立召回后，同一旧记录若与多个候选都相关，会在 Review payload 中重复出现，增加一部分 token；这是明确表达归属关系的当前代价，后续只有在真实预算压力出现时再优化。
2. `Assertion.identity()` 仍依赖 subject、relation、scope 的提取一致性。模型使用近义 relation 或漏掉 scope 时，身份通道仍可能漏召回，需要由后续召回质量设计处理。
3. 候选自己的召回诊断仍可能过于保守地阻止新增，本步只消除了跨候选误伤。
4. 回答上下文选择和本步的维护召回是两条不同流程；本步完成不代表整体记忆检索质量已经完善。

下一步不能自动开始。应先由用户审查本步代码和本文档，再决定是否进入“移除自由 bundle”或对本步继续调整。
