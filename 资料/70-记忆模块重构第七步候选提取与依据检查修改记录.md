# 记忆模块重构第七步：候选提取与依据检查

日期：2026-10-15。前置资料69；前置提交 `e7ba613`。

## 改了什么

新增 `memory/formation.py` 的 Candidate、Extraction、GroundedCandidate 和提取流程。候选带 Assertion、表达性质、维护意图、明确提供的字段及原话引用。新增 `memory/tokens.py` 限制辅助模型输入，配置候选数量和处理预算，依赖清单声明 tiktoken。

本步没有替换现有 Graph 提取路径，也不写入长期记忆；先独立解释“原文到候选”。

## 为什么这样改

**这一步只把原话变成“值得继续审查的候选”，不把模型提取结果直接当作事实。** 需要区分两种错误：引用根本不存在，程序可以检查；引用存在但理解反了，必须继续作语义复核。

同样提到 Linux，“假如换Linux”和“我已经换Linux”不一样；“朋友喜欢Rust”不能变成用户偏好。结构里明确这些维度，便于复核，不表示 schema 本身能理解语言。

程序 ground_candidate 只检查来源、引用、前文ID和明确不支持的候选性质。语义支持仍需后续完整原文判断，不能因为引文里有“Linux”就认为整条断言成立。

## 数据流和代码讲解

```text
SourceBatch -> LangChain结构化输出 -> Extraction
  -> 候选数量边界
  -> ground_candidate 核对新用户原话
  -> 程序填入 user:实际用户ID
  -> GroundedCandidate 与诊断
```

来源时间、user_id、session_id 从应用消息取得，不让 LLM 填。context_messages 可包含必要助手原文，帮助理解新用户的“对”；但证据锚点仍须是 new_messages。

失败候选逐条记录原因，不为一个无效引文抹掉其他有效候选。输入或整体模型输出错误交给处理边界，不层层吞异常。

### 先看模型到底要输出什么

原话：“以后学习新概念通常先给我看例子，今天这次只给结论。”期望的持续性候选可以概括为：

```text
text              学习新概念时先看例子
subject_kind      user
modality          asserted
intent            assert
assertion.scope   学习新概念
assertion.value   先看例子
supplied_fields   [value, scope]
evidence          [{message_id: u1, quote: 以后学习新概念通常先给我看例子}]
```

这是解释字段含义的示例，不是一次真实请求的逐字输出。另一句“今天这次只给结论”可以影响本轮回答，但不应作为长期偏好进入有效候选。

| 字段 | 回答什么问题 | 为什么不能省略 |
| --- | --- | --- |
| subject_kind | 说的是用户、项目，还是别人？ | 防止朋友的情况混成用户资料 |
| modality | 在断言，还是假设、提问、临时要求？ | “假如用 Linux”不等于已经使用 |
| intent | 新认识、补充、变化、纠错还是维护要求？ | 后续不能把“删除它”存成一句新事实 |
| supplied_fields | 新原话明确提供了哪些变化？ | “暂停”不能顺带清空期限 |
| evidence | 哪条新用户消息的哪段原文？ | 后续必须回查真实依据 |
| context_message_ids | 为了理解指代参考了哪些前文？ | 前文帮助解释，但不是新证据 |

这些字段仍由模型理解后填写，所以 schema 只约束输出形状。模型把 temporary 错填成 asserted，类型检查也会通过。我们保留第二次读完整原话的复核，正是为了面对这种风险。

### ground_candidate 的检查为什么要落在这里

实际核心代码位于 [formation.py](../human_chat/memory/formation.py)：

```python
sources = {message.id: message for message in batch.new_messages}
for quote in claim.evidence:
    source = sources.get(quote.message_id)
    if source is None or quote.quote not in source.content:
        raise ValueError("quotation_not_in_new_user_source")
    evidence.append(Evidence(
        message_id=source.id, user_id=source.user_id, session_id=source.session_id,
        message_time=source.occurred_at, quote=quote.quote,
    ))
```

第一行建立“新消息 ID -> 真实消息”的字典。循环中要求引用能在这份原文中找到，再从真实消息填入身份与时间；不会采用模型自报的接收时间。返回的是可信来源锚定后的 Evidence，而不是模型最初给出的 Quote。

注意 substring 检查的局限：原文“我不喜欢 Python”确实包含“喜欢 Python”。所以“引文存在”不能证明“用户喜欢 Python”。第二次复核必须看到完整 new_messages，检查否定、条件、主体和范围，而不只看候选挑出的短引文。资料73会继续这条链。

### 为什么形成流程不用助手回答当新事实

前文是助手建议“可以先做一个示例”，用户新消息仅为“对，以后这样”。上下文有助于解释“这样”；新确认仍锚定在用户这条消息。如果用户没确认，助手自己的建议不能变成“用户长期喜欢这种方式”。

程序能检查 context ID 是否来自已提供前文，但不能凭这个检查证明用户确实确认了全部建议。因此上下文集合只解决可追踪性，确认范围仍由语义复核判断。

### extract 为什么返回两个集合

`accepted` 是继续处理的 `GroundedCandidate`；`diagnostics` 记录候选为什么被排除，例如 unknown_context 或 quotation_not_in_new_user_source。每个候选有稳定的批次内编号 candidate-0、candidate-1，便于第二次模型调用把决定对应回原候选。

候选检查失败只排除该候选；如果整个响应无法解析、超预算或超候选数量，则本批次失败交给后台任务处理。这个区分避免一条无效引用抹掉其他合法候选，也避免把整体模型失败伪装成“没有值得记的内容”。

## 案例与验证

合成输入“我喜欢Python”生成四个模拟候选：合法、假设、虚构来源、第三方。程序只保留合法项，另外三项有明确诊断。该风险用例实际通过，证明约束处理，不证明真实模型能自动识别这四类。

第7步原提交 `b239459` 的 `structured_call` 使用 function_calling。**最终集成 `be5476a` 已改为 JSON mode，并为记忆辅助调用设置非思考模式与独立输出预算**，这是实际供应商验证后的调整，不能再按旧描述理解当前代码。两种方式都经 LangChain 结构化接口解析；JSON 格式有效也不保证内容正确。详情见资料78。

预算使用 cl100k_base tokenizer 加余量，但它只是 Qwen 的代理估计，不是原生精确计数。[tokens.py](../human_chat/memory/tokens.py) 检查完整辅助请求，输入过大时抛出 MemoryBudgetError；不会偷偷裁掉否定词或后半句来“凑够长度”。

## 待改进与阅读顺序

本步不完成语义复核、旧记忆比较、保存或无感后台。下一步先接真实语义索引；第10步把候选和旧记录交给决策，明确支持/反驳/未知，防止程序校验被误解为语义确认。

读 Candidate → EXTRACT_PROMPT → ground_candidate → extract。重点分清“模型描述表达性质”和“程序验证引用合法”，二者都不能单独保证认识正确。

自查：一个候选引用真实、字段齐全，能马上 add 吗？不能；它仍可能把否定理解反、遗漏范围，或与已存记录重复。下一阶段必须结合完整原话和旧记录决定具体操作。
