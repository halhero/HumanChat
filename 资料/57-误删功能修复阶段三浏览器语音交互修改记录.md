# 误删功能修复阶段三：浏览器语音交互修改记录

## 1. 本阶段目标

阶段二已经提供稳定的语音 API。本阶段在 React 前端恢复用户真正能使用的语音功能：

1. 浏览器启动时读取后端语音能力；
2. 使用浏览器麦克风录制音频；
3. 支持选择已有音频文件；
4. 将音频上传给 STT，并把识别文字放入输入框；
5. 为每条助手消息提供按需朗读；
6. 提供可持久化的自动朗读开关；
7. 正确回收麦克风、请求、Audio 对象和 Blob URL；
8. 保持桌面和移动端布局紧凑，不把技术细节暴露给普通用户。

本阶段不把工具调用过程展示给聊天用户，也不重新引入 CLI。语音交互是聊天表现层功能，
因此放在 Web 端。

## 2. 完整数据流

### 2.1 语音输入

```text
用户点击麦克风
    -> navigator.mediaDevices.getUserMedia({audio: true})
    -> MediaRecorder 产生音频 Blob
    -> FormData 上传 /voice/transcriptions
    -> FastAPI -> Application -> STT Service
    -> 返回文字
    -> 填入聊天输入框
    -> 用户检查后手动发送
```

选择音频文件时跳过录制步骤，其余流程完全相同。前端没有第二套文件转写实现，录音和文件
统一进入 `transcribeAudio()` API。

### 2.2 语音输出

```text
用户点击助手消息的朗读按钮
    -> POST /voice/speech {text}
    -> FastAPI -> Application -> TTS Service
    -> 返回 audio Blob
    -> URL.createObjectURL(blob)
    -> new Audio(url).play()
```

自动朗读也复用同一个 `playSpeech()`，仅触发时机不同，不会出现手动朗读和自动朗读两套
音频生命周期代码。

## 3. 为什么转写后不自动发送

STT 结果可能出现人名、专有名词、数字或语言识别错误。如果前端拿到结果后立即开始
Agent 对话，会产生三个风险：

1. 用户没有机会纠正识别错误；
2. 错误内容可能触发不必要的工具调用；
3. 错误内容可能进入长期记忆候选流程。

因此转写结果只更新 `draft`：

```typescript
setDraft((current) =>
  current.trim() ? `${current.trim()} ${text}` : text,
);
```

用户仍需点击发送或按 Enter。这是一次明确的人机确认，同时允许在已有草稿后追加语音
内容。

## 4. `useVoice` 为什么独立成 Hook

语音交互包含较多浏览器状态：

- 后端能力；
- 是否录音；
- 是否正在转写；
- 哪条消息正在生成音频；
- 哪条消息正在播放；
- MediaRecorder 与 MediaStream；
- STT/TTS AbortController；
- HTMLAudioElement 和 Object URL；
- 自动朗读偏好。

如果全部放入 `App.tsx`，会话流、审核流和设备生命周期会混在一个组件里。新增
`hooks/useVoice.ts` 后：

- `App` 只负责把转写文本放入 draft，并把错误交给统一 toast；
- `ChatView` 只渲染按钮和状态；
- `useVoice` 独占浏览器语音资源和清理逻辑；
- `api.ts` 独占 HTTP 格式。

这不是为了追求文件数量，而是把具有独立生命周期的一组复杂状态收口。

## 5. MediaRecorder 基础语法

浏览器先请求音频轨道：

```typescript
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```

随后创建录制器：

```typescript
const recorder = new MediaRecorder(stream, { mimeType });
recorder.ondataavailable = (event) => chunks.push(event.data);
recorder.start(250);
```

参数 `250` 表示浏览器大约每 250ms 产生一个数据块。停止时再合并：

```typescript
const blob = new Blob(chunks, { type: recorder.mimeType });
```

不同浏览器支持的编码不同，所以代码按顺序检测：

```text
audio/webm;codecs=opus
audio/mp4
audio/ogg;codecs=opus
audio/webm
```

`MediaRecorder.isTypeSupported()` 确保不会把浏览器不支持的 MIME 强行传给构造函数。

## 6. 麦克风权限和并发保护

`getUserMedia()` 只能在安全上下文或 localhost 使用，并会由浏览器向用户请求麦克风权限。
权限被拒绝时，界面显示“没有获得麦克风权限”，文本聊天仍然可用。

`startingRecordingRef` 防止用户在权限窗口出现前连续点击，创建多个并发
`getUserMedia()` 请求。组件卸载期间如果权限请求才返回，代码会立即停止刚获得的 tracks，
不会留下浏览器仍在使用麦克风的状态。

结束录音或组件卸载时执行：

```typescript
stream.getTracks().forEach((track) => track.stop());
```

停止 MediaRecorder 并不保证自动释放物理设备，显式停止每条 track 才能让浏览器关闭
麦克风占用指示。

## 7. FormData 与文件上传

音频上传使用：

```typescript
const form = new FormData();
form.append("audio", audioBlob, filename);
fetch(url, { method: "POST", body: form });
```

这里不能手动设置 `Content-Type: multipart/form-data`。浏览器需要自动生成 boundary，并把
它同时写入 Header 和 Body；手动设置通常会导致 FastAPI 无法解析文件。

前端会先根据后端返回的 `max_audio_bytes` 做一次快速大小检查，避免明显超限文件消耗上传
时间。后端仍然执行最终校验，因为客户端校验不能作为安全边界。

Windows 或某些浏览器可能不给文件提供 MIME。代码会根据 `.wav`、`.mp3`、`.m4a`、
`.webm`、`.ogg`、`.flac` 等扩展名补充类型；无法识别时直接提示用户，不发送含糊的
`application/octet-stream`。

## 8. 音频播放与 Object URL

浏览器拿到 `Blob` 后不能直接把二进制对象交给 `Audio.src`，所以创建临时 URL：

```typescript
const url = URL.createObjectURL(blob);
const audio = new Audio(url);
await audio.play();
```

Object URL 会让浏览器保持对 Blob 的引用。如果每次朗读都创建而不释放，会逐渐积累内存。
因此播放结束、切换消息、用户停止或组件卸载时都会执行：

```typescript
audio.pause();
URL.revokeObjectURL(url);
```

同一时刻只保留一个 Audio。点击另一条消息会先停止当前播放，再生成新音频；点击正在播放
或正在生成的同一条消息则表示停止。

## 9. AbortController 的作用

STT 和 TTS 都可能是耗时网络请求。Hook 为两类请求分别保留 `AbortController`：

- 新转写开始时取消旧转写；
- 用户停止朗读时取消仍在等待的 TTS 请求；
- 组件卸载时取消所有未完成请求。

取消产生的 `AbortError` 不显示为错误 toast，因为它是用户或生命周期主动结束，不是系统
故障。

## 10. 自动朗读设计

自动朗读是显式开关，并通过：

```text
localStorage["human-chat:auto-speak"]
```

保存到当前浏览器。刷新页面后仍保持用户选择。按钮使用 `aria-pressed` 表达切换状态，既
便于辅助技术识别，也能让 CSS 精确显示启用状态。

只有同时满足以下条件才自动请求 TTS：

- 用户已开启自动朗读；
- 后端报告当前角色配置了 TTS；
- SSE 收到新的 `message.completed` 助手消息。

加载历史会话不会把所有旧消息重新朗读。

## 11. 可选能力如何不影响文本聊天

页面启动时请求 `/voice/capabilities`。如果旧后端、网络故障或可选语音模块不可用：

- 不显示语音输入和朗读按钮；
- 不弹出阻塞聊天的启动错误；
- 会话列表、文字发送和审核流程继续工作。

实际点击语音功能后产生的失败会显示统一错误提示。这样避免“可选能力发现失败”和“用户
明确操作失败”使用同一严重程度。

## 12. 界面调整

输入框左侧增加两个图标按钮：

- 音频文件图标：选择本地音频；
- 麦克风图标：开始录音，录音中显示停止符号，转写中显示 spinner。

助手消息下方增加小型扬声器按钮。顶部增加自动朗读开关。所有按钮均具有：

- `aria-label`；
- `title` 工具提示；
- 固定宽高，状态切换不会推动布局；
- disabled 状态；
- 键盘 focus 样式。

没有增加解释型卡片、技术状态面板或工具调用日志，聊天界面仍保持精简。
