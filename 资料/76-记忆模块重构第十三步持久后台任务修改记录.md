# 第十三步：可恢复的后台记忆维护任务

## 1. 为什么需要这一层

**本步只抓住一个顺序：先保存“准备怎么改”，再真正改记忆，最后记录任务完成。** 后台线程解决不阻塞用户，任务表解决进程中断后还能知道做到哪里；二者不是同一件事。

回答结束后才形成长期记忆，不应让用户等候保存或批准。但简单启动一个临时线程，进程关闭就会丢任务；重启重新提取又可能产生不同操作并重复写入。因此引入小型 SQLite 任务表，而不是新建通用任务平台。

## 2. 修改位置与职责

- 新增 `memory/jobs.py`：`MemoryJobs` 管理持久任务和计划；`MemoryWorker` 管理单工作线程、有限重试与索引同步。
- `memory/service.py`：增加删除监听，把删除传播到待执行计划；相同被删除来源不能通过重新提取换一个断言描述再次复活。
- `memory/index.py`：没有变化时不重复写快照。

任务表只长期保存来源ID、checkpoint定位、用户/会话、状态和简短结果。待执行计划临时包含 Mutation；完成后清空计划正文，不永久复制全部对话。来源原文由应用在第十四步按不可变 checkpoint 读取。

## 3. 执行过程

```text
enqueue(用户、来源ID、checkpoint) -> 稳定job_id，重复登记无效
pending -> 从checkpoint读取来源 -> prepare -> 持久化FormationPlan
planned -> 依次MemoryService.apply -> done，清空计划
异常 -> 有限延迟重试；达到3次 -> failed，保留可排查状态
```

最重要的顺序是“先存计划，再执行”。如果主记录已经写入但进程没来得及标记任务完成，恢复后读取原计划，用相同 operation_id 再提交；主记录内的 receipt 返回 already_applied，不再新增版本。不会重新让模型临时生成另一套操作。

任务生成阶段失败可重新提取；已经生成计划后的重试只重放计划。版本冲突/被删除/禁记属于有业务结果的操作，不无限重试覆盖新记录。

### 3.1 为什么已经有 checkpoint，还要 SQLite 任务表

checkpoint 保存聊天/Graph 执行状态，可以找到 u2 的原话；它没有保存“u2 对应的后台计划是否已经执行到某一步”。如果只扫描聊天重新提取，LLM 第二次可能给出不同操作，无法稳定判断是否重复。

任务表保存的是执行账目，长期记忆仍存原 Repository：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| id / source_id | 后台任务身份及原话身份 | J / u2 |
| thread_id / checkpoint_id | 从哪份对话快照找来源 | 会话 t1 的快照 c8 |
| source_time | 来源接收时间，用于待办顺序 | u2 的原接收时间 |
| status / attempts / retry_at | 进度与有限重试安排 | planned / 1 / 下次可重试时间 |
| plan | 尚未执行完的确定操作 | op-pause 修改 m1 第2版 |
| outcome / error | 简短结果或失败标记 | applied / maintenance_failed |

`INSERT OR IGNORE` 配合固定 job_id，使正常登记和启动对账遇到同一来源时不会创建两个任务。SQL 参数通过占位符传入；消息文本不拼成 SQL 指令。

### 3.2 process_one 里最关键的十几行

以下节选 [jobs.py](../human_chat/memory/jobs.py)，省略异常处理和结果格式化：

```python
if job["plan"]:
    plan = FormationPlan.model_validate_json(job["plan"])
else:
    plan = self.formation.prepare(self.load_source(job), job["id"])
    self.jobs.save_plan(job["id"], plan)
    job["plan"] = plan.model_dump_json()
if self.jobs.is_done(job["id"]):
    return True
outcomes = [self.service.apply(operation).outcome for operation in plan.operations]
self.jobs.finish(job["id"], ",".join(outcomes) if outcomes else "no_supported_change")
```

有 plan 就恢复同一计划，没有才调模型。`save_plan` 返回后才调用 apply，因此计划必须先落盘；在内存 job 中也记下 plan，异常重试时才能选择 planned 而非重新提取。

`is_done` 用于识别形成期间任务已因删除被放弃的情况。它不是分布式抢占锁，也不是逐条操作之间的跨库事务。单进程之外的并发部署不能凭这行得到保证。

### 3.3 三个中断位置，恢复行为完全不同

| 中断位置 | 已保存状态 | 下次怎么做 |
| --- | --- | --- |
| 模型形成过程中，计划尚未保存 | pending，plan 为空 | 可以重新提取，因为尚未开始 apply |
| 计划已保存，尚未写记忆 | planned，plan 完整 | 恢复计划，执行固定操作 |
| 记忆已写成功，任务未 finish | planned，主记录已有 receipts | 重放原操作，Service 返回 already_applied |

第三种就是资料67“先查回执再看版本”的真正使用场景。任务库和记忆库不必处于同一事务，也能通过确定计划加幂等执行避免同一操作重复生效；这不是所有故障条件下的分布式 exactly-once 保证。

如果计划有两条操作，第一条成功后中断，恢复时第一条回执命中，第二条继续。若第二条已与新版本冲突，则得到 conflict 并记录结果，不强行修改 expected_version。

### 3.4 什么会重试，什么不会

网络异常、解析异常等通过异常路径进入 `failed`：累计失败次数，小于3次时延迟重试；达到3次置为 failed，不再被 `next` 取出。已有计划继续保留，以便排查。

业务结果 rejected/conflict 不抛网络异常，任务会以对应 outcome 完成。零操作得到 no_supported_change，也可以正常 done。defer/reject 的诊断在计划阶段存在，完成后计划清空，当前日志只记录数量，**没有持久的逐候选原因审计界面**。

因此“任务 done”表示这次处理流程结束，不等于所有候选都保存成功；“暂缓”也不表示系统已经安排自动重新审查。后续运营工具应针对这些真实缺口设计，而不是先建立通用任务平台。

## 4. 生命周期和删除

线程非游离任务，由应用 start/close。close 唤醒并等待线程退出，数据库和 checkpoint 要在线程退出后才能关闭；实际应用接线在下一步。正在执行的外部请求由模型超时约束，不强行中断已进行的主存储写入。

删除时清除引用目标或已知来源的待执行计划。若同一来源还包含其他认识，本轮保守放弃整个相关任务，优先避免复活被删除内容；后续新证据仍可保存其他信息。这是明确取舍，不宣称细粒度语义擦除已完美解决。

SQLite 启用 secure_delete，完成/取消后计划列清空；这不等于对操作系统备份、旧磁盘块或原始聊天记录的取证级擦除。删除长期记忆不自动删除用户聊天历史。

索引同步在工作线程执行，失败后至少等待60秒再试；记录维护重试有限，不因索引故障重复提交主记录。没有变动不重写索引快照。

实际顺序是 `process_one` 完成主记录维护并标记任务 done，然后 `_run` 尝试 index.sync。索引失败不会把已成功写入的业务任务重新置为 pending；它有独立的60秒重试节流。**done 不能用来证明向量索引已同步**，读取端仍需资料71、72的回源和覆盖检查。

`Event` 负责唤醒/停止，线程空闲时等待，避免持续空转。`daemon=False` 加 close 中的 join 表示应用主动等线程退出，再关闭任务数据库与检查点。若请求正在等待模型，关闭可能等到请求完成或超时；当前没有强杀模型调用或“关闭立即返回”的保证。

最终集成补了 `enabled`：关闭自动提取时保留队列，但 `process_one` 不再执行；索引同步仍可继续。这样既不偷偷处理旧待办，也不需要靠 formation=None 引发异常来实现暂停。
